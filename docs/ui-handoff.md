# UI 队员接手指南

目标：在已有业务流程上改善信息层级、视觉一致性、长内容阅读和运行反馈，为比赛演示形成完整的产品体验。

2026-10-08 M2 引导修复：成功时提示待确认事项可在使用最终提示时补充；失败时区分内容格式、方案关联、任务核心信息、超时、网络、权限和额度，提供下一步及诊断目录。请保留这些说明及重试入口。方案内的新未知显示“AI 规划时提出，待确认”，不应改成必须逐项处理才能继续的关卡。

## 1. 先找到实际生效的位置

`PromptSmithApp(GuidedFlowMixin)` 定义于 `src/promptsmith/ui.py`。初始化调用的 `_build_layout()` 来自 `guided_flow.py`。当前需求页、方案页、结果页和主动作也主要由 Mixin 定义；Skill 页在 `ui.py`。

`ui.py` 中 `_legacy_build_layout`、`_legacy_build_requirements_page`、`_legacy_primary_action` 等是历史实现，修改它们可能不会影响当前界面。主题与窗口配置仍由 `_configure_root()` 处理。

| 改动目标 | 入口 |
|---|---|
| 框架、导航、底部主按钮 | `GuidedFlowMixin._build_layout` |
| 设置页、模型表单与返回工作区 | `_build_settings_page`, `show_settings`, `return_from_settings` |
| 当前需求、追问与完整选项 | `_build_requirements_page`, `_format_guided_question`, `_format_guided_questions` |
| 当前下一步的标签与行为 | `_primary_action`, `_refresh_primary_action`, `run_primary_action` |
| 方案核对 | `_build_plan_page`, `confirm_preview_and_plan`, `confirm_plan_and_generate` |
| Skill 列表、详情与选择 | `PromptSmithApp._build_skills_page` 及 Skill 搜索/刷新方法 |
| 本地与网络搜索反馈 | `_local_skill_search_ok`, `_network_skill_search_ok` 及对应失败路径 |
| 成果预览与交付 | `_build_export_page`, `copy_current_prompt`, `export_current_result` |
| 滚动、菜单、长内容 | `_scrollable_page`, `_route_page_mousewheel`, `_tree`, `_bind_context_menu` |
| 主题与字体 | `PromptSmithApp._configure_root` 和各页面样式 |

`self.widgets` 的键被事件、刷新方法和多项 UI 测试引用。拆组件或改控件时建立旧键到新控件的映射，查清依赖再移除。

2026-10-08 的首轮调整：默认窗口目标 1440×810（16:9），按屏幕可用空间等比例缩小，保留自由调整大小。模型设置已移入独立设置页，右上角“设置”位于“保存”左侧；设置页可返回之前的工作区，缺少模型配置或尚未确认时主动作也会进入设置。测试连接和获取模型不确认配置；只有独立“确认”按钮写入当前运行时的确认快照，正式模型请求要求快照仍有效。修改任意连接字段需重新确认，确认不调用 API，也不把密钥写入会话。原四个工作区仍为索引 0–3，设置追加为索引 4，原模型控件键继续可用。

## 2. 首轮设计建议

为五个用户阶段分别画主视图：描述任务、澄清需求、确认方案、选配 Skill、交付提示。当前实现是四工作区，新设计可以合并/拆分视觉页面，但要维护相同业务路径。

建议浅色内容区配深色导航和蓝青色强调色。优先定义中文字体层级、间距、表单、按钮、卡片、提示状态及图标；用同一套规范制作 PPT 和技术图。

页面上始终能回答：我正在做什么、已完成什么、现在是 AI 在处理还是在等我、下一步在哪里。主要操作突出，低频设置折叠，长文案可完整展开。对内部 M1/M4、Schema、ID 等信息提供诊断详情入口。

## 3. 必须设计的状态

| 区域 | 至少覆盖 |
|---|---|
| 模型设置 | 未配置、待确认、已确认、修改后待重新确认、探测中、探测成功、探测失败、正式请求失败 |
| 需求 | 初始、分析中、待回答、可核对、用户修改后待分析、保留未知的草稿 |
| 方案 | 未生成、生成中、可编辑、已确认、依据变化而过期、生成失败保留旧方案 |
| Skill | 未搜索、本地处理中、本地有/无结果、网络处理中、部分成功、无结果、失败、已选择 |
| 交付 | 草稿、可复制/导出、有待补充事项、来源失效需重建、试运行中/失败 |

搜索结果卡片至少展示：名称、适合解决的工作、推荐原因、来源链接或本地路径、信息不足的说明、选中状态。读取状态是简洁说明，无需做成额外操作关卡。

后置待补充项应可在最终提示中阅读并带出；不要新增末端确认墙。技术错误要说明可执行的恢复操作，保留用户已经输入的内容。

## 4. 与业务逻辑连接的约定

- 页面输入通过现有 `_sync_input`、会话编辑/确认方法落地；不要直接给 `confirmed_*` 字段赋值。
- 主按钮文字与动作取同一状态判断，避免“提示处理冲突，点击却无反应”重现。
- 需求、方案和 Skill 改动保留来源与版本失效逻辑；取消选用调用真实取消/重建路径。
- 网络调用继续通过后台提交和主线程回调，状态文案只显示实际已发生的进展，不伪造百分比。
- 展示完整问题与选项，不按固定字符数裁掉语义，也不把问题的必要后半段放进另一个隐藏解释区。
- 暂存、返回、失败、取消和恢复后的内容可见；不要仅在理想成功路径上设计页面。
- 文案与色彩表达状态时保持一致；错误、警告、成功同时有文字，不能只靠颜色。

## 5. 与功能队员的边界

UI 队员可直接修改布局、样式、呈现文案、视觉资源和可访问性。业务结构、模型输出格式、来源校验或确认条件有变动时，在 PR 中说明目标与影响，与负责模块的功能队员共同检查。

如果选择 Web 或新的 UI 框架，需要先定义可序列化的状态接口、事件接口、异步任务和文件操作方式。当前仓库没有可直接连接的前端 API；本轮交接不要求更换技术栈。

## 6. UI 验收与交付

每批改动对应相关检查，参见 [开发指南](development.md)。人工检查建议覆盖：

1. 新用户从初始页进入任务，能找到模型设置和开始入口。
2. 长任务、多题、完整选项和长中文内容可读，不遮住主要按钮。
3. 一次正常无 Skill 流程可复制、导出、保存重开。
4. 本地无 Skill 时能理解原因并继续；网络部分失败仍展示可用结果。
5. 选择/取消 Skill 后最终文本中的名称、来源和用途对应当前选择。
6. 超时、错误、返回修改时输入仍在，主操作恢复有效。
7. 常用窗口尺寸以及真实 100%/125%/150% DPI 下，内容和按钮可到达；鼠标滚轮、键盘焦点、右键复制正常。

交付物：关键页面预览、视觉规范、实现改动、改动范围与相关检查记录、同版演示截图。截图中隐藏密钥和个人信息；比赛材料还需遵守匿名要求。

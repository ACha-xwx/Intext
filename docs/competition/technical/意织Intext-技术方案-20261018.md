# 意织 Intext 技术方案

## 项目摘要

意织 Intext 是一款面向 AI 使用者的 Windows 桌面应用。用户从一句任务目标开始，通过澄清问答、需求核对和方案确认，逐步形成一份可交给下游 AI 使用的提示词。软件还可查找本地及网络中的 Agent Skill，将选定 Skill 的来源、用途和使用位置写入交付内容。

项目采用 Python 与 WebView2，使用外部大语言模型分析自然语言，由本地会话状态管理来源、版本、用户确认和任务取消。当前功能包括多供应商配置、流式输出、问答回退、历史会话恢复、Skill 推荐、Markdown 导出与独立 Debug 控制台。研发重点是把含糊目标整理为可核对、可修改的任务说明，并控制重复请求和重复上下文带来的成本。

项目已形成可运行的安装版本，并开展了用户试用。后续将通过固定任务对照评测，记录任务完成质量、操作时间与模型用量，为访谈和 Skill 推荐策略的调整提供依据。

## 一、产品概述与定位

### 1.1 背景与研发目标

生成式 AI 已进入文本写作、学习和办公任务。CNNIC《生成式人工智能应用发展报告（2026）》称，截至 2026 年上半年，我国生成式 AI 用户规模突破 7 亿人，普及率超过 50%；报告脚注注明，这两个数值来自 CNNIC 依据网络数据平台的测算。[1] 同一报告引用截至 2025 年 12 月的电话问卷数据：生成处理文本的使用目的占比为 37.6%，生成工作总结、会议纪要、PPT 等办公内容为 32.5%。[1][2] 这些数据支持写作与办公场景的选择，尚不足以推算提示词工具的市场规模。

团队在研发和试用中遇到的一个问题是：用户往往能说出“想完成什么”，却没有一次说明受众、素材、限制和交付格式。例如，“做一份奖学金答辩 PPT”已经给出了任务，但没有交代答辩时长、展示重点、材料是否齐全，以及需要逐页内容还是演讲稿。下游模型可能自行补齐这些条件，也可能先生成一份需要返工的结果。

意织把任务准备过程做成连续对话。模型负责识别当前还缺少哪些重要条件；用户可以回答、跳过或修订；程序保留已经确认的内容，并在生成方案前展示给用户核对。方案确认后，软件将任务要求、步骤、交付形式及一般性未知信息组织成提示词。对于能从专项知识或工作方法中受益的任务，用户还可以加入 Agent Skill。

研发目标包括：让初次使用者从简短目标开始完成任务说明；让较长任务的需求与方案保持版本一致；让提示词包含清楚的执行步骤和完成标准；在可继续交付的情况下保留未知，减少反复追问。项目同时关注模型请求耗时、上下文体积和用户中断能力，因为提示词准备本身也会消耗时间与模型额度。

### 1.2 产品定位、用户与使用边界

意织属于 AI 赋能的任务准备与提示构建工具，主要面向需要借助 AI 完成具体工作的学生、教师、内容创作者，以及处理汇报、策划、研究和编程任务的个人或小组。当前交付形态是本地 Windows 桌面软件，用户自行配置模型服务和 API Key。

| 用户任务 | 软件协助整理的内容 | 交付给下游 AI 的内容 |
| --- | --- | --- |
| 奖学金答辩、课程展示、项目汇报 | 受众、时长、重点、素材边界、页面与讲稿要求 | PPT 规划提示词、逐页任务与完成标准 |
| 报告、技术文档与内容创作 | 文档目的、读者、事实来源、结构、引用要求 | 写作步骤、素材使用规则及文档检查要求 |
| 教学、学习与活动策划 | 学习对象、目标、已有基础、时间与条件 | 教学或活动方案的生成提示词 |
| 编程与界面修改 | 技术栈、修改范围、已有行为、交互和验收要求 | 实施方案、限制条件与测试要求 |
| 数据分析与研究准备 | 分析问题、数据条件、方法偏好、结果形式 | 分析任务说明、步骤和待核实前提 |

软件当前输出提示词和 Markdown 方案。PPT、PDF 报告、代码等实际成果由下游 AI 或相应工具生成。Skill 在本产品中是具有来源和用途的任务资源；软件提供发现、匹配、选择和提示词整合，安装及执行取决于下游环境与用户授权。

项目的差异化设计集中在三个方面：生成前的需求访谈与用户确认；跨阶段的来源、版本和回退管理；把 Skill 的具体用法嵌入任务方案。多模型接入为用户选择服务提供条件，实际耗时和内容质量仍受所选模型、网络和任务复杂度影响。

## 二、技术架构与创新

### 2.1 整体架构与数据交互

意织按界面、交互控制、业务状态、模型与检索适配、本地存储组织代码。WebView2 负责对话、设置和编辑界面的布局、滚动与动画，独立 WebView2 窗口展示 Debug 日志。Python 业务对象及 SessionState 由专属 Tk 线程管理；界面通过受限桥接入口提交动作并读取数据快照。业务操作在所属线程执行，网络请求与流式读取交由后台线程处理。

~~~mermaid
flowchart TB
    U[用户] --> W[WebView2 工作区 / 设置 / 编辑器]
    W -->|dispatch 动作| B[DesktopApi 桥接与动作队列]
    B --> C[WorkspaceController / GuidedFlowMixin]
    C <--> S[SessionState：来源 / 需求 / 方案 / Skill / 交付版本]
    C --> T[后台任务与 TaskScope]
    T --> A[模型协议适配器]
    A <--> L[用户配置的大语言模型服务]
    T --> K[本地索引 / Skill 索引站 / GitHub / 开放网页]
    K --> R[候选资格检查、摘要评分与来源记录]
    R --> S
    T -->|流式事件与完成队列| C
    S -->|可公开的数据快照| B
    B -->|snapshot| W
    S <--> D[本地会话与历史索引]
    C <--> P[设置与 DPAPI 密钥存储]
    C --> F[提示词渲染 / 复制 / Markdown 导出]
    T --> G[内存诊断与模型运行证据]
    G --> V[独立 Debug 窗口]
~~~

一次模型操作遵循以下顺序：Controller 根据当前会话构造带任务身份和版本的请求；后台线程完成 HTTP 与流式读取；完成队列把结果送回业务线程；程序核对请求是否仍有效，再解析、暂存模型建议或更新状态；界面读取新的快照。后台线程不直接改动界面控件。

SessionState 是业务状态的统一来源。它记录原始输入和回答来源、需求条目、确认版本、待处理问题、冲突、方案、Skill 绑定以及最终提示词。模型返回的结构化建议先进入本地解析过程；正式确认、取消和阶段转换由程序依据用户动作执行。[3]

例如，需求从版本 v 变为 v+1 时，旧版本产生的方案不能继续当作已确认方案使用。完成回调还会核对任务、请求及会话作用域，避免用户新建会话、停止任务或返回上一步后，旧请求覆盖当前内容。

### 2.2 技术选型及依据

| 技术或机制 | 当前用途 | 选型考虑与约束 |
| --- | --- | --- |
| Python 3.11 及以上 | 业务状态、模型调用、Skill 检索、存储和打包 | 复用 Python 网络、JSON 与桌面生态；CPU 密集型工作仍需关注界面线程占用 |
| pywebview / Windows WebView2 | 主工作区、设置、编辑器和独立 Debug 窗口 | 使用 HTML、CSS、JavaScript 表达组件和动画；依赖 Windows WebView2 Runtime |
| Tk 专属业务线程 | 持有应用对象与业务状态，处理动作队列 | 在所属线程串行处理状态更新，后台任务通过队列回写 |
| 外部大语言模型 | 需求分析、充分性判断、方案生成和 Skill 匹配 | 通过用户配置的服务调用，按任务组织输入与输出 |
| JSON Schema 与本地语义处理 | 约束模型输出形状，检查引用、身份及状态关联 | 对可恢复的格式问题进行兼容处理；影响确认和版本的错误需要提示用户处理 |
| ThreadPoolExecutor、队列、TaskScope | 后台模型与检索任务、取消和完成回调 | 网络等待不阻塞界面；迟到结果需要额外校验 |
| 本地 JSON、历史小索引 | 设置、会话和断点恢复 | 适合单机部署，以文件组织设置和会话数据 |
| Windows DPAPI | 加密保存每个服务的 API Key | 使用当前 Windows 用户的保护能力；跨电脑迁移须重新考虑凭据 |
| pytest、模拟 HTTP、WebView2 验收脚本 | 解析、状态、协议、DOM、宿主和安装验证 | 分层定位问题；模拟响应不能替代真实模型质量评估 |
| PyInstaller onedir、Inno Setup | 冻结 Python 依赖并制作安装包 | 用户无需另装 Python；缺少 WebView2 时需联网安装依赖 |

模型供应商设置包含 OpenAI、Anthropic、Google、xAI 和 DeepSeek 五类。实际协议客户端包括 OpenAI Chat Completions、OpenAI Responses 和 Anthropic Messages。Google、xAI 类别通过所配置的兼容接口接入；自定义服务必须指定所属模型类别，以确定参数映射。可选模型以当前服务返回的模型目录为准，本地目录补充匹配模型的说明。

请求参数按协议和模型类别映射。例如，Responses 使用 max_output_tokens，OpenAI Chat 使用适配后的 max_completion_tokens，其他适用接口使用 max_tokens；推理配置分别转换为相应 reasoning 或 thinking 字段。Responses 使用显式消息项及 input_text，并设置 store=false。兼容处理仍取决于服务端实现，第三方中转需要单独验证。[4]

### 2.3 AI 应用设计与相关产品比较

项目将“模型分析”和“用户确认”分开：模型提出需求、问题和方案，程序保留来源并管理确认结果。这使用户能在同一工作区检查模型如何理解任务，修改后也能识别哪些后续内容需要重新生成。其工程贡献可从状态模型、请求控制与交付规则中看出。

访谈过程采用逐轮充分性判断。模型已能据现有信息形成方案时，可以提前结束；默认最多自动询问五轮，超过后每轮由用户选择是否继续。对于实际文件、截图和数据等执行材料，提示词记录材料要求及待核实前提，供下游 AI 在执行阶段接收与处理。

Skill 推荐过程中按需读取资源。软件先利用名称、简介与索引形成候选，再把有限候选送给模型分析；联网检索依据简介和受限片段完成一轮评分。交付时写出 Skill 应用于哪项工作、需要什么输入、应产生什么结果。因此，推荐列表与任务步骤的对应关系可以核对。

| 相关产品或规范 | 官方资料确认的能力 | 与意织当前设计的关系 |
| --- | --- | --- |
| OpenAI Custom GPTs / GPT Actions | 指令、知识文档、第三方服务定制；Actions 经 REST API 与外部应用交互 [5] | 主要在 ChatGPT 内运行定制助手；意织将用户确认后的任务说明交给下游 AI |
| Dify | 模型管理、Prompt IDE、工作流、RAG、Agent、应用发布与自托管 [6] | 覆盖 AI 应用构建和运行；意织聚焦桌面上的任务澄清、方案确认与提示交付 |
| Agent Skills 开放格式 | 以 SKILL.md 组织指令及可选资源，支持按需发现与加载 [7][8] | 为意织发现并交付可定位的 Skill 引用提供格式基础 |
| 意织 Intext | 连续访谈、需求与方案确认、版本回退、可选 Skill 整合、本地恢复 | 将任务准备做成用户可修改的完整流程；效果需要同任务比较验证 |

上述比较依据官方功能说明，未开展竞品体验或性能对照。本项目的产品侧重点是需求确认后的提示交付，以及 Skill 与具体任务步骤的关联。

研究基础方面，成员郑又祥、李佳乐参与了《提示词语气对国产大语言模型输出结果的影响分析》。该研究使用固定题目与参数，比较三种模型在标准化选择题上的作答准确率、词元成本和显性输出结构。[9] 团队从中积累了控制变量和保留实验记录的经验。论文研究对象是标准化选择题与提示语气；意织的多轮访谈和 Skill 推荐需要各自的评测数据。

## 三、功能设计与实现

### 3.1 核心功能与 AI 实现

#### 3.1.1 从目标到需求：澄清、记录与确认

用户输入目标后，M1 接收任务、原始来源、当前需求和问答历史，分析已有信息，提出需求更新和必要问题。首轮与增量处理使用不同提示资源，共享输出契约。当前首轮装载 M1_contract_v0.1 与 M1_system_v0.25，增量装载 M1_incremental_v0.18；程序按 JSON Schema 和会话语义解析返回内容。[10]

每条回答都保留可追溯来源。需求中的来源引用用于区分用户实际说过的内容与模型推断。用户可以核对或编辑需求；程序记录用户确认的版本，再进入方案生成。M1 的一次整理对应一次模型请求，可恢复的格式差异和部分引用问题由本地解析层处理。

问题卡片使用内联回答框，Enter 提交已填写的回答，Shift+Enter 换行。跳过表示用户不回答该问题，后续交付排除相应的强制补答要求；“不确定”信息则作为未知保留。已经回答的问题会进入后续请求上下文，本地处理还识别部分重复问法，减少同一条件反复询问。任意语义改写的去重仍依赖模型判断，当前规则只能覆盖有限模式。

需求足够时，工作区在对话中展示需求核对内容。用户确认后生成方案，已完成的阶段面板收起。返回上一步会恢复对应阶段的起始状态：访谈中恢复本轮已填但未提交的回答，方案阶段返回需求核对；程序同时隐藏失效的后续展示，防止新旧内容混在一起。

#### 3.1.2 从需求到方案：步骤、依赖与完成标准

M2 从已确认需求构造初始方案，包含目标、范围、交付物、步骤、关键工作、完成标准与需求覆盖。步骤记录输入、动作和输出，依赖关系使用稳定标识关联。用户在对话中查看和确认方案，随后选择是否检索 Skill。

阶段间传递带有来源的紧凑状态。已经确认的回答内容可以通过 source ID 引用，避免在多处重复提供全文。一般未知进入方案及交付说明；需要改变任务方向的冲突或失效确认仍由用户处理。软件尽量把必要问题集中在方案确认前，后期缺少的执行材料在提示词中说明。

M1、M2、M3、M4 是面向不同任务的提示与解析模块，共用用户选择的模型服务。其中，M1 负责需求澄清，M2 负责方案生成，M3 提供候选适配分析能力，M4 负责所选 Skill 的使用整合。主流程在完成提示词交付后结束。[10]

#### 3.1.3 Skill 检索、推荐与整合

Agent Skill 通常是包含 SKILL.md 的指令资源包，可附带脚本、参考资料和资产。[7][8] 软件围绕方案中的关键工作查找这些资源，并保留本地路径或网络来源。

~~~mermaid
flowchart LR
    P[已确认方案与关键工作] --> Q[任务检索词]
    Q --> L[本地增量索引与粗筛]
    Q --> N[索引站 / GitHub / 开放网页]
    L --> C[有限候选与内容片段]
    N --> V[Skill 身份与来源检查]
    V --> C
    C --> A[AI 适配分析或简介评分]
    A --> T[合并表格：来源 / 用途 / 推荐系数]
    T --> U[用户选择]
    U --> M[M4：映射步骤、输入、输出与检查点]
    M --> F[带 Skill 来源及使用说明的提示词]
~~~

本地检索会扫描约定的用户、插件及项目 Skill 目录，建立增量元数据索引。索引记录路径、时间戳、大小、名称、描述、正文片段和摘要指纹。再次检索时，程序根据文件状态复用未变化条目，并针对文件的新建、修改和删除更新索引。启动预热减少首次任务的重复读取；目录枚举与文件状态检查仍有成本。

粗筛与内容读取分层执行。当前默认本地正文粗筛候选数为 24、名称与描述粗筛为 12、AI 复核为 8；正文核验使用受限节选，并标明覆盖范围。这些数值是可调整的搜索预算，模型接收筛选后的候选及有限内容片段。

联网检索先规划检索词，随后并行查询 Skill 索引、GitHub 和开放网页。普通主题网页须满足可识别的 Skill 来源条件才能进入候选。各来源有独立时间预算，单个来源失败仍可保留其他来源结果。共享 HTTP 会话复用读取，并对拒绝访问、鉴权、限流和人工验证分类处理，暂停受限入口。

程序依据名称、简介和受限公开摘要，对网络候选集中评分。默认简介上限为 1600 字符、公开摘要 2000 字符、任务 6000 字符、累计候选预算 60000 字符；正文核验另有默认 4000 字符的节选预算。实际取值随设置变化。推荐系数范围为 0～1，默认筛选线为 0.4，最多推荐 8 项，表格默认简略显示 6 项并可切换显示全部。该系数表示与任务的适配程度，尚未做概率校准。

程序区分“有效评分后相关性低”和“评分失败”。前者可显示无匹配，后者可提供数量受限且标记未完成 AI 核验的粗筛结果，并给出重新查找的提示。取消任务时不再写回降级结果。本地与网络候选累计合并，已选 Skill 在表格中标记，避免重复选择。[11]

M4 按用户选中的绑定生成 Skill 使用说明，并由本地记录补齐名称、来源和对应工作。若仅依据简介或节选，交付中保留这一限制；若下游无法访问本地路径，用户需要提供相应 Skill 文件。外部 Skill 内容只作为任务资源读取，软件不在搜索过程中导入或执行其脚本。

#### 3.1.4 提示词交付与格式恢复

最终提示词承接用户确认的需求、方案步骤、完成标准、选定 Skill 的使用位置以及需由下游核实的一般前提。用户可以复制、补充语气与附注，或导出 Markdown。保存会话后，提示词及关联状态可以恢复。

模型返回格式不完整时，程序在本地提取已有有效内容；无法形成结果时，向用户提示下一步操作。原始 JSON、技术字段和损坏响应保存在诊断证据中，交付正文呈现可供下游使用的任务内容。M4 格式恢复专项验收覆盖了截断 JSON、代码块包装、额外对象、取消与保存重开等情况。[12]

交付前检查需求与方案版本、关键引用和用户确认，使导出内容与当前确认依据一致。普通材料缺失和执行期细节作为待核实前提写入提示词，用户可以继续复制或导出。

### 3.3 扩展性设计

模型适配层将配置、请求字段和流式事件转换与业务状态分开。新增供应商或原生协议时，可以扩展客户端及参数映射，并用模拟 HTTP 核对请求；需求确认与方案状态不应因接口调整而重写。提示词与 Schema 按版本放在资源目录，升级时需同步加载器、测试路径和冻结打包清单。

Skill 检索的来源适配器与候选数据分开，便于增加新索引源、更新资格规则或更换评分策略。当前分数由模型给出，后续可以用人工标注任务集校准阈值，研究“名称与简介筛选”和“正文核验”的收益及调用成本。

界面通过快照和动作桥接使用业务能力，为拆分业务服务提供条件。当前桥接面向单机桌面工作区；扩展为 Web 或协作产品时，需要建立服务端鉴权、任务隔离、数据库迁移、配额与并发控制。

### 4.2 关键代码与优化策略

#### 4.2.1 等值来源引用，减少重复输入

访谈历史中的回答可能同时存在于来源列表与问题记录。程序只在两处全文相等时考虑省去重复字段，并比较节省的字节数与新增引用说明的成本。以下节选来自 model_input.py 的 prepare_json_input，省略日志及其他分支。[14]

~~~python
sources = {row.get("source_id"): row.get("text")
           for row in payload.get("sources", [])}
compact = deepcopy(payload)
for row in compact.get("state", {}).get("question_history", []):
    text = row.get("answer_text")
    if isinstance(text, str) and text and sources.get(row.get("answer_source_id")) == text:
        row.pop("answer_text")
        removed += 1
candidate = json_text(compact)
if len(original.encode("utf-8")) - len(candidate.encode("utf-8")) > len(("\n" + _ANSWER_REFERENCE).encode("utf-8")):
    wire = candidate
    system_prompt += "\n" + _ANSWER_REFERENCE
~~~

这一处理只改变发送视图，本地状态、校验和运行证据保留完整输入。M2、M4 还通过紧凑来源和元数据减少重复。UTF-8 字节数用于本地比较，实际 token 用量以供应商返回的 usage 为准。

#### 4.2.2 取消作用域与响应清理

TaskScope 用 Event 表示取消状态，用锁保护可中断清理回调。以下为 cancel 与 check 的节选，完整实现见 task_scope.py。[15]

~~~python
def cancel(self) -> None:
    self._cancelled.set()
    with self._lock:
        aborters = tuple(self._aborters)
        self._aborters.clear()
    for abort in aborters:
        try:
            abort()
        except Exception:
            logging.getLogger(__name__).warning(
                "Cancelled transport cleanup failed", exc_info=True)

def check(self) -> None:
    if self.cancelled:
        raise CancelledError("后台任务已停止或随会话切换、程序关闭取消。")
~~~

网络读取与搜索阶段在边界检查取消状态，完成回调另行核对作用域及请求版本。程序可中断已注册的响应读取，并隔离已经返回但失效的结果；DNS、建立连接和收到响应头前的等待仍可能持续至超时。服务商已经执行的推理可能继续计费，界面停止不应解释成供应商计费确认。

#### 4.2.3 本地 Skill 增量索引

local_skill_index.py 用修改时间、大小和创建时间组成文件状态戳；状态相同且缓存字段完整时复用元数据，否则重新解析。索引更新使用临时文件替换，并返回缓存命中、元数据读取、移除文件与耗时等诊断值。[16]

~~~python
def file_stamp(path: Path) -> list[int]:
    stat = path.stat()
    return [stat.st_mtime_ns, stat.st_size, stat.st_ctime_ns]
~~~

索引把不随任务变化的文件读取与任务相关的语义匹配分开。缓存节省的是重复解析成本；具体检索速度还取决于目录规模、磁盘与候选评分，需在固定环境下测量冷启动和热查询。

| 评价对象 | 指标与计算方法 | 采集方式 |
| --- | --- | --- |

~~~

根目录 run.bat 优先使用项目虚拟环境并显式选择 Web 渲染。缺少依赖时，应按启动反馈安装相应依赖后重试。

开发构建使用 scripts/build.ps1；安装构建使用 scripts/build-installer.ps1，并需要 PyInstaller 与 Inno Setup。PromptSmith.spec 收集提示词、Schema、Web 资源及运行依赖。发布时应将源码提交、构建产物和校验值对应，防止旧 EXE 与新源码混用。

应用通过本机客户端直接连接用户配置的远端模型服务。云端部署的扩展设计需覆盖账号鉴权、数据隔离、并发任务、密钥托管、审计和备份。

#### 4.4.3 设置、凭据与数据边界

默认数据目录为 %LOCALAPPDATA%\Intext。主要数据包括 settings.json、会话与历史索引、Skill 索引缓存、模型运行证据，以及用户手动保存的日志。设置和会话采用临时文件替换，减少写入中断导致的损坏。

API Key 使用 Windows 当前用户 DPAPI 加密，并结合服务、协议和接口身份附加约束；明文 Key 不写入 settings.json，已保存的密钥不通过普通界面快照回传。加密失败时程序反馈错误，不改为明文保存。[22]

任务内容会随请求发送到用户选择的模型服务；联网 Skill 检索也会访问外部来源。DPAPI 保护本地静态凭据，服务端的数据留存和传输安全还取决于所选接口。模型证据可能包含任务输入，用户分享诊断材料前需要检查其中的个人内容。Debug 保存日志时执行脱敏，但不能替代用户对业务材料的隐私判断。

## 五、应用价值与展望

### 5.1 应用场景与操作案例

以下以奖学金答辩 PPT 为例，说明从初始目标到交付提示词的操作过程。具体问题和结果以实际模型返回为准。

| 环节 | 用户操作 | 形成的任务信息 |
| --- | --- | --- |
| 输入目标 | “我想做一份奖学金答辩PPT。” | 确定任务类型，受众、时长和输出形式等信息仍待明确 |
| 澄清回答 | 按实际提问说明受众和时长，选出展示重点、风格以及所需内容 | 建立可核对的约束；真实成绩和证书材料留待提供给下游 |
| 需求核对 | 查看、修改模型整理的要求，确认当前版本 | 区分用户已确认内容与仍需核实的材料 |
| 方案确认 | 核对材料整理、叙事结构、逐页内容和讲稿等工作 | 将“做 PPT”展开为可以交付和检查的步骤 |
| 可选 Skill | 查找并选择与演示文稿、结构表达相关的实际 Skill | 保留来源、具体用法及访问条件；无匹配时可继续交付 |
| 复制与导出 | 将最终提示词交给下游 AI，补充真实个人材料 | 下游按相同任务要求生成 PPT 内容或文件，并核对完成标准 |

初始目标只有一句话。流程完成后，用户得到一份包含任务目的、已确认条件、步骤、输出结构、完成标准及可选 Skill 用法的说明。真实成绩和证书等材料由用户提供给下游 AI；尚未提供的材料在提示词中列为待补充、待核实内容。

技术文档场景还可把读者、引用、技术事实与 PDF 交付检查组织起来；编程场景则可把修改范围、保留行为、实施步骤和测试要求传给下游。当前可观察的产品价值是任务信息能够检查、修改、保存和交接。减少返工、提升结果质量或节省成本属于待验证效果，现有试用尚未形成可报告的比例。

### 5.2 市场分析与应用推广条件

生成式 AI 的总体用户情况及其在文本、办公中的用途，构成了意织的使用背景。[1][2] 意织面向其中具有复杂任务、愿意核对需求、使用电脑并能配置模型服务的用户。该细分群体的规模、使用频率和付费意愿仍需专项调查。

目前相关能力已经分布在通用聊天助手、提示词工具和 AI 应用平台中。[5][6] 用户也可以直接让聊天模型提问、再生成提示词。意织需要证明的价值在于：把这些动作整理成持续可用的桌面流程，保留每次确认与回退，并降低跨阶段信息混乱的成本。

推广初期可从课程展示、竞赛汇报、技术文档等任务明确的小组开始。以实际任务观察首次配置、访谈结束条件、需求修改和提示交接的障碍，再决定是否增加预设服务、案例模板或简化部署。API 配置门槛、生成等待和下游 Skill 可用性，是用户当前采用意织时需要考虑的条件，后续调查需要单独记录。

### 5.3 成果总结与研发经验

团队已建立目标澄清、需求确认、方案确认、可选 Skill 和提示交付的桌面工作流；实现了多协议模型调用与五类服务配置，并以统一会话状态维护来源和版本。主要界面、设置和 Debug 使用 WebView2，本地历史与检查点支持保存后继续处理及返回修改。安装包已经完成本机发布验收。

AI 在产品中承担自然语言理解、充分性判断、方案组织和候选适配分析。程序承担用户授权、状态一致性、请求隔离、数据存储和交付渲染。团队在长等待、重复追问、损坏 JSON 与界面冻结等问题中逐渐明确了这个分工：模型输出需要保留解释与恢复路径，后台任务必须有身份、取消和回写检查。

Skill 功能已将 Skill 发现与任务用途联系起来。增量索引减少文件重复解析，有限候选与集中评分控制输入规模，来源记录帮助下游定位资源。推荐相关性和资源实际可执行性仍需人工标注及真实任务验证。

已取得的成果包括可运行应用、源码与版本记录、提示与 Schema 资源、分层回归测试、专项验收文档和安装发布。真实用户已有试用，但团队没有保存系统化的任务成功率、满意度或效率对比数据。项目当前效益主要体现为功能和交付能力，量化结果留待后续采集。

### 5.4 当前不足与后续研发重点

| 当前问题 | 后续工作 | 可检查的完成条件 |
| --- | --- | --- |
| 完整回归仍有失败和隔离不复现项 | 对 72 项失败按有效缺陷、契约变化和环境问题逐项处理，调查 10 项稳定性问题 | 保留每项判断与复现记录，运行新的完整回归并公开准确结果 |
| 强推理可能长时间无正文 | 比较不同模型与参数下的完成率，继续减少重复上下文，完善无正文、停止与重试反馈 | 同任务记录延迟、usage 和最终正文，保持用户所选强度的可解释性 |
| 访谈充分性和重复问题识别仍依赖模型 | 建立含跳过、改写、冲突、材料延后的任务集，评估问题必要性 | 报告必要条件覆盖、重复率和平均轮数，并保留失败样例 |
| Skill 简介评分尚未校准 | 人工标注任务与 Skill 对，比较简介评分和正文核验 | 报告前 k 项相关性、无效来源和成本，明确“未阅读全文”标记 |
| 第三方中转实现不一致 | 扩充协议录制夹具，并经授权做有限真实服务验收 | 按服务类别报告请求形状、服务端响应、适用版本及验证范围 |
| 桌面性能与兼容性证据有限 | 在干净 Windows、不同 DPI、输入法及高刷新率设备测量 | 记录启动时间、帧间隔、滚动长任务和长期内存等运行测量结果 |
| 用户效果缺少系统数据 | 采用固定任务、盲评和自愿用户观察 | 分别报告任务质量、时间、token、失败情况与用户反馈 |
| 单机架构限制协作和云端运行 | 评估业务服务拆分、账户、存储迁移和任务队列 | 完成鉴权、数据隔离与并发设计后，再验证协作部署 |

下一阶段优先处理回归失败和真实任务评测，建立当前安装版、固定输入、模型输出与人工评分之间的证据链，再依据结果调整访谈及 Skill 策略。下一版本发布前，还需在组员电脑或干净环境复核安装依赖、历史恢复和主要交付流程。

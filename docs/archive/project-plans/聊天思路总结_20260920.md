**已经比较明确的产品倾向：**

- 用户先表达想做的事情，软件再帮助其补齐必要信息。
- 提问应与用户的具体任务有关，早期固定问题设想逐渐转向定制化提问。
- 将用户补充的信息整理为结构化内容，最终生成可使用的提示。
- 提供相关 Skill 的选择与使用入口，减少查找和组织负担。
- 礼貌语气保留为局部设置，整个软件不以“礼貌一定提高效果”为成立条件。
- 需要可运行的软件、清晰的 AI 功能与效果验证。

**聊天没有决定的内容：** 首批用户、首个场景、Skill 的格式、具体模型、谁提供 API、离线范围、是否直接执行生成后的提示，以及新实验的评价标准。软件开发是讨论举例，并未确定为唯一场景。

**新版作出的实施建议，与聊天原意分开看：**

| 待决定事项 | 为控制工期给出的建议 |
|---|---|
| 先服务谁 | 先试做学生或小团队的 AI 辅助软件开发需求准备；这是建议，可由团队替换 |
| 怎样问问题 | 通用字段 + 场景字段 + 针对缺失信息的少量动态追问 |
| 怎样确认整理结果 | 增加可查看、编辑和确认的需求卡，让用户纠正 AI 的理解；这是本版新增的交互建议 |
| Skill 是什么 | 首版定义为可选任务方法包，包含所需信息、处理步骤、输出要求和检查点；不宣称可安装执行外部插件 |
| 怎样接模型 | 团队服务端接入一个已验证可用的模型，用户无需本地部署；个人 API 配置留作扩展 |
| 离线怎么办 | 作为可选的表单、已保存模板与复制导出降级方式，不承担模型推理 |
| 生成后怎么验证 | 用户可试运行；正式效果对照由团队先用脚本完成，避免重建完整评测平台 |

# 软件分阶段实现建议

更新：2026年9月23日。你负责软件全部功能实现；UI成员提供展示组件、样式与体验反馈。原A/B人员划分不再作为开发前提。

建议分成五个初版阶段和一个后续迭代阶段。每一阶段都保留能启动、能操作的版本，通过验收后再进入下一阶段。阶段是开发顺序，不是六个独立项目，也不需要同时开六个窗口修改代码。

配套：[新对话提示词与阶段任务模板](<分阶段开发-新对话提示词-20260923.md>)。

## 当前基础与目标

已有完整方案、MVP说明和提示设计资料。本次在当前项目中检索未发现Python产品源码、依赖清单或打包配置；如果代码在别处，新开发窗口应先检查你指定的代码位置，按实际完成度跳过已有工作，不能据此认定整个团队还没开始。

提示设计已有：[入口说明](<../prompt-design/README.md>)、[M1 v0.2](<../../../resources/prompts/M1_system_v0.2.txt>)、[输入Schema](<../../../resources/prompts/M1_input.schema.json>)、[输出Schema](<../../../resources/prompts/M1_output.schema.json>)和人工案例。当前记录是设计检查，真实模型效果和接入尚未验证。先使用并核对这些成果，不另起一套M1。

产品目标保持为：六类任务与通用入口共用需求引导；用户确认需求后生成完整初始方案；方案确认后才按关键工作查找Skill；用户选用或跳过后获得最终方案、提示和可复用文档。论文代码不作为依赖，论文只提供语气控制与评价方法基础。

路线沿用Python、Tkinter/ttk、JSON会话与PyInstaller目录模式。若实际已有可运行代码采用其他已确认框架，先核对再决定，不能为了符合本文重写已有成果。

## 总体顺序

| 阶段 | 完成后你能实际做什么 | 提示工程模块 |
|---|---|---|
| 1. 可运行骨架与接口 | 打开窗口，输入并保存任务，测试API连接，重开会话 | 不要求新业务提示 |
| 2. AI需求引导 | 真实提取已有信息、追问、修改与确认需求卡 | 接入已有M1 |
| 3. 独立方案与导出 | 无需Skill也能形成完整方案、最终提示并导出 | M2＋M4的无Skill路径 |
| 4. 后置Skill增强 | 方案确认后检索、选用或跳过，形成整合结果 | 程序检索；按需M3；M4增强路径 |
| 5. Windows初版交付 | 在目标Windows电脑上启动并完成整条流程 | 固定已验收提示版本 |
| 6. 按反馈迭代 | 增加局部样例、在线搜索、试运行和效果证据 | M5及按需要修改既有模块 |

阶段1—5是周四晚初版目标。今天已是周三，不再把9月21、22日的安排当作已完成成果。时间是否足够取决于现有代码、API配置和你的可投入时间，不能仅凭排期承诺完成。

## 阶段1：先有一个能打开、能保存的程序

先检查源码、现有UI、Python环境及提示目录，确定唯一代码目录和启动命令。无源码时再建立小型项目，不引入复杂服务、数据库或插件系统。

这一阶段做：

1. 四步基础窗口：任务输入、需求卡、初始方案、Skill增强与导出。未实现步骤显示尚未就绪，不用预填结果冒充成功。
2. 统一会话数据与状态：任务编号、类别、需求版本、需求来源及状态、方案版本与确认记录、所选Skill、最终结果及错误。界面只展示状态并发送操作，业务逻辑不写进控件。
3. JSON保存和重开。密钥默认仅在会话内使用，不进入业务保存文件；保存失败明确提示。记录数据格式版本，后续加字段时有默认值或兼容处理。
4. 单模型API模块及“测试连接”入口，配置供应商接口地址、模型名和密钥。先核实供应商协议，不假设所有模型都兼容同一请求格式。
5. API请求放后台，主线程更新界面，记录实际耗时和用量，缺失用量保留空值。至少能处理超时、鉴权失败和格式错误，界面不冻结。
6. 尽早做一次最小PyInstaller打包，验证Python、Tk与资源路径可用于Windows交付。

内部联调可以用明确标注的测试数据，正式验收需一条真实API成功记录。没有模型配置时继续做界面和存储，但将API检查标为待验证，不能用演示数据代替。

验收：窗口启动；任务保存后重开内容一致；API成功与失败都有明确反馈；密钥不被导出；最小发行目录能启动。

给下一阶段留下：启动命令、会话结构、API返回格式、错误处理方式、UI回调约定。不要一次写很多空模块，按以上可运行路径创建必要文件。

## 阶段2：接入真实需求理解与追问

前提是阶段1的会话与API可用。以已有M1 v0.2和建议Schema为起点，先核对字段如何映射到应用。若必须调整契约，记录差异并创建新版本，不能静默删除来源、版本或冲突字段来图省事。

这一阶段做：

1. 从会话生成输入快照，包括原始任务、材料来源、已有需求、回答与问题历史、类别配置、轮次预算。
2. 一次模型调用返回候选类别、增量需求、冲突、缺口和少量问题。只发送模型所需的提示正文、契约及实例数据，不把设计README或人工期望答案一起发给模型。
3. 本地校验结构、ID引用与范围，再展示候选差异。用户编辑或接受后，由程序更新需求版本；模型声称“已确认”不能改变真实状态。
4. 支持回答、跳过、不确定、撤销或修改。完整输入直接进入需求复核，预算用尽但信息仍不足时保留草稿和未决项。
5. 六类与通用入口使用同一调用路径，每类只补有意义的字段。不为每一类写独立聊天程序。
6. 拒收旧请求结果：用户在等待期间修改需求后，迟到响应不得覆盖新版本。只有真正展示给用户的问题才计入交互预算，网络重试不算一轮追问。

先用已有01正常与02冲突/预算耗尽案例各做一次真实调用，保存原始响应并校验；再在界面完成一条实际多轮任务。人工expected只用于检查，不能当成模型输出或输入中的答案。

验收：已知内容不重复问；限制未丢失；系统建议未被自动确认；用户改需求能生效；预算耗尽不冒充需求完整；旧响应不能覆盖新状态。结构检查通过还需人工看内容是否正确。

这一阶段结束，你应能得到一张可信、可编辑的需求卡，暂时不用Skill或生成完整成品。

## 阶段3：先跑通独立方案、最终提示和导出

前提是用户确认了具体版本的需求。这里实现第一个完整使用结果：输入想法后，最终拿到可以交给另一个AI窗口使用的文档。

这一阶段做：

1. 实现M2：用已确认需求和明确保留的未知项生成完整初始方案，至少包含目标、约束、工作步骤、交付物、完成标准和待确认事项。可同次生成带步骤编号的关键工作，减少额外调用。
2. 初始方案生成时不接收Skill候选。未知预算、技术选型、资料结论等不能被补成已确认事实；候选建议与用户要求分别显示。
3. 支持编辑并确认方案。编辑后复核关键工作和步骤编号，避免后续推荐引用已经删除的工作。
4. 实现M4的无Skill路径。用户确认初始方案后，形成完整任务提示与可导出方案；可用确定性模板组织，只有确需语义整理时再调用模型。
5. 加入中性／适度礼貌选择，先使用受控措辞包装。改变语气不触发重新改写需求，不改变语义正文。
6. 导出Markdown和会话JSON。独立文档包含任务背景、确认要求、方案、未决项和提示，避免“按前面说的”“第二版”等指代。导出后仍能保存重开继续编辑。

验收：一条任务从真实追问走到完整导出；不使用任何Skill也可完成；硬约束保留；未知项仍可见；修改需求后旧方案及最终提示被标记失效；两个语气版本只有措辞差异。

阶段3是最重要的中间成果。如果此时只能得到大段聊天记录而没有可复用的独立方案，就先修正这一阶段，不急着增加功能。

## 阶段4：接入方案末端的Skill检索与整合

前提是当前初始方案已由用户确认。检索的对象是方案中的关键工作，不能提前让Skill决定用户要做什么。

这一阶段做：

1. 建立小型目录，先使用前期已读取来源的真实条目，约3—5个即可。保存ID、来源、版本/核验日期、工作标签、输入输出、环境依赖、许可和核验状态。
2. 用关键工作和环境筛选，返回目录中的真实ID；初版关键词与标签匹配即可。需要模型解释时才接M3，并校验它不能返回候选范围以外的ID。
3. 界面展示“用于哪一步、为什么适合、需要什么条件、是否实测”，支持无匹配、全部跳过、选择及取消。不要让热度替代能力与环境匹配。
4. 扩展M4：将已选项放入对应步骤，保留初始方案；返回最终方案、提示、改动清单和额外待确认项。可抽象的方法说明与必须依赖外部宿主执行的步骤区分开。
5. 处理变化：取消Skill后重建对应结果，改初始方案后推荐失效；Skill新增要求不能自动改写用户标准。
6. 导出Skill来源与适用条件，遇到没有匹配的类别仍可完成无Skill路径。

验收：有匹配、无匹配、全部跳过、选中后取消、修改前置方案这五种情况都正确。不能只做推荐列表却不改变最终方案，也不能把目录检索宣传成全网搜索。

目录中真实条目有限是可接受的初版边界。不要为了填满六类而编造Skill能力，或安装执行来源文件中的指令。

## 阶段5：把已有功能打包成可交付的Windows版本

先冻结功能范围，再做发行验证。阶段1的最小打包只是提前排雷，不能代替本阶段的完整验证。

这一阶段做：

1. 固定依赖与构建配置，打包Tk资源、当前提示正文、Schema和类别/Skill目录等程序实际需要的资源。不要把整套研究资料、测试凭据和工作目录无差别塞进发行包。
2. 采用PyInstaller目录模式，提供exe及依赖文件夹。用户会话写入可写目录，不写进临时解包位置；路径不能只在开发机成立。
3. 六类各跑一条基本任务，通用、改选类别、修改需求、无Skill、API失败、保存重开等做功能回归。只需针对关键风险的测试，不把界面装饰逐项写成单元测试。
4. 在另一台未装Python、与目标系统及架构匹配的Windows电脑检查启动、中文路径、联网、保存导出；检查常见缩放和长文本显示。
5. 交付发行目录、源码、依赖与构建命令、模型配置说明、操作说明、检查记录及已知问题。检查输出和截图无密钥。

验收：另一台电脑可走完同一完整流程；打包成功和运行成功都有证据。没有第二环境时标为待验证，不能用“本机exe启动了”替代。exe不包含云端模型，AI调用仍需网络和账户。

## 阶段6：周五后按反馈逐项增加能力

按以下顺序选择最有价值的下一项，每次只做一个可检查改进：

| 优先顺序 | 具体内容 | 证据 |
|---|---|---|
| 先修阻断问题 | 不知道下一步、修改不生效、结果丢失、等待无反馈 | 原问题能复现，修复后同样操作通过 |
| 局部样例与隐含标准 | 接入M5，比较单一维度，反馈只形成待确认标准；允许两者都不要 | 用户能说明差异，标准不被擅自扩大到其他任务 |
| 文本试运行与成本 | 使用最终提示调用目标模型，分开记录准备和执行开销 | 真实输出与接口用量，失败也记录 |
| 在线Skill搜索 | 在限定来源检索真实页面，读取核验后入库或推荐 | 来源和读取状态可追溯，不能以模型记忆充当搜索 |
| 新任务验证 | 固定版本，按原计划做12个分类案例及3—5人试用 | 质量、使用负担与总成本，保留相近和退化结果 |

语气对照保持需求、方案、Skill和参数一致。对多个类别分别记录结果，不能把论文客观题结论直接套成通用产品效果。完整PPT生成、多模型路由和自动执行外部Skill不在当前必做范围。

## 9月23—24日怎样安排

建议以结果决定下一步：9月23日优先完成阶段1—3；9月24日上午完成阶段4；9月24日下午保留给阶段5的打包、另一台电脑验证及修复。已有步骤直接核对后跳过，不重做。

如果从零开始、模型配置仍未解决或当天可用时间很少，周四交付全部能力可能无法做到。此时先交付真实可运行的阶段3版本，明确Skill增强或打包验证尚未完成，再继续推进；不能把缺失项称为完整MVP。先减样例、装饰、历史浏览和在线搜索，不删确认、保存或真实调用来掩盖问题。

实现过程中始终保留六类公共配置结构，可先用一条任务跑通，再逐类检查。通用产品定位不需要等六类都精修完才开始联调。

## UI成员怎样配合你

你维护模型调用、业务状态、保存、检索与打包，也先提供可运行的标准控件界面。UI成员接入展示组件和样式，约定只读取你提供的数据、通过回调发送操作，避免自行维护另一套确认状态。

先对齐两个组件：需求卡和Skill推荐卡。页面布局可以独立优化，接口改变则同步双方。Tkinter界面不能直接粘贴HTML/CSS组件；收到其他形式设计稿时先按约定框架实现，不在临近交付时无声更换技术栈。

## 每个阶段给下一窗口留下什么

建议在代码目录维护一份开发交接记录，例如 `docs/开发交接.md`；如果已有等价文件就沿用，避免多套状态互相矛盾。新窗口先读再动手。

交接只写事实：当前入口和启动命令、已完成模块、提示与Schema版本、状态和回调接口、实际运行的检查及结果、已知缺口、下一阶段入口。明确区分人工样例、真实模型响应、本机启动和另一台电脑验收。不把密钥写进交接。

提示设计窗口与编码窗口可以分开：前者维护模型提示和契约，后者接接口、状态和UI。不要让两边同时改同一份Schema或源码。按阶段开发的窗口尽量连续使用，换窗口时带交接记录，不重新从一句项目介绍推导系统。

本文是实施顺序建议，未执行产品开发、模型实测或exe构建。正式产品功能和截止日期仍按实际证据更新。

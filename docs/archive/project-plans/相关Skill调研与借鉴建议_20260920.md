**1. grill-me 实际如何工作。**

来源是 Matt Pocock 的 [mattpocock/skills](https://github.com/mattpocock/skills)。本次固定版本为 `c55ee46073ed923f86ce59a5eb3b6d895095d1b7`。

当前 [grill-me/SKILL.md](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/grill-me/SKILL.md) 只是用户入口，正文调用 `grilling`。真正的访谈逻辑在 [grilling/SKILL.md](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/grilling/SKILL.md)。因此，不能只看入口文件就判断它没有具体方法；也不能把旧版本或二手介绍中的行为当成当前原文。

| 源码规定 | 对你们的启发 |
|---|---|
| 将计划表示为设计决策树，后续决策依赖前面的决定 | 根据已确认条件决定下一步问什么，避免固定长问卷 |
| 每轮提出全部前置条件已明确的可问问题，每个问题给推荐回答 | 把可以并行回答的问题放在一起；存在依赖的问题留到下一轮 |
| 回答后重新计算可问的问题；本轮依赖其他未回答问题的事项不得提前问 | 用户改变关键条件时，后续问题与提示需要随之调整 |
| 可从环境查到的事实由系统查找，决定由用户作出 | 先利用用户已授权提供的材料，再问真正需要用户判断的问题 |
| 当前可问前沿为空、决策分支已遍历，且用户确认形成共同理解后结束 | 停止条件应与需求状态有关，不能只按轮数判断完成 |

这里的“决策树”是访谈组织方式，不代表训练了机器学习中的决策树模型。原文件是供模型遵循的指令，也不能仅凭它就认定每次执行都能完整维护依赖或消除所有假设。

例子：用户想做报名网站。在“课程演示还是实际部署”尚未明确时，先不要连续问云服务购买和运维安排；确认实际部署后，再询问访问量、运行环境和相关条件。是否允许重复报名属于用户的产品决定，不能靠搜索替用户决定。

**3. 对当前方案建议做五处具体调整。**

第一，给已有需求字段加轻量依赖关系。首版只需字段表，不必实现通用图引擎。建议保留字段名、来源、状态、前置条件、重要性。先问会改变任务方向的问题，再问依赖它的细节。例如“是否实际部署”决定是否需要部署环境问题。

第二，把“两轮追问”改成默认交互预算。每轮优先显示1—3个前置条件已明确、影响较大的问题。这是针对用户负担的产品改造，原 grilling 要求的是询问整个可问前沿。关键字段足够且无明显冲突时即可让用户确认；达到预算仍有缺口时，只能生成带待确认项的草稿，并允许用户继续、跳过或返回修改，不能宣布全部澄清完成。

第三，推荐回答与用户确认分开。可以提供少量选项与理由，保留自由输入和“不确定”。推荐内容未获选择或确认前，属于系统建议，不能自动写成事实。参考文件中的推荐机制可能诱导选择，产品应验证其是否减少负担，还是让用户被动接受。

第四，需求卡随回答持续更新。区分已确认事实、用户决定、待确认项和系统建议；保留字段级来源。用户修改前置决定后，标记受影响内容需要复核。借鉴 domain-modeling 对模糊词的澄清，例如“用户”到底指报名者还是管理员，不把所有矛盾都交给最终生成阶段处理。

第五，生成提示时附带可检查的要求。借鉴 to-spec 和 goal-prompt，说明要交付什么、必须遵守什么、怎样判断完成、哪些内容尚未确定。没有依据的预算、性能阈值、技术选型和测试命令不应被模型补成事实。先支持三个已有方法包即可，不增加 Skill 商店或任意插件执行。

可以概括为：任务输入→提取已知信息→按依赖追问→更新并确认需求卡→组合方法包→形成语气可控的提示→试运行与核验。

**具体问法按目标用户重新设计。**

借鉴时分开看内部模型指令、规定的问答格式和实际用户问句。内部规则可以精确描述依赖、状态与终止条件；面向用户的对话则应自然、具体、容易回答。读取 Skill 的内部指令不能替代对实际问答的体验检查。

- 保留“先问关键决定、根据回答调整后续问题”的机制，使用用户熟悉的任务词汇。
- 接着用户已经说的内容问，避免重复询问或每轮从头总结。
- 选项、推荐和理由按需要提供，不强制每题套用同一长格式；不把推荐默认为用户决定。
- 允许“不确定”、跳过和修改；需要确认的是具体需求内容，无需每轮重复同一句确认话术。

例如，已知用户想给社团做活动报名页，可以问“这个报名页是给大家实际用，还是先做个演示？”；确定实际使用后，再问“报名后，成员需要自己修改或取消吗？”这是本项目自拟示例，不是原 Skill 的引文。是否自然、是否容易回答，应在既定的小规模试用中收集具体反馈。

原版 grilling 保留为实验基线，与产品自行编写问法并不冲突。若改写基线的指令，应另标“适配版”，保留版本与变更记录；不预设原版体验更差，也不把文案改写本身宣称为新算法。

**4. 与论文中的礼貌提示思想怎样结合。**

必须区分三个对象：

| 对象 | 本项目如何处理 | 证据来源 |
|---|---|---|
| 问什么、按什么次序问 | 对任务缺口、约束和冲突作针对性追问 | grilling、brainstorming 等提供可借鉴流程，效果仍需产品测试 |
| 怎样与用户说话 | 清楚、尊重，可质疑假设，允许用户不确定或跳过 | 属于用户体验设计，论文没有研究礼貌访谈对用户的效果 |
| 最终怎样向目标模型表达任务 | 在固定事实、要求和方法包下生成中性／适度礼貌变体 | 继承原论文的语气变量与对照方法；新任务中的影响需验证 |

`grill` 所表达的深入追问，不等于使用粗鲁措辞。一个问题可以检验用户的假设，同时用尊重的方式表达。不能把访谈方式的收益、需求补全的收益，都算成最终提示礼貌语气的收益。

自然表达与礼貌程度也应分开：前者涉及简洁、上下文衔接和避免模板化，后者是论文研究的语气变量。自然的问句可以采用中性语气，客气的表达也可能难以理解。访谈语言的改进通过用户体验检查；最终模型提示的语气影响按固定任务内容的对照方法验证。

原论文第6页明确，礼貌相对中性的准确率差异尚无统计显著优势；第7页讨论了任务边界。因此，本次 Skill 检索为需求引导提供方法参考，论文为语气控制和质量／词元联合观察提供基础，二者承担不同作用。没有新增证据前，不宣称两者结合必然提升质量。

**5. 已有 Skill 对创新性和评价的影响。**

“通过连续追问澄清需求”“把讨论整理成文档”“提示中包含验收要求”都已有公开实现。此前若把这些功能单独写成新颖机制，需要收紧表述。组合成软件有工程价值，但工程价值与优于现有方式是不同的结论。

可主张并等待验证的改进是：面向一个具体场景的可用界面、轻量依赖追问、用户可纠正且可追溯的需求卡、可选择的方法包、与任务内容分离的语气控制，以及全过程质量与资源消耗记录。是否比直接使用这些 Skill 更有效，必须比较。

在原有A原始提示、B普通润色、C等信息普通表达、D完整流程之外，建议增加E“同模型直接使用固定版本 grilling 指令”。统一任务材料、模型、可访问资料、用户事实回答规则和资源上限，记录上游版本及原始日志。Skill不是单独的模型，比较对象是“模型+固定指令+宿主能力”，不能让E访问整个仓库、却只给D一句话，也不能反过来。

原 grilling 是访谈流程，未承诺自动产生完整的最终任务提示。用于比较最终产出时，应在两边同样提供的公开阶段，用固定中性指令整理已确认信息；将此阶段明确标为评测附加步骤，不冒充原 Skill 功能，并计入开销。若受统一预算限制而提前终止，保留待确认项并报告，不把它当成上游自然完成。

E与D先比较需求遗漏、重复提问、用户操作负担、硬约束保持和总成本。两边获取信息不同的结果只能解释为整体流程差异；要判断提示组织是否更好，再使用相同的已确认信息进行生成比较。语气影响继续单独固定其他条件比较。

不要为新增基线再扩展产品页面。10—12个任务原有四组需要约40—48次下游调用；加入E约50—60次，另计澄清、改写和生成的调用。初期也可以在预先选定的小子集试比较，明确其探索性质。统计首次完成全过程成本，并将后续复用成本另列，不能只报告最后一次回答的词元。

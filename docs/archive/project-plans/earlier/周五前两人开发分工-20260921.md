# 周五前初版：两名开发成员分工

目标：9月24日（周四）晚交付可运行的 Python 初版，9月25日（周五）试用并开始迭代。

暂用 A、B 代表两名主要开发成员，C 代表 UI 设计成员，可自行替换为姓名。建议更熟悉论文实验代码和模型调用的成员担任 A，更熟悉 Python 程序组织、界面连接和打包的成员担任 B。本表是任务安排，所列模块尚未完成。

## 一、职责怎么分

| 成员 | 主责 | 周四交付物 |
|---|---|---|
| A：模型与内容流程 | 模型接口、需求提取与追问、六类字段、初始方案、关键工作提取、选定 Skill 后的最终整合、语气控制 | 一套可被界面调用的 Python 功能模块、六类配置、固定输入输出样例及对应检查结果 |
| B：程序与产品整合 | 可操作的基础界面、流程状态、需求卡编辑、Skill 目录检索与选择、保存导出、后台调用、Windows 打包 | 可运行桌面程序、可保存重开的会话、Markdown导出、exe发行目录与运行说明 |
| C：UI设计参与 | 参与页面顺序、按钮文案、信息布局与试用反馈；可提供简单草图或样式建议 | 可选的页面草图和问题建议，不承担周四前任何必经开发模块 |

B 用 Tkinter/ttk 标准控件先做能操作的界面，无需等待 C 的设计稿。A 和 B 承担功能检查与交付，C 有时间时参与体验检查。周五后再由 C 主导界面优化，A、B 配合改造。

## 二、这次必须跑通的链路

输入任务 → 分类与追问 → 编辑并确认需求卡 → 生成并确认完整初始方案 → 识别关键工作 → 检索与选择 Skill → 整合最终方案与提示 → 保存导出。

六类保留：写作、PPT、学习、策划、数据分析、编程，另有通用入口。它们共用同一套程序，差异先放在字段和检查要求里。不选择 Skill 也能导出完整方案；没有适合项时明确显示无匹配。

周四前先做已核验目录内的检索，不做全网搜索、自动安装和执行外部 Skill。短样例对比、复杂视觉布局、下游任务试运行与完整效果实验留到周五后。真实模型追问和方案生成必须接通，不能只用预填文本演示。

## 三、A 的任务清单

1. **接通一个模型。** 核对已有论文调用代码能否复用，统一请求与返回格式，设置超时，处理接口失败。密钥从运行配置传入，不写入源码、日志或导出。
2. **做需求提取与追问。** 从输入中区分已知事实、系统建议和未知信息，每次提出少量关键问题。整理后的候选需求交给界面确认，模型不能自行把建议设为已确认。
3. **准备六类基础配置。** 每类先补3—5个有区分度的字段或检查点，公共字段保持一致。避免把字段列表变成逐题必答问卷。
4. **生成独立初始方案。** 输入确认后的需求，输出目标、约束、步骤、交付物、完成标准、未决项及关键工作。此阶段不接收候选 Skill，也不依赖检索结果。
5. **整合用户选定的 Skill。** 输入初始方案和 B 返回的已选真实记录，将其写入对应工作步骤，并返回改动说明。保留未决项，范围或成本变化标为待确认；不选时保留初始方案。
6. **输出最终提示并控制语气。** 中性与适度礼貌仅改变请求措辞，事实、限制和所选 Skill 保持不变。初版优先采用受控文本替换，避免整段自由润色。

A 负责检查：已有信息不反复问、未知信息不编造、已确认限制不丢失、没有 Skill 也能生成方案、语气切换不改变任务。先用脚本直接运行这些接口，再交给 B 接界面。

## 四、B 的任务清单

1. **搭建能用的四步界面。** 任务输入、需求确认、初始方案、Skill增强与导出。需求卡支持修改与确认，不以美化程度阻塞联调。
2. **维护流程状态。** 方案确认前不允许推荐 Skill。需求修改后，相关方案、推荐与整合结果标记失效；取消 Skill 后不能残留旧内容。
3. **整理小型真实 Skill 目录并实现检索。** 优先核对现有资料中的条目，先准备约3—5个确实可用的记录，不以数量为目标。按关键工作的标签、输入输出和环境筛选，展示来源与适用理由；无合适项返回空结果。前期资料偏需求与规划，不假装覆盖所有专业执行工具。
4. **连接 A 的模块。** 模型请求放到后台线程，通过队列将结果交给主线程更新界面。失败显示原因并保留输入；请求期间避免重复提交。结果回来时核对请求对应的需求版本，不能覆盖用户后来修改的内容。
5. **保存与导出。** JSON保存会话并支持重新打开；Markdown导出需求、初始方案、所选Skill来源、最终方案、提示和未决项。版本失效状态一并保存，密钥不进入文件。
6. **提前打包。** 9月22日先打包最小窗口程序，9月24日再打包完整程序。用PyInstaller目录模式，交付整个发行文件夹，并在另一台未装Python的Windows电脑验证。

B 负责检查：检索只返回目录里的真实条目、用户可跳过、选择取消生效、编辑后旧结果失效、失败不丢输入、保存重开一致、中文路径和打包资源可用。

## 五、两人怎样对接，避免互相等待

第一轮先花约30分钟确定接口和样例，B 可以用明确标注的测试数据接界面，A 同时独立开发真实调用；测试数据只用于联调，不能当作真实AI效果展示。

| 交接点 | A 提供 | B 负责 |
|---|---|---|
| 输入与追问 | 任务文本、当前需求输入后，返回候选字段、关键问题与来源 | 展示、编辑、记录用户确认与版本 |
| 初始方案 | 确认需求输入后，返回完整方案、带编号的步骤与关键工作 | 展示和编辑，用户确认后才开放Skill检索 |
| Skill整合 | 根据方案和已选真实记录，返回最终方案、提示、改动说明及待确认变化 | 目录检索、选择界面、校验选中编号与来源、处理新增确认 |
| 保存导出 | 提供结构化内容及真实调用状态/用量 | 保存当前会话、导出文件和界面展示 |

交接数据统一使用 Python 字典和列表，不互相传界面控件。至少统一这些字段名及含义：`session_id`、`revision`、`category`、`requirements`、`questions`、`initial_plan`、`plan_confirmed`、`key_tasks`、`selected_skills`、`final_plan`、`prompt`、`pending_changes`、`error`。需求字段带 `status` 和 `source`；Skill带真实目录编号、来源及对应的工作编号。JSON能保存这些数据即可，初版不引入数据库迁移。

初始方案和需求确认状态由 B 的程序根据用户操作维护；A 的模型输出只能提供内容建议。最终整合如果提出额外要求，由用户确认后再导出为已确认内容，否则继续保留待确认状态。

建议代码归属：A维护模型接口、内容流程、语气规则与类别配置；B维护启动入口、界面、状态管理、Skill目录/检索、存储导出与打包。六类配置与目录分开存放，避免两人频繁修改同一个文件。共享数据格式由两人先定，变更时同步样例和调用方。

每日最少两次联调：首次工作开始时确认当天交接，中途接一次真实模块，晚间共同跑一条完整任务。接口完成后立即接入，不等所有功能都写完再合并。B负责集成版，A负责修复模型和内容侧问题。

## 七、工作量超出预期时怎么取舍

9月23日晚以“能否走完主流程”为检查点。若进度不足，先取消动态样例、在线搜索、动画、复杂历史版本和下游任务执行。目录用关键词与标签匹配即可，模型排序可后加；UI用标准控件；六类共用代码，只保留必要差异字段。

保留真实AI调用、可编辑确认的需求、独立初始方案、末端真实目录检索、可跳过的整合、保存导出及Windows交付。不要退回只有分类按钮和模板的演示，也不要把打包任务拖到周四晚上。未通过的验收在问题清单中说明，不写成已完成。

## 八、周四共同验收清单

- [ ] 六类各有一条真实输入记录，字段或提问确实随任务变化。
- [ ] 已知内容能被提取，候选建议需确认，未决问题能保留。
- [ ] 未检索Skill时即可生成并确认完整初始方案。
- [ ] 方案确认后再检索，推荐有真实来源，无匹配可跳过。
- [ ] 所选Skill对应具体工作；取消后重新整合，无旧内容残留。
- [ ] 修改需求或方案后旧结果失效；迟到的模型响应不会覆盖新版本。
- [ ] 中性／适度礼貌切换不改变事实、限制和所选Skill。
- [ ] API失败不丢输入，密钥不进入源码、日志、会话或导出。
- [ ] 会话保存重开一致，导出文档在新对话里能独立读懂。
- [ ] 另一台无Python的Windows电脑验证完整发行目录，问题有记录。

这些是初版功能检查，不等同于论文实验或产品效果验证。正式分类对照、隐含标准样例研究和用户体验测试在初版交付后按总方案进行。

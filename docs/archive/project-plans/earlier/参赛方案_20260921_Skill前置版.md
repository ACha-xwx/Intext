# 需求引导式提示构建助手

赛题二“AI+软件创新”参赛方案最终整合稿｜2026年9月21日修订：通用流程与任务分类

项目拟面向写作、汇报、学习、策划、数据分析和编程等常见 AI 协作任务，帮助用户通过对话、局部示例和反馈，逐步说清任务要求与评价标准，将确认后的内容整理为可编辑、可复用的需求文档，再结合任务方法包生成提示，支持文本试运行与结果检查。

“提示工程”是本项目的技术方向。作品名称突出软件用途，沿用“需求引导式提示构建助手”。以下功能和测试为开发安排；已有论文结果与拟开展的新实验分别说明。

## 一、要解决的问题

用户向 AI 提出任务时，通常能够说明“想做什么”，却未必能说清“什么结果才算合适”。一句“帮我做一个方案”，可能隐含着对内容深度、呈现方式、可执行程度和使用场景的要求。这些标准没有进入输入，如果模型直接按自己的假设生成结果，就容易与用户预期错位。

其中一部分信息可以直接问出来，例如使用对象、截止时间和必须包含的内容。另一部分需要借助具体结果才能表达：用户可能说不清汇报要怎样组织，但看过两种单页示例后，会发现自己更在意先看到结论，还是先理解推导过程；准备开发任务时，则可能更关注任务能否直接分工、是否有验收依据。

因此，系统需要同时支持直接澄清和借助示例确认标准。用户的判断既可能来自原本没有表达出来的经验，也可能是在比较和讨论中才逐渐形成。AI 的作用是提供具体参照、整理反馈、帮助确认；所有推测都要接受用户修正。

本项目希望把部分反复修改前移到需求准备阶段，用较小的交互与样例开销减少后续完整生成的返工。这个收益需要测试：前期多问、多展示也可能增加负担，不能预先宣称节省时间或费用。

## 二、首版服务谁、交付什么

产品定位为面向学生、内容创作者及小团队的通用需求引导与提示构建工具。赛题二要求参赛作品本身是 AI 软件，并未要求服务场景必须是软件开发。[2] 软件开发保留为一个任务类别与演示案例。

首版建议采用“六类常见任务＋通用入口”。所有类别共用需求提取、追问、样例反馈、用户确认、提示生成和保存导出的流程，类别配置决定补问什么、用什么示例、怎样检查结果。分类按本次希望得到的交付物划分，用户无需先理解提示工程术语。

| 类别 | 典型任务 | 需要补充的要求 | 首版可比较的小样与文本试运行 |
|---|---|---|---|
| 写作与内容表达 | 文章、文案、邮件、报告 | 读者、目的、篇幅、文风、事实依据、必须保留的信息 | 两种开头或段落；试运行短文或局部改写 |
| PPT与汇报 | 课堂展示、论文汇报、项目答辩 | 听众、时长、页数、核心信息、叙事顺序、图文偏好 | 两种大纲或单页内容；试运行逐页提纲与视觉说明 |
| 学习与知识理解 | 概念讲解、知识梳理、学习计划 | 当前基础、学习目标、难点、可用时间、例子或练习偏好 | 同一知识点的两种讲解；试运行讲解或学习计划 |
| 方案策划与研究准备 | 活动策划、项目方案、调研提纲 | 决策目的、参与对象、资源、范围、时间、依据要求 | 两种方案结构或一个任务阶段；试运行方案提纲与检查项 |
| 数据分析与可视化 | 分析计划、图表需求、数据报告 | 数据字段与口径、希望回答的问题、比较维度、图表用途 | 两种分析步骤或图表说明；试运行分析计划与图表规格 |
| 编程与软件开发 | 功能需求、开发计划、代码修改说明 | 使用者、已有代码或环境、功能边界、输入输出、验收条件 | 两种任务拆解或需求片段；试运行开发方案与验收清单 |

通用入口允许用户直接描述未被覆盖的任务，沿用目标、背景、限制、交付物和完成标准等公共字段；它不代表所有专业任务都已验证。首版优先打磨写作、PPT和编程这三个体验路径，其余三类也要完成字段、样例、生成及基本验证，不能只有分类按钮。

对比三种实现方式：只做一个场景便于深入验证，但覆盖面偏窄；完全不区分任务容易给出泛泛问题；采用共用流程和少量类别配置，能够在控制重复开发的同时适配常见任务。因此本版选择第三种。分类增加的实际工作是设计问题依赖、准备样例、检查内容与补充测试，不能仅凭使用同一个模型就认为扩展没有成本。

软件交付三类可查看、可修改的结果：

- 需求与标准文档：记录任务背景、已确认要求、表达偏好和待确认事项。
- 可直接使用的任务提示：组织上述信息，并加入用户选定的方法包要求。
- 文本试运行记录：保存输入、输出、模型配置、用量、耗时与失败信息。

首版各类任务均可生成需求文档和可导出的提示，内置试运行以文本产物为范围：PPT类输出提纲、单页内容和视觉要求，数据类输出分析计划与图表规格。完整PPT文件、图片、真实数据计算或可部署程序等产物，可以使用导出的提示在相应工具中继续完成；本软件不将准备这些提示等同于已经生成或核验这些产物。

用户转述的 PPT 协作案例用于设计样例反馈。文字结构可以直接比较两份大纲或单页内容；颜色、布局等视觉偏好则需实际可见的示意。首版可用少量固定的单页布局卡承载同一段内容，不增加完整PPT制作引擎。若暂未实现布局卡，应明确只支持内容结构比较与视觉要求记录，不能把文字描述的比较宣传成视觉效果验证。

## 三、用户怎样完成一次任务

流程为：表达任务 → 推荐可修改的任务类别并提取已有信息 → 针对缺口追问 → 必要时看局部示例并反馈 → 确认需求与标准 → 选择方法包 → 生成提示 → 文本试运行、修订与导出。

以下以编程类别说明一条完整路径；其他类别复用相同机制并替换场景字段与样例。示例为设计说明，不是实际测试记录。

用户输入：“帮我做一个活动报名网站。”

系统先问影响任务方向的问题，例如“这个网站准备实际使用，还是先做课堂演示？”在用户确认课堂演示后，再补充必需功能、完成时间等条件。假设用户最终确认：只管理一个活动，两周内完成，熟悉 Python，需要报名、名额限制和管理员导出名单，不做付款。

这时，系统已经知道软件要做什么。如果用户仍不确定希望 AI 怎样组织开发方案，可以展示两段很短的表达，保持事实相同，只改变组织形式：

> 示例 A：支持活动报名和名额限制，管理员可以导出名单；本次不做付款。

| 示例 B 的栏目 | 相同的需求内容 |
|---|---|
| 功能 | 活动报名、名额限制、管理员导出名单 |
| 范围边界 | 不做付款 |

用户反馈：“B 比较清楚，但我还想知道每一项怎样才算做完。”

系统据此提出待确认标准：“开发任务用表格列出，并为每项任务写出能检查的完成条件。”用户确认后，这一条才进入需求卡。若用户只说“B 好一点”，系统应进一步询问是表格结构、文字密度还是其他因素起作用，不能把 B 的所有特征都当成用户偏好。

形成的需求卡可以包含：

| 内容 | 类型与状态 | 依据 |
|---|---|---|
| 单活动报名网站，用于课堂演示 | 任务事实，已确认 | 用户回答 |
| 报名、名额限制、管理员导出名单 | 必需功能，已确认 | 用户回答 |
| 不做付款 | 范围限制，已确认 | 用户回答 |
| 两周完成，熟悉 Python | 已有条件，已确认 | 用户回答 |
| 开发任务采用表格，并附可检查的完成条件 | 输出标准，已确认 | 样例反馈后确认 |
| 管理员登录方式 | 待确认 | 当前对话尚未确定 |

用户选择“开发任务拆解”和“验收检查”方法包后，系统生成提示片段：

> 请根据以下已确认需求，给出适合两周完成的最小软件方案。项目用于课堂演示，管理单个活动，必须支持报名、名额限制和管理员导出名单，不包含付款。开发者熟悉 Python。请用表格列出开发任务、任务依赖和可检查的完成条件。管理员登录方式等未确定事项请单独列出；新增功能建议标为可选，未经确认不要纳入必需范围。

用户可以在软件中试运行，也可以导出文档与提示，在新的对话中使用。导出的内容应包含执行所需的已确认信息、适用范围和未决问题，不能依赖“按刚才说的做”或“采用第二版”这类只有原聊天才能理解的指代。转交后仍可能需要补充信息，产品不承诺一次交代就永远无需修改。

## 四、需求引导的具体机制

### 1. 根据已有信息决定下一步

通用需求字段覆盖目标、受众、已有材料、硬性限制、期望输出和完成标准。类别补充专有字段：PPT增加汇报时长与页数，学习增加知识基础，数据分析增加字段口径，编程增加运行环境。类别字段是候选检查范围，模型仍需结合实际任务判断，不逐项强制询问。

用户可以先选类别，也可以直接输入一句话，由系统推荐并允许改选。不明确时保持通用流程，仅在分类会影响下一步时澄清。遇到“整理论文并做汇报PPT”这类任务，按主要交付物选择PPT类别，并保留论文阅读要求，不要求用户把整项任务硬拆进单一标签。改选类别时保留公共信息，复核不再适用的专有要求和方法包，避免旧限制被误带入新输出。

每次回答后，系统先更新字段，再判断是否需要提问。优先处理会改变任务方向的缺口和已有信息之间的冲突。用户已说明的内容不重复询问，用户改变前置决定后，相关字段标为需要复核。

首版用简单字段依赖表实现，不开发通用决策树引擎。默认两轮，每轮最多三个关键问题；这是交互预算。用户可以继续、跳过或保留待确认项。达到轮数上限时，系统不得将仍有关键缺口的需求标成已经完成。

### 2. 说不清时，提供足够小的参照

当用户明确表示“不知道怎么描述”，或提出“高级一点”“更实用”等难以直接判断的标准时，系统可提供一组局部示例。信息已足够的任务直接进入确认，不强制展示样例。

首版默认最多一组、两个片段，每段约100—200字；任务简单时更短。片段可按类别选为文章开头、单页内容、知识讲解、方案步骤、图表说明或开发任务清单，只比较一个明确维度，尽量保持任务事实相同。布局卡也使用相同内容，标明正在比较的布局差异。示例中未确认的内容、阈值与技术选择须标为假设，不能进入正式需求。

用户可以选择其一、分别保留部分内容、两者都不要，或者描述自己的版本。系统询问具体理由，再把反馈写成待确认标准。偏好记录需要保留上下文，例如“本次课程项目的任务清单采用表格”，避免从一次选择推导出“用户所有任务都喜欢表格”。

首版以文本片段和简单表格为主，每类准备一组样例骨架，由模型结合当前任务填充；PPT可增加少量固定布局卡。相同事实下可交换左右顺序，避免把展示位置当作偏好。只做必要比较，不要求用户每次都经历完整的样例循环。对事实性内容，优先使用用户提供的材料；无法核验的内容标明状态，不能将示例当作已核实的知识或数据结果。

### 3. 把反馈转成用户能核对的要求

候选标准要指向具体产物和可观察特征。例如“更实用”可以进一步确认成“每项开发任务附完成条件”；“清楚一点”则需要继续分辨是结构、术语还是细节层次的问题。

每条记录至少保存内容、类型、状态、来源和适用范围。类型区分事实、硬约束、偏好与系统建议；状态区分已确认、待确认与需复核。未经确认的推荐选项和模型推测，不能自动升级为用户要求。

新旧要求发生冲突时，系统指出具体冲突，请用户决定。用户应能编辑、拒绝或撤销一条标准，而不必重新回答整套问题。实现上保留上一次记录即可，不增加复杂的历史版本管理。

### 4. 让进展可见，让结束有依据

指纹录入可以帮助解释“多次补充、累积保留”的过程。界面可显示“任务目标已确认”“交付格式待确认”“存在一项冲突”等具体状态，每轮说明刚补充了什么。初版不设计没有依据的完整度百分比。

需求可能在讨论中变化，因此完成条件定为：足以形成当前任务提示的关键信息已确认，已发现的重要冲突已处理，剩余未知项明确列出，并经用户确认。缺少基本目标时只能保存草稿。

### 5. 把协作结果保存为可复用资料

需求文档同时记录任务信息和已确认标准。用户可以保存、重新打开、复制及导出 Markdown 文档。复用旧记录时，先显示适用范围，并请用户确认要沿用哪些要求；不把旧项目的截止时间、对象和技术限制自动带入新任务。

首版以人工选择和确认完成复用，不建设长期偏好推断系统。文档使已确认信息能够跨对话携带，但并不意味着其他模型会自动记住或遵守全部要求。

## 五、Skill 如何进入产品

对 grill-me/grilling 借鉴问题依赖、已有事实利用、回答后的状态更新与结束确认。内部模型指令和用户问句由团队按场景编写，具体问法应承接上下文、简短、容易回答，不强制每轮输出固定的分析与客套话。

其他参考包括 domain-modeling 的术语澄清与决策记录、brainstorming 的目标与约束确认、to-spec 的讨论整理，以及 goal-prompt 对完成条件和验证证据的组织方法。它们提供设计参考，实际效果需要本项目验证。

类别与 Skill 分别承担不同作用：类别描述“这次要做什么”，方法包描述“希望采用怎样的工作方式”。首版将 Skill 定义为可选任务方法包，底层只维护三个公共方法，再按类别填充具体要求：

| 方法包 | 在提示中增加的工作要求 |
|---|---|
| 结构化组织 | 按适合该产物的结构整理信息；如写作提纲、PPT逐页结构、软件需求规格 |
| 步骤规划 | 根据任务给出顺序、依赖和范围；如学习安排、策划实施步骤、开发任务拆解 |
| 标准核对 | 按已确认要求检查结果；如事实与篇幅、汇报时长、分析口径、功能验收 |

每个方法包包含适用任务、必要输入、处理步骤、输出结构、检查点、来源和版本。在编程类别中，步骤规划可显示为“开发任务拆解”，标准核对可显示为“验收检查”，与前面的示例对应；其他类别使用各自能理解的名称。首版只提供已写好适用规则的组合，推荐最多两个，用户可以改选或不选。选择或取消后，提示应出现对应的实际变化，不把三个公共包机械套到所有任务。

用户已确认的限制优先于方法包默认建议。方法包新增的功能与具体阈值须单独确认；检查要求可以提醒发现遗漏，但不能假造用户已经认可的标准。共用要求合并去重，冲突需要处理。

本版不接入 Skill 商店、不安装执行任意外部 Skill。已有方法在参赛材料中如实注明，连续追问或结构化整理不能单独宣称为团队独创。

## 六、与既有论文的实质联系

研究基础为《提示词语气对国产大语言模型输出结果的影响分析》。论文使用635道中文纯文本选择题，设置五档语气，对三种模型分别重复三次，形成28,575条正式记录。[1]

论文第6页报告：礼貌相对中性的准确率变化分别为 DeepSeek +0.157、Doubao +0.000、Qwen +0.420 个百分点，尚不能认为存在统计显著优势；词元消耗和显性回答结构的变化依赖模型。论文第7页也明确了向开放任务、多轮对话和代码生成等场景推广的边界。

本项目继承以下内容：

| 论文基础 | 产品中的用途 | 验证边界 |
|---|---|---|
| 固定任务内容，只调整语气的对照方法 | 需求、方法包、格式与语气分别保存，生成可核对的语气变体 | 新任务的语气效果需另测 |
| 礼貌程度分档及原表达的感知检验 | 提供中性与适度礼貌选项，初版用受控措辞替换 | 原五条表达的分档检验不能直接覆盖全部新表达 |
| 同时观察正确率、词元和回答结构 | 在新场景同时记录任务符合程度、全过程用量和输出结构 | 不以回答变长代替质量提高，不把词元直接当成费用或能耗 |
| 历史实验记录与保留的代码 | 核对后复用调用、日志、异常处理和用量汇总模块 | 代码尚未提供审查，不能预设可以原样接入 |

语气设置作用于最终发给目标模型的提示。可默认使用适度礼貌且简洁的表达，同时允许中性表达；这是产品选择，不能称为已证明最优。切换语气时保持事实、硬约束、输出格式和方法包一致，显示差异，防止润色过程中改变任务。

访谈问句的自然程度与上述礼貌变量分别处理。用户是否容易理解和回答，由试用检查；模型在不同语气下如何响应，由固定其他条件的对照实验检查。需求澄清、样例反馈和标准保存是新增软件能力，论文没有直接验证这些机制。增加任务类别也不会自动扩大论文结论的适用范围，语气结果应按实际测试的任务和模型报告。

项目的研究延伸可以表述为：前期工作研究了固定任务下语气变化对模型输出的影响；本项目进一步面向任务尚不明确的输入，开发需求澄清与提示构建软件，并沿用控制变量、结果质量与资源消耗共同观察的方法进行评价。

## 七、软件怎样实现

首版采用一个已验证可用的大模型 API，由团队服务端调用。模型承担类别建议、需求提取、针对性提问、样例适配、反馈整理和提示生成；普通软件逻辑维护状态、字段依赖、确认记录、保存与导出。

六类任务使用同一套引导程序。每类以配置文件保存补充字段、提问依赖、一组对比样例、可选方法包和检查要点；分类变化时加载对应配置。增加类别主要扩展这些配置与测试，不复制页面、接口或会话管理。不为首版训练分类模型，使用可修改的模型建议即可。

建议界面集中为三个页面：

| 页面 | 用户完成的操作 |
|---|---|
| 说明任务 | 直接描述或选择类别、输入背景、回答关键问题，必要时比较局部示例 |
| 确认要求 | 编辑需求卡、确认候选标准和待确认项、选择方法包 |
| 生成与试用 | 查看提示、切换语气、调用模型试运行、修订并导出 |

如团队已有 Python 基础，可用 Streamlit、现有模型调用代码和 SQLite/文件存储完成原型；已有成熟 Web 技术栈则沿用。具体模型优先从团队已有可用账户中选择，检查中文理解、结构化返回、延迟与实际调用价格。论文比较过三种模型，不代表首版需要接入三个。

核心数据包括任务输入、任务类别与配置版本、需求字段及其状态、样例与反馈、已确认标准、方法包版本、生成提示、模型配置和调用记录。每次更新保存来源，生成时以当前确认版本为准，待确认信息带状态进入文档。首版材料输入以粘贴文本、字段说明和少量表格片段为主；文件解析与大规模检索不作为六类入口成立的前提，未知材料内容不能自行补造。

模型输出使用结构化格式校验；格式失败时允许一次修复重试，并记录开销。接口异常保存已填写内容，允许重试或导出已有结果。密钥留在服务端。对用户文本和参考资料按数据处理，其中的指令不能绕过确认、状态维护和输出约束。

首版的最小验收范围如下：

| 核心能力 | 可检查的完成标准 |
|---|---|
| 六类配置与通用入口 | 每类实际改变补问字段、样例或检查项；支持改选类别，公共信息保留，冲突项需复核 |
| 真实 AI 需求引导 | 能提取已知信息，追问关键缺口，对信息完整输入跳过多余提问 |
| 局部示例与反馈整理 | 支持一组短样例、拒绝两者与自由反馈；能提出待确认标准 |
| 可编辑需求卡 | 用户可以确认、修改、拒绝或撤销标准；新值用于后续生成 |

## 八、如何证明这个流程有用

核心问题是：这个流程能否帮助用户表达并保留任务要求，减少后续遗漏和修改，同时让总交互成本处于可接受范围。评价中分别观察整体流程、标准表达、语气影响和转交复用，不将所有变化归因于提示措辞。

### 案例对照

准备12个正式案例，每类2个，整体覆盖简略需求、信息完整、存在冲突、表达标准模糊和用户中途修改等情况。每个案例事先记录任务事实、关键约束、可回答的补充信息与类别对应的评分清单；调试案例和正式评价案例分开。另做通用输入、跨类任务及中途改选类别的功能检查，作为功能检查记录，不混入12个正式案例分数。

人为预设的隐藏标准只用于检查系统能否询问和保留信息，不能据此证明系统能够普遍识别人真实的隐含偏好。回答按预先记录的事实提供，未被问到的信息不能由后台自动补入。

| 条件 | 处理方式 | 比较目的 |
|---|---|---|
| A：原始输入 | 直接使用初始简略需求 | 观察未经辅助的起点 |
| B：普通改写 | 同模型进行一次常规改写，不补造事实 | 比较常见润色方式 |
| C：等信息普通表达 | 用固定普通文本格式呈现 D 最终确认的全部事实、标准和未知项 | 控制信息差异，比较提示组织与方法包组合 |
| D：本产品流程 | 追问，按需看样例，确认需求与标准，再生成提示 | 观察完整流程表现 |
| E：已有方法 | 同模型使用固定版本 grilling 指令 | 与公开需求访谈方法比较 |

同一案例的各条件使用相同初始材料、事实回答规则、模型、可访问资料和资源上限，并使用相同的最终任务要求。最终产物随类别调整：写作输出短文，PPT输出逐页内容提纲，学习输出讲解或计划，策划输出方案，数据分析输出分析计划与图表规格，编程输出需求规格及开发任务。每个案例统一各组的下游模型参数、语气和输出上限，不能要求所有类别都输出软件开发清单。grilling 本身聚焦访谈，最后将已确认信息整理为任务输入的步骤须注明为评测附加步骤，并计入成本，不能写成原 Skill 的功能。

C 包含 D 已确认的全部信息。若 D 的提示遗漏了某个已确认要求，应计为生成错误，不能从 C 删除该要求来配平。D 与 E 获得的信息不同，结果差异首先反映整体流程，不能直接解释为某种句式更有效。达到共同预算仍有缺口时保留并报告，不视为自然完成。

按预先确定的评分规则，报告关键需求覆盖、已确认硬约束违背、无依据新增要求、完成标准可检查程度和流程失败情况。每类另检查对应事项，例如写作是否符合受众和事实要求，PPT提纲是否适合给定时长，数据分析计划是否使用正确字段口径。由两名成员尽可能隐藏条件名称后独立评阅，再核对分歧。自动规则用于格式和明确字段检查，不替代全部语义判断。数据类仅得到计划时不能报告实际计算准确率；PPT只有文本提纲时不能报告成品视觉质量。

12个案例、5种条件、各一次下游运行约需60次下游调用，另计访谈、样例生成、整理、修复重试及功能检查调用。先用两个调试案例估算预算。按类别报告结果并给出完整案例明细，不用某一类别的良好表现替代其他类别的证据；每类只有2例，仅用于初步比较，不能宣称跨领域普遍有效。

### 标准表达与用户试用

邀请3—5名非开发成员带真实任务试用，优先覆盖写作、PPT和编程，记录用户在哪些地方无法直接回答、哪些反馈来自看过样例之后，以及系统整理的标准是否被接受、改写或拒绝。没有真实用户试用的类别须如实标明，功能案例通过不能替代用户体验验证。

在少量模糊任务上探索“只有追问”与“追问加局部示例”的区别。两种流程分别记录，不让用户先看样例后再把已经想清楚的标准当作未受影响的直接问答结果；可使用难度相近的不同任务并交错顺序。小样本主要发现问题，不预设样例一定有效。

记录主动操作时间、等待时间、重复问题、后续修改次数和具体误解。样例带来的新标准应由用户解释并确认；采纳数量本身不能证明质量。若示例诱导用户接受无关限制，或让简单任务更费时，应记录并调整触发条件。

### 语气与复用验证

语气验证选用预先确定的新任务，固定需求、标准、方法包、模型及参数，只生成中性与适度礼貌两个版本，人工检查信息一致性后运行。记录任务符合程度与词元消耗，不预设胜出档位。注明测试覆盖的类别，不直接混合不同任务的原始得分来声称统一增益。工期或额度不足时，明确保留论文历史证据，并说明新场景的语气效果尚未验证。

复用验证在不带原聊天历史的新上下文中，仅提供导出的需求文档及公开的执行要求，检查关键约束、输出标准和未决事项是否能够恢复。它验证文档能否独立传递信息，不等同于验证模型长期记忆。复用同一任务时可沿用记录，迁移到新任务时重新确认适用范围。

全部成本同时报告准备阶段、下游执行和全过程合计；首次整理与后续复用分别统计。词元按接口口径记录，避免重复计算缓存或推理用量。只有计费口径明确时才估算费用。测试报告保留相近、退化和失败结果，演示案例不能替代完整测试。

## 九、为什么符合赛题二

赛题二要求将 AI 算法转化为有实际用途的软件，完成核心功能，并提供算法说明、测试、部署及演示材料。[2] 本项目的模型参与需求理解、动态提问、反馈归纳和提示生成，软件提供状态维护、用户确认、试运行与复用能力，能够形成可操作的完整流程。

需要向评审展示的差异包括：同一引导流程怎样根据任务类别改变追问和检查内容；用户说不清标准时如何借助短示例表达；AI 推测如何经确认变成要求；需求变化后怎样更新；文档怎样在新对话中使用；为获得这些结果付出了多少时间与模型调用。类别数量本身不构成创新证据，必须展示实际适配与使用效果。

这些能力中有已有方法，也有团队需要完成的整合、交互和工程实现。参赛材料应按真实贡献描述，并以比较和试用支撑差异化，不使用“首创”“读懂用户全部想法”或“礼貌必然提高质量”等表述。

| 评分项 | 分值 | 应准备的证据 |
|---|---:|---|
| 创新性 | 20 | 与普通改写、公开访谈方法的具体差异及结果 |
| 技术实现 | 20 | 真实调用、状态维护、样例反馈归纳、异常处理与日志 |
| 功能完整性 | 20 | 输入到确认、生成、试用、保存和导出的完整演示 |
| 方案完整性 | 20 | 需求、架构、方法、分工、测试、部署说明 |
| 应用价值 | 15 | 真实任务试用、可观察的帮助与存在的问题 |
| 总结与展望 | 5 | 实际成果、限制及有依据的后续安排 |

以上权重对应规则第5页，不构成得分预测。

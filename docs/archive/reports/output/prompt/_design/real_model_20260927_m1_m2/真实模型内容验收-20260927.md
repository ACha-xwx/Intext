# M1/M2 真实模型内容验收 v1 — 2026-09-27

## 结论与阶段建议

本轮真实调用已完成：7 次请求均成功返回，通过当前程序的结构、引用及业务校验；两个真实生成的会话均通过生产加载函数重开。**内容质量未全部通过。** 发现三类需要收紧的内容边界：无依据扩大要求、待确认建议混入确定标准、草稿与可发布状态混用。

可以继续下一阶段开发，与 M1/M2 提示修订并行推进；这不是宣告 M1/M2 内容质量已经验收通过。将本轮三类问题作为内容质量待办，修订后保留同输入对照复测证据，再升级内容验收状态。两个实测方案保持 draft，关键工作保持待复核，不应直接作为已确认方案进入后续推荐或导出流程。

此前 2026-09-27 功能验收中的 189 项测试及两条人工响应流程是独立的历史功能证据。本轮新增的是当前提示的真实内容证据，并非证明旧程序修复失效，也不能仅据本轮判断问题是否由最近一次修改引入。

## 三类内容问题及修订判据

### F1：来源只支持部分内容，模型增加排除性限制

**证据：** `coding-m1-1` 的 proposals.p2 将“供自己日常使用”写成“工具供用户本人在日常使用场景下运行，不是对外分发或演示。”引用不支持后半句。操作者拒绝这一候选，接受其余有依据的候选；不能把后续流程通过描述成完全无需人工纠正。

同类表现：`coding-m2-1` 的 goal.audience 写“唯一日常使用者”；`writing-m2-1` 的 completion_criteria.c2 从“发布渠道为新生微信群”增加“不依赖群外渠道”。后者无明确来源，还可能与已确认的线上报名表产生歧义。另有编程 s1 将“离线运行”收窄为“仅使用 Python 标准库能力”，这是合理实现建议，但不是用户已确定的技术限制。

**影响：** 有引用并不代表整句话都被引用支持；模型可能悄悄缩小用户的使用范围或技术选择。

**修订判据：** 每条用户事实／要求中的实质性断言均须有依据；不从“我使用”推导“只有我使用”，不从“发微信群”推导“禁止群外工具”。实现建议允许存在，但明确作为方案提议，不冒充用户硬约束。正常规划步骤不必逐项要求用户额外审批。

### F2：待确认建议在其他字段中提前成为确定标准

**证据：** `coding-m2-1` 的 suggestions.sg3 将输出路径同名冲突的“提示并终止、不覆盖”标记 requires_user_confirmation=true，reason 又明确承认用户只规定保护源 CSV、未规定其他输出冲突行为。同时 s1/s3 已要求按该策略实现，整体 c4 与关键工作 k2 检查点也把它当作确定标准。

**影响：** 同一事项在建议区待确认，却在步骤与验收区被当成已经确定，下游整合难以正确识别其状态。

**修订判据：** 保留源文件保护硬约束；其他输出冲突策略写成待选／有条件分支，或清楚标注建议默认及适用前提，不挂靠旧需求编号当作已确认标准。若标为需确认，步骤、交付物、完成标准及关键工作不能提前把它无条件固化。问题在于状态一致性，不是要求软件采用覆盖文件的危险行为。

### F3：带占位信息的草稿被描述为可直接发布

**证据：** `writing-m2-1` 的 s4 称“形成可直接发到新生微信群的最终文本”，d3 称“可发布到新生微信群的定稿”，同时要求保留待补充标记。ug3/ug4 则要求在发布前补齐报名链接、联系人信息；sug1 又将替换占位列为 optional_improvement。不同位置对发布前提的描述不一致。

**影响：** 用户可能误认为含未解决报名／联系入口的通知已经达到发布条件。

**修订判据：** 当前可以交付结构完整的写作方案及带占位草稿。明确区分“方案可继续”“草稿可交付”和“满足发布条件”；如存在发布前必须完成的事项，使用条件表述，不能同时宣称可直接发布。不得为消除矛盾而编造缺失信息，也不能据此认定带未知的完整初始方案必然失败。

### 次要观察（不另计为确定失败）

写作受众从“大一新生”变成“以大一新生为主”，但测试答案本身同时写了“也欢迎已有摄影经验的同学”，存在范围歧义。不能据此断言模型明确扩展到高年级；后续样本应明确“有经验的大一新生”，再单独测试年级范围是否保留。其他措辞如把流式实现一律视为必须用户确认，也值得精简，避免将普通实现选择过度推回给用户。

# M1/M2 真实模型问题专项报告 v1

报告日期：2026-09-28（Asia/Shanghai）；真实调用日期：2026-09-27  
测试对象：M1_system_v0.5／m1.v0.2；M2_system_v0.1／m2.v0.1  
服务与模型：官方 DeepSeek，OpenAI Chat Completions 协议，deepseek-flash  
本报告状态：问题已复核，尚未修订产品提示或代码，尚未进行修复后复测。

## 一、结论

两个任务共 7 次真实调用成功返回，全部通过当前程序校验。内容审阅确认了 **3 类问题**：

1. 用户原话被扩大为无依据的限制。
2. 同一建议在部分位置待确认，在其他位置却成为确定标准。
3. 带待补充信息的草稿与满足发布条件的成稿混用。

这些问题足以说明当前版本的内容质量尚未全部达标。它们不等于 API 不通、状态丢失或程序自动确认；本轮也没有证据证明它们是上次修复新引入的回归。

本报告只归档问题、影响和未来验收判据，不启动这些问题的修复。用户最新决定为：F1–F3 暂缓修复，下一阶段开发继续推进，不把这三项作为前置阻塞。既有功能验收记录仍然保留，不能将其误读为内容也已经全部通过。

## 二、测试条件与判定边界

| 项目 | 实际情况 |
|---|---|
| 编程任务 | 个人使用的 Windows 离线 Python CLI，把指定文件夹当前层 CSV 按行合并；保护源文件；严格表头；数据规模未知 |
| 非编程任务 | 摄影社招新通知，发新生微信群，500 字以内，自然语气；日期、报名链接和联系人细节未确定 |
| 调用构成 | 编程 2 次 M1＋1 次 M2；写作 3 次 M1＋1 次 M2，共 7 次 |

| 测试用户 | 预设合成任务与答案库，由测试操作者按实际问题作答；不是一次真实用户调研 |
| 人工干预 | 编程首轮 p2 被拒绝；其余接受、回答和测试需求确认均有日志 |
| 模型参数 | temperature=0；JSON object；45 秒超时；未另设输出词元上限；无自动重试 |
| 保存结果 | 两个会话可通过生产加载函数重开；需求版本分别为 5、8；两份方案均仍为 draft，各有 3 项关键工作待复核 |
| 用量 | 输入 37,030、输出 36,974，共 74,004 tokens；来自真实响应，未估算金额 |

“通过程序校验”表示 JSON、Schema、引用及现有业务规则通过，不表示模型的每个语义断言都有充分依据。check.json 中 semantic=passed 也是程序校验结果，不能当成人工内容评审结论。

未被询问、没有发送给模型的答案库条目，不能算作已知需求。例如答案库虽准备了输出同名策略，但本次实际只发送了表头和递归范围回答；不能用未发送的答案替模型输出补依据。

样本只有两个任务和一个模型，不能据此估计六类任务总体错误率、跨模型稳定性，或判定某次提示修改导致回归。

## 三、F1：用户原话被扩大为额外限制

**状态：确认存在。涉及 M1 和 M2。影响：需求忠实性。**

### 1. 最明确的原始证据

编程用户原话：

> 供自己日常使用

coding-m1-1 的 proposals 中，proposal_id=p2：

> 工具供用户本人在日常使用场景下运行，不是对外分发或演示。

该候选的 kind 是 user_fact，引用只有“供自己日常使用”。“不是对外分发或演示”没有来自用户的依据；个人使用与未来分享、演示并不互相排斥。

这一条的 strength 为 unspecified，不应误称模型将它直接标成了 hard。但把未被支持的排除性断言归为 user_fact，本身已经不符合忠实提取要求。

### 2. 同类表现

| 请求／位置 | 原始输出 | 判定 |
|---|---|---|
| coding-m2-1：plan.goal.audience | 工具的唯一日常使用者（本人），在 Windows 环境下通过命令行调用，无需联网。 | “唯一”缺少依据；此前拒绝 p2 并未消除 M2 同类过度推断 |
| writing-m2-1：plan.completion_criteria 中 c2 | 通知内容适配新生微信群发布，不依赖群外渠道。 | 发布渠道为微信群，不等于排除群外渠道；原有线上报名表也未被取消 |

对于写作 c2，可以确认它增加了未明确提出的限制。不能进一步断言线上报名表已被删除或一定无法使用，因为方案其他位置仍保留了线上报名表；更准确的问题是新增限制及跨字段解释歧义。

### 3. 实际处理与影响

测试操作者拒绝了 p2，接受有明确来源的其他候选后继续，动作在 operator_actions.json 中可查。原始返回没有被改写，正式需求也没有接受该候选。

因此，程序提供的候选复核边界起了作用，但本轮仍需要操作者纠正模型。不能把最终能继续运行描述为模型从未产生错误要求。

如果用户未察觉并接受此类候选，下游可能错误收窄使用对象、传播方式、技术路线或交付范围。这是潜在影响，本轮未执行这些下游任务，不能描述为已发生的实际损失。

### 4. 将来判定改善的标准

- 用户事实中的每个实质性断言都有原话或可核验材料支持。
- “已说明一个场景”不自动变成“排除所有其他场景”。
- 同类保护延续到 M2，不只在 M1 候选区生效。
- 系统可以提出建议，但要与用户已经决定的内容区分。

## 四、F2：待确认建议与确定完成标准混用

**状态：确认存在。涉及 M2。影响：方案一致性和用户决策边界。**

### 1. 实际已确认的文件保护要求

用户要求不能修改或覆盖原文件。正式需求 r3 是：

> 合并过程不得修改或覆盖原始 CSV 文件，结果只写入新文件。

它支持保护源 CSV，但没有穷尽遇到其他已有输出路径时的交互选择，例如停止、换一个新路径或提示用户决定。以下问题不要求程序开放危险覆盖行为。

### 2. 同一响应中的矛盾

coding-m2-1 的 plan.suggestions 中 sg3：

> 输出文件路径已存在同名文件时，明确采用“提示并终止、不覆盖”的策略，并在说明中写清。

它被标记 requires_user_confirmation=true，reason 明确写道：

> r3 只要求不修改或覆盖原 CSV，未规定输出路径冲突时的行为；该策略需用户确认后固定。

同一份方案中：

| 位置 | 输出表现 |
|---|---|
| s1.actions／局部标准 | 虽承认需确认，又规定未确认前按“不覆盖、仅提示”处理 |
| s3.actions | 输出路径已存在时按 s1 约定处理（默认提示并终止，不覆盖） |
| s3.completion_criteria | 输出路径冲突时未发生覆盖 |
| 整体 c4 | 输出仅写入新文件且不覆盖已存在的同名文件，归于 r3 |
| 关键工作 k2.checkpoints | 输出路径冲突时不覆盖 |

### 3. 判定及重要限定

“不覆盖”的保护原则本身并无问题，也可以作为合理的保守方案提议。问题在于整套同名冲突策略一方面标记需要确认，另一方面又在执行与检查字段中固化，未清楚分开保护原则、暂定处理和用户尚未决定的行为。

M2 本来就负责提出方案，不必对每个正常实现细节另问一次用户。因此，本报告不是要求所有步骤必须来自逐字用户指令；需要保留的是同一事项跨字段的身份和确认条件一致。

本轮该方案仍是 draft，没有发生程序替用户完成方案确认。这里确认的是**模型草稿的语义边界不一致**，不能把它写成“程序已经擅自修改正式需求”或“已确认方案已被污染”。

### 4. 影响与未来验收标准

下游若只读取步骤和完成标准，可能漏掉建议区中的待确认条件；只读取建议区，又可能误认为前面的步骤尚未采用它。这会影响后续整合、导出及用户复核。

后续验收应检查：

- 同一策略在建议、步骤、标准和关键工作中，待确认状态一致。
- 已确认保护原文件的约束完整保留。
- 可合理选择保守默认，但明确其提议／条件身份，不冒充用户已经确认。
- 对有条件的部分，说明何时需要决定、未决定时哪些工作仍可继续。

## 五、F3：占位草稿与可直接发布成稿混用

**状态：确认存在。涉及 M2。影响：完成状态和使用指导。**

### 1. 输入明确允许暂时缺失信息

写作测试用户说明报名链接未确定，负责人姓名和联系方式尚未提供，先保留待补充标记，不编造。模型确实保留了这些未知，没有捏造实际日期、链接或联系人。

### 2. 同一方案的不同表述

writing-m2-1：

| 位置 | 原始内容／状态 |
|---|---|
| s4.title | 定稿发布版通知 |
| s4.purpose | 在核对通过后形成可直接发到新生微信群的最终文本。 |
| s4.actions | 保留所有待补充标记；输出最终通知文本供用户确认后发布 |
| d3.description | 可发布到新生微信群的定稿，保留待补充标记，不编造活动日期、报名链接、负责人姓名与联系方式。 |
| ug3.confirm_by | 在通知发布前，由用户提供或确认报名链接后更新。 |
| ug4.impact | 不影响起草，但发布前需要补齐信息。 |
| sug1 | 确定链接与联系方式后替换占位，被归为 optional_improvement，并标需要用户确认 |

### 3. 判定与边界

一份结构完整的初始方案可以含未知，带占位的通知也可以作为当前阶段的完整草稿。这两点符合产品设计，不构成失败。

失败在于方案自己同时规定“发布前需要补齐”并称当前输出“可直接发布”，没有清晰表达中间条件。s4 的“用户确认后发布”保留了人工环节，但未与信息补齐前提充分对齐。

本轮没有实际发布通知，也没有生成下游最终通知文本。观察对象是 **M2 对未来交付物及完成条件的描述**，不能表述为软件已经把错误通知发出。

### 4. 影响与未来验收标准

用户可能把“方案完整”“草稿可交付”误读为“已经满足发布条件”。后续 Skill 整合也可能继承同一状态歧义。

改善应表现为：保留未知，分别描述当前草稿的完成标准、发布前需要满足的条件及可继续的工作；涉及必须补齐的条件，不再同时写成不影响发布的可选项。无需为使文案看起来完成而编造缺失信息。

## 六、另外两项观察：先记录，不扩大为确定失败

### O1：写作受众范围存在输入歧义

初始输入为“大一新生”，测试回答为“欢迎零基础的大一新生，也欢迎已有摄影经验的同学”。模型提取成“以大一新生为主”。后一半测试答案本身未重申年级边界。

可以关注“以……为主”的精度，但证据不足以判定模型明确把受众扩大到其他年级。未来使用“零基础或已有摄影经验的大一新生”等无歧义输入复验，不把本项计成另一个已确认严重错误。

### O2：普通实现建议与技术限制的区分还不够清楚

编程 s1 写“明确离线要求……仅使用 Python 标准库能力”。标准库是可行实现建议，离线运行本身不排斥预装的第三方库。

应关注它是否被误解为已确定的技术限制。不过，M2 有权提出执行办法，因此“选择标准库”本身不是错误；问题是其与用户硬约束身份的表述不清。这一观察作为 F1 的补充线索，不单独计入主问题数量。

## 七、这是不是之前的问题，是否说明没修好

当前证据支持以下结论：

- 这些是在本轮当前版本真实输出中观察到的问题，属于新的实测证据。
- 不能仅据这些输出，判断其首次出现于哪一版，或者认定上次代码修复引入了回归。
- 此前的程序回归、人工 fixture 与本轮真实内容审阅验证的是不同层面；程序通过并未承诺所有模型输出语义正确。
- 当前提示中已有忠实承接需求、建议与事实分开等原则；本轮说明它们在这些真实输入上仍未充分约束输出，具体成因尚未做版本对照或消融分析。

因此，目前应登记为“当前版本的内容质量待改进项”，不贴上未经证实的“旧问题未修好”或“新代码故障”标签。

## 八、优先级与阶段判断

| 项目 | 对内容验收的要求 | 对当前程序功能结论的影响 |
|---|---|---|
| F1 无依据的额外限制 | 内容验收前必须关注，核心目标是忠实保留用户要求 | 未证明 API 或状态机制失效；候选复核实际拦住了 p2 |
| F2 跨字段确认边界 | 内容验收前必须关注，尤其影响末端整合 | 未观察到程序自动确认，但后续模块应避免继承歧义 |
| F3 草稿／发布状态 | 内容验收前必须明确完成条件 | 未发生实际发布，不能归为发布功能事故 |
| O1／O2 | 明确输入或调整判据后再验证 | 暂不单独计为失败或扩大阻断范围 |

现有功能证据仍支持开展后续开发；当前内容样本不足以宣布 M1/M2 质量全部通过。按照用户最新安排，问题修订暂缓，后续开发继续，不需要等待这三项修复或复测。新模块仍应保留已有来源、未知和确认边界；不能把“允许继续开发”解释为这些测试草稿已被确认。

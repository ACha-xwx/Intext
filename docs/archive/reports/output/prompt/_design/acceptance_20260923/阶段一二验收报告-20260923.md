## 按产品预期看，完成到什么程度

用户关心的是“能否真正帮助人把要求说清”，技术检查是判断这一点的证据。以下不使用缺少依据的完成百分比。

| 原本预期 | 当前判断 | 用户实际会感受到什么 |
|---|---|---|
| 有一个能打开、输入、保存重开的程序 | 基本达到本机阶段预期 | 源码和exe可以启动，会话正常保存重开；跨机仍待验证 |
| AI真的理解输入并追问，而不是固定模板演示 | 在已测编程案例达到 | 能保留“不做付款”，先问实际使用还是演示，再根据回答补充功能 |
| 已经说过的要求可靠累积保留 | 未充分达到 | 正常案例能保留，但改任务、错误响应和接受失败时会出现错配或状态损坏 |
| 不知道、跳过、改主意都能顺利继续 | 部分达到 | 按钮和记录已有；未知可能被漏掉，冲突可能过早消失，真实边界路径还未测完 |
| 用户看懂需求卡并真正决定接受什么 | 部分达到 | 可以编辑和接受，但看不到来源、建议／决定、硬约束／偏好的清楚区别 |
| 对话自然，不让用户反复做机械操作 | 正常问句已有改进，交互仍需打磨 | 回答问题前被要求先接受或忽略候选；用户需要理解两张列表及多次按钮操作 |
| 六类共用且有实际适配 | 框架达到，效果待验证 | 七个入口及字段存在；目前留存真实证据不足以证明写作、PPT等也能自然引导 |

## 想比当前预期更好，最值得做的3个小改进

这些是修复正确性问题之后的体验建议，未在本次实施，也不擅自变成必须新增的功能范围。

1. **让回答问题更直接。** 将模型提取先积累为可编辑草稿，允许用户直接回答下一问；保留最终版本化确认，只有冲突或高影响改动需要提前明确处理。避免每轮都先“接受候选”才能继续讨论。可以先做到“提交回答时保留未处理草稿”，无需重做整个界面。
2. **让需求卡解释“为什么这样写”。** 点中一条即可看完整内容、对应原话、用户决定还是系统建议、是否硬约束，以及本轮改了什么。用户能快速发现误解，比增加更多字段或装饰更有价值。简单做一个详情区即可。
3. **每轮只突出一个明确的下一步。** 有关键问题时突出回答；信息足够时突出核对需求；有冲突时展示两侧并处理；预算用尽时说清还缺什么及能否带未知继续。保留跳过、修改等辅助入口，不要求用户先理解need_goal、can_defer等内部枚举。

内容质量的下一步建议用一条信息完整的写作任务和一条“不知道标准”的PPT任务检验：前者应少问或不问多余问题，后者应帮助把“清楚一点”等模糊表达变成可讨论标准。局部示例生成仍按后续阶段安排，不为这次验收提前扩大范围。

## 必须先修复的4项问题

### R1 · P1：合法的input_error会被当作正常结果应用，清空旧缺口与冲突

代码：[workflow.py:54](<../../../../../../../src/promptsmith/workflow.py>)、[workflow.py:100](<../../../../../../../src/promptsmith/workflow.py>)、[session.py:171](<../../../../../../../src/promptsmith/session.py>)。

`parse_m1_response()`允许符合约定的`status=input_error`空结果；workflow将“结构合法”统一写为校验成功并进入apply。Session没有按status分支，直接用空数组覆盖已有gaps、conflicts和候选。

复现：载入已保存会话，在内存中设置一项旧冲突，输入有3个缺口、1项冲突；应用合法input_error后两者均变为0。readiness明明为false，随后仍可确认需求版本4。界面还会显示“需求候选已返回并通过本地校验”。

影响：一次输入处理失败就能让未决事项和冲突消失，违背“失败保留状态”和“不能由模型确认”的核心边界。

修复要求：把业务失败与结构合法分开；input_error记录为失败并显示说明，保留旧卡、候选、缺口、冲突和确认依据，不扣问题预算。新增一条从workflow到UI的回归，而不仅测试JSON是否符合错误格式。

### R2 · P1：确认没有绑定当前有效内容，修改任务后仍可确认旧需求

代码：[session.py:123](<../../../../../../../src/promptsmith/session.py>)、[session.py:130](<../../../../../../../src/promptsmith/session.py>)、[session.py:268](<../../../../../../../src/promptsmith/session.py>)、[ui.py:449](<../../../../../../../src/promptsmith/ui.py>)。

确认函数只检查存在需求、无候选、无冲突及无blocking gap。它没有判断当前目标／交付物是否有效、readiness是否过期、输入是否截断、是否有待复核条目。set_task又会清空缺口和冲突，保留旧requirements及旧readiness。UI确认按钮未先同步任务输入框。

三个复现均成立：

1. 已确认的网站任务改为“写一篇社团招新文章，读者和篇幅还没想好”，未经新分析，就能把旧网站的4条需求确认为新版本5。
2. 撤销唯一deliverable条目后，只剩约束、用途和功能，仍能直接确认。
3. UI输入框显示全新的写作任务，点击确认时session仍是原网站任务，却显示“已由用户确认需求版本4”。

修复要求：统一内容快照与确认依据；编辑任务、改类别、撤销关键项后使旧充分性判断失效并标记受影响内容需复核。确认操作先同步UI，检查当前版本的方向、交付物、冲突和复核项。不要仅增加对模型ready布尔值的信任，也不要简单要求必须有一个field=goal条目，因为目标可能已由具体交付物表达。

### R3 · P1：批量接受候选中途失败后发生部分写入，版本却不变

代码：[session.py:184](<../../../../../../../src/promptsmith/session.py>)、[session.py:197](<../../../../../../../src/promptsmith/session.py>)、[session.py:223](<../../../../../../../src/promptsmith/session.py>)。

复现：当前有一个new候选和一个replace r2候选，两者先通过现有M1校验。用户手工编辑r2后，旧r2归档、获得新ID，但原候选仍保留。点击接受全部，循环先加入new项，处理replace时因r2不存在抛错，最后的版本更新与候选清理没有执行。

本次连续点两次的结果：需求由4条变为6条，版本一直为5，两个候选仍在，界面连续收到“候选引用了不存在的需求：r2”。独立状态审查也复现了相同行为。

影响：用户看到失败，却已有内容写入；重试重复添加，保存后会持久化错误状态。

修复要求：候选保留生成版本，编辑／撤销后作废或重新校验相关候选；整批先验证目标、重复目标、依赖和冲突，再一次提交。失败应不改变任何业务状态。补“先new后失效replace”和重复点击回归。

### R4 · P1：接受冲突里的候选即删除整条冲突，矛盾要求可以一起确认

代码：[session.py:219](<../../../../../../../src/promptsmith/session.py>)。

复现：旧需求r2是“本次不做付款”，本轮返回new候选“本次加入在线付款”并列出冲突。这种输出形状通过当前完整Schema及语义校验。接受候选只新增一条要求，没有移除旧约束，但代码只要发现accepted_ids与conflict.proposal_ids相交就删除整条冲突。最终两条矛盾要求同时存在、open_conflicts为空，确认成功。

影响：冲突提示并未保证矛盾真正解决；涉及多个候选或多个旧项时，部分处理也会过早关闭冲突。

修复要求：根据冲突的实际涉及项和用户的替换／保留／撤回决定关闭冲突。不能以“接受了其中一项”代表全部解决；无法证明已解决时继续保留。补new与旧约束冲突、多个冲突候选只处理一部分的回归。

## 完成不足的3项内容

### R5 · P2：未知项仍依赖模型主动保留，程序允许无依据清空

代码：[m1.py:184](<../../../../../../../src/promptsmith/m1.py>)、[session.py:175](<../../../../../../../src/promptsmith/session.py>)。

旧冲突ID有守卫，旧gap却没有同类机制。复现中没有新证据、没有任何更新proposal，只让合法响应返回gaps=[]；校验通过并把旧3个gap全部清空。已有3项中至少表单／功能细节和运行方式仍未解决。这与既有设计中“省略旧gap不等于解决”的规定不一致。

另发现已保存的真实UI结果把“用途已明确，该缺口可关闭”仍保留为一个`can_defer`未决项，界面因此同时把已解决事项和真实未知都叫作未决项。该问题来自实际留存响应及程序消费方式，不只是构造输入。

修复要求：用来源、用户范围修改或明确的解决建议审核gap变更；不应依赖字段出现就删除，也不宜永远保留所有旧gap。需要能区分保留、已解决和不再适用。至少补“跳过后空数组返回”和“回答后关闭对应缺口”的回归。

### R6 · P2：前置需求改变后，依赖和待复核状态没有形成闭环

代码：[session.py:247](<../../../../../../../src/promptsmith/session.py>)、[session.py:261](<../../../../../../../src/promptsmith/session.py>)、[session.py:174](<../../../../../../../src/promptsmith/session.py>)、[m1.py:116](<../../../../../../../src/promptsmith/m1.py>)。

复现：r4依赖用途r3；将r3从课堂演示改为实际上线后，旧r3归档但r4仍depends_on=[r3]，且r4仍显示confirmed。下一轮build_m1_input仍把悬空引用发给模型，用户也能继续确认。

`review_item_ids`只是存入pending_review_item_ids，没有落实到条目状态、UI复核入口或确认拦截；构造不存在的missing-r999也能通过当前输出校验。

修复要求：统一编辑／替换／撤销时的依赖处理，只有语义等价时才安全重定向，否则将受影响项标为review_needed并提供复核操作。校验活动引用及review_item_ids。类别改选也按这套机制处理专有字段。

### R7 · P2：需求卡保存了来源等信息，用户却无法在界面核对

代码：[ui.py:215](<../../../../../../../src/promptsmith/ui.py>)、[ui.py:225](<../../../../../../../src/promptsmith/ui.py>)、[ui.py:483](<../../../../../../../src/promptsmith/ui.py>)。

实际控件检查：正式卡只显示field/text/status，候选只显示operation/field/text；详情区仅列类别、冲突和缺口；没有选中条目的详情绑定。用户看不到kind、strength、scope、source_refs及原文证据，也没有清楚的旧值／新值并列。

影响：系统建议、用户明确决定、硬约束和偏好在接受前无法辨别，削弱“可追溯、可纠正”的核心体验。Treeview单行内容无全文详情，对长要求和长问句也不利。问题options已由模型返回但没有展示。

修复要求：至少增加一个可滚动的选中项详情，显示完整文本、来源与原话、类型、硬约束／偏好、适用范围、变更前后值；把内部英文枚举转换成用户语言。无需为此重做整个UI。补一个含系统建议和长硬约束的人工操作案例。

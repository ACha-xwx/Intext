## 结论

D2 在第二次 M1 调用因响应额外返回 `readiness.blocking_gap_ids_note` 被严格 Schema 拒收。该失败被正确记录，不能据此推断 D2 的需求确认、M2 方案、Skill 匹配或 M4 整合质量；这些步骤本次均未执行。

## D1 内容与流程复核

1. M1 前四轮保持用户事实、硬约束和语气缺口；第四轮得到 `next_action=review_requirements`，需求版本为 5。M2 返回了完整初始方案，且仍把 `sg1`、`sg2` 保留为待用户决定建议。
2. M5 请求发生在需求和方案确认之后，评价维度是“语气自然但活泼程度适中”，A 为轻快俏皮，B 为温和亲切，维度没有漂移。
3. 操作者选择 B 并记录“喜欢 B 的直接，但不要口号”，程序生成了一个 `m5_feedback` 的 `pending_interpretation` 候选。`session.json` 中正式需求仍只有原来的 `r6`“自然活泼，但不要口号式表达”；该反馈没有被错误地自动写入需求，这一点符合当前状态边界。
4. 但固定案例要求对这条窄范围标准进行复核确认，实际操作没有接受该候选；随后直接确认了 final。因而 final 的 `confirmed` 只证明原需求／方案基线被确认，不能证明 M5 反馈已经生效。
5. 本次 D1 没有 `trial` 调用或试运行记录。固定案例要求的“确认最终提示后主动点击一次短文本试运行”未执行。
6. M5 raw 的 A 选项包含“**不用带复杂装备**”，B 选项包含“**不需要有基础**”，但 `unsupported_assumptions=[]`。A 明确触及用户禁止凭空添加器材要求的边界；B 也缺乏用户来源。`m5.py` 当前的约束检查主要是负向词的字面重叠，不能覆盖这类同义或正向表述，因此不能把 M5 的结构通过当成内容安全通过。
7. 走查脚本的 D1 自动内容观察把 final 的完整结构（其中本来就有“不得添加负责人、收费或器材”的约束文本）序列化后查禁词，得到 `forbidden_terms_present=[负责人, 收费, 器材]`。这属于观察脚本的明显误报，且结果状态已经标为 `automated_observation_pending_human`；它不能证明最终提示正文实际加入了这些内容，也不能替代人工审阅。

## 可重复的程序与走查边界

- M5 解析器能校验维度、字段、长度和明显字面冲突，但不会从 shared assumptions、用户来源和选项文本之间做完整事实核对；模型把新增器材／能力说法标成空的 `unsupported_assumptions` 时，程序仍会接受。
- M5 反馈候选默认待审，未被自动升级为正式需求；这不是 D1 的失败原因，但走查脚本必须显式执行“接受候选并重新确认”或把本项记为未完成。
- 旧 D1 runner 调用 `record_m5_feedback` 后未执行 UI 中追加 `pending_proposals` 的步骤。因此这次 final 确认并没有面对正常 UI 流程的待审 M5 候选；这是走查脚本漏接，不能据此推断产品允许绕过待审候选。
- D1 自动内容观察检查了结构化 final 全文，而不是实际交付文本字段，禁词结果不能用于判断最终提示是否违反禁止项。
- D2 的 additive-field 失败显示当前线上模型输出仍可能超出 `m1.v0.2` 契约；本次审计不擅自放宽 Schema，也不修改提示或代码。

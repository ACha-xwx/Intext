## B1 · P1：接受已知要求或提交“不知道”，会把未解决缺口删除

位置：[session.py:206](<../../../../../../../src/promptsmith/session.py>)、[session.py:437](<../../../../../../../src/promptsmith/session.py>)、[session.py:581](<../../../../../../../src/promptsmith/session.py>)。

复现一：任务是供社团实际使用的报名网站，明确“不做付款”；模型正确地同时列出已知付款限制和未知预算，两者均为 `constraints / 整体任务`。接受“不做付款”等候选后，程序按 `(field, scope)` 批量删除预算缺口。预算问题仍未回答，`gaps` 却为空，并可确认需求版本 2；保存重开后仍为空。

复现二：程序询问报名表单字段，用户在自由输入框回答“这个我还不知道”，点击提交回答。`record_question()` 只判断回答非空，立即删除对应缺口。下一轮模型省略该 gap 时，保留机制已无旧记录可合并，需求可确认且不再保留这项未知。

这不是要求未知全部解决后才能确认：可延期未知本来就允许带入方案。问题是未知被误认定为已解决并丢失，违背“信息累积、未知标明”的核心目标。

修复要求：字段和范围只用于组织信息，不能作为具体缺口已解决的证明。记录回答时保留缺口及处理状态；关闭需要对应具体 gap 的答案／证据与可核验的解决建议。模型省略、不确定、部分回答、接受同字段其他要求均不能自动关闭。避免新增“永远不能关闭”的反向问题，确有完整答案时应可关闭。

验收案例：不做付款＋预算未知；自由输入不知道；只回答一部分；明确回答后关闭目标 gap 并保留其他 gap。

证据：`observed_state_round2.json → same_field_scope_gap_closure`；`observed_results_round2.json → unknown_free_text_closes_gap`。

## B2 · P1：模型返回空 review_item_ids，可以撤销程序要求的用户复核

位置：[session.py:294](<../../../../../../../src/promptsmith/session.py>)。

复现：需求 r2“报名数据仅临时保存在浏览器”依赖 r1“课堂演示网站”。手工把 r1 改为“供社团实际上线使用”，程序正确重定向依赖，并将 r2 标为 `review_needed`。随后一个通过完整校验的模型响应返回 `review_item_ids=[]`。

`stage_m1_result()` 用模型列表覆盖程序复核列表，并把未列出的 `review_needed` 条目改回 `pending`。没有调用任何用户复核操作，r2 的复核要求就消失，最终可确认版本 4。

模型漏报受影响条目是可能发生的内容错误，程序不应把漏报解释为用户已完成复核。这里不是模型直接设置 confirmed，而是模型清掉了原本用于保护确认流程的门槛。

修复要求：模型只能新增复核建议；程序设置的待复核标记应持续保留，直到明确用户复核，或有对应条目的替换／撤回处理。合并时记录产生原因，不能因下一轮省略而清除。修复时同时处理 B3 的已归档复核 ID，避免合并后永久残留。

验收案例：前置需求改动 → 依赖项待复核 → 模型返回空复核列表 → 仍不能确认 → 用户明确复核后才放行。

证据：`observed_results_round2.json → program_review_erased_by_model`。

## B3 · P2：替换、撤销、编辑后，部分活动引用仍指向旧编号

位置：[session.py:368](<../../../../../../../src/promptsmith/session.py>)、[session.py:435](<../../../../../../../src/promptsmith/session.py>)、[session.py:469](<../../../../../../../src/promptsmith/session.py>)、[session.py:217](<../../../../../../../src/promptsmith/session.py>)。

两条独立路径已复现：

1. 合法返回同时建议替换／撤销 r2，并要求复核 r2。用户接受候选后 r2 已归档，`pending_review_item_ids` 仍有 r2。确认被拦截，但正式需求卡已没有 r2，用户不能通过选中该项完成复核。只能额外分析恢复；保存重开也保留错误。
2. 未知项与问题均依赖 r1。用户编辑 r1 后新编号是 r3，正式需求依赖得到更新，但 gap 和待回答问题仍引用 r1。下一轮 `build_m1_input()` 把悬空 gap 发送出去；模型按原样保留这个未知时，响应校验反而报“依赖引用了不存在的旧需求：r1”。

修复要求：所有修改入口共用引用更新规则，覆盖正式需求、候选、缺口、问题、冲突和待复核列表。不能安全沿用的问题应失效或待重新判断；不能把清理引用等同于该未知已解决。构建输入和确认前检查全部活动引用，而不仅检查正式需求的 `depends_on`。

验收案例：替换和撤销待复核项后列表只含活动 ID；编辑前置项后未知项仍保留且引用合法；下一轮正常返回可被接受；保存重开结果一致。

证据：`observed_state_round2.json → retired_pending_review_ids / gap_question_dangling_dependencies`。

## B4 · P2：跳过一个子任务的问题，会封禁其他范围内的同字段追问

位置：[m1.py:190](<../../../../../../../src/promptsmith/m1.py>)。

复现：混合任务是“活动报名网站＋介绍网站的 PPT”。用户跳过网站使用者问题（`audience / 活动报名网站`）。下一轮问 PPT 听众（`audience / PPT汇报`），仍被本地校验拒绝，报“用户已跳过或表示不确定的问题不能在无新上下文时重复询问”。

代码仅按 `field` 拦截，没有比较 scope，也没有判断新证据／主动重开。M1 v0.3 的规则却明确按同一 field 与 scope 判断重复，并允许在有新原因时重问。因此这项修复过宽，会把合理的新问题变成整个模型响应失败。

修复要求：按具体问题或 gap、字段和适用范围判断重复；是否因新证据重开应有明确依据。不要只凭 reason 非空放行，也不要永久禁止整个字段。继续保留对无新依据、同范围重复追问的保护。

验收案例：同字段不同 scope 可以问；同 scope 无新信息不得重问；用户主动重开后允许有依据的再次提问。

证据：`observed_results_round2.json → skip_one_scope_blocks_another`。

## 补充边界：确认门槛还没有完整覆盖输入契约

位置：[session.py:533](<../../../../../../../src/promptsmith/session.py>)。

追加检查中，`context_coverage=truncated`、模型正确返回 `pause_with_unknowns`，程序仍可确认。另一个故意构造的防御性场景中，`deliverable_identified=false` 且交付物未知被误标为 can_defer，只有一条泛目标也能确认。后者不是正确的模型行为，记录它是为了标明程序不会拦截这类互相矛盾的充分性判断。

当前 UI 默认提供 complete 上下文，所以截断场景不作为本轮日常操作的主要阻断；在开始裁剪上下文或接 M2 时应补齐该契约边界。`analysis_basis_version` 只证明本版本分析过，不证明内容足够。检查应结合当前实际需求、有效分析依据和未知状态，不能简单依赖单个布尔值，也不应要求所有未知消失或一律禁止 `pause_with_unknowns` 下的确认。

证据：`truncated_context_can_confirm`、`false_deliverable_readiness_can_confirm`。

## 建议本轮收尾顺序

1. 先修 B1、B2，保证未知不会误删、程序要求的复核不会由模型取消。
2. 同批修 B3，使所有修改入口的活动引用保持一致；再修 B4，避免混合任务误报失败。
3. 把本次复现转为预期行为的回归，跑现有 56 项及新增测试，检查保存重开，重建发行包。无需扩展 M2—M5 功能来通过这轮验收。
4. 补三条真实模型路径：有预算时明确改要求；跳过／不确定后的多轮继续；信息完整的非编程任务少问或不多问。逐项检查信息保留、追问依赖和语义质量，保存实际用量。再人工走一次输入到确认及长文本／缩放体验。

本轮已有的来源详情、先回答后处理候选、下一步提示值得保留。下一步最有价值的提升是让用户在不知道、修改和跳过时仍能自然继续，并确信需求卡没有丢掉重要信息。

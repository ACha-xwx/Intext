### 2.2 Skill 匹配漏报

这条优先问题**成立**。

- `catalog_v0.1.json` 中 `to-spec` 的 `software_context` 与 `specification_work` 是两组。
- `skill_catalog.py` 对组内做 OR、组间做 AND，并且 `_work_text()` 只读取关键工作的标题、目标、说明、输入、输出、检查点和动作，不读取 `session.task_text`。
- D2 的 k1/k2/k3 都命中“规格/测试决定”等 specification 组，但三个关键工作自身没有“软件/报名系统/网站/程序”等 software_context 词，因此真实结果为 `no_match`。
- 只把 k1 标题改成“软件功能需求规格编写”可以匹配 k1，说明当前目录规则本身能工作；问题在于关键工作与任务语境之间没有传递。

v0.1 提出的“只把原始任务文本纳入匹配”单独不够，因为 D2 原文使用“报名工具/开发者”，而当前 software_context 没有“工具”，且 matcher 不读取 task_text。

直接加入裸词“工具/系统/开发”也不成立为安全修法。当前 matcher 是子串匹配，已有词“应用/网站/程序”就能让“应用数学课程规格编写”“课程应用需求规格编写”“网站内容规格整理”误命中 `to-spec`；再放宽泛词会扩大误报。

## 3. 新发现

1. **当前目录已经存在误命中，不只是 D2 漏报。** 这是因为 `应用`、`网站`、`程序` 采用简单子串匹配。后续任何放宽 software_context 的修复都必须同时收紧或改为复合语境匹配。
2. **现有 fixture 不能证明真实 D2 可匹配。** `tests/test_fixed_demo_runner.py` 的离线 coding fixture 使用了含“软件需求规格”的关键工作标题，与真实 D2 的 k1/k2/k3 不同，因此它只验证了流程，不覆盖真实目录漏报。
3. **修复 Skill 匹配需要跨接口传递上下文。** 当前公开入口是 `SkillCatalog.match(key_works)`，UI 传入的只有关键工作；推荐增加可选 `context_text` 或等价的明确字段，保留匹配证据来源为“任务上下文/关键工作”，不要把任务词伪装成关键工作原话。
4. **目录记录改动会影响可信哈希。** 若修改 `catalog_v0.1.json`，必须重算 `to-spec.record_hash` 和目录快照哈希，否则加载会被 `skill_catalog.py` 的记录校验拒绝。
5. **设计索引存在相对链接错误。** `output/prompt/_design/README.md` 顶部使用 `../../verification/...`，从该文件所在目录解析会指向不存在的 `output/verification/...`；实际证据目录在项目根的 `verification/...`。目标文件存在，问题只在索引相对路径。

## 4. 如果只能做一件事

优先修正 **Skill 匹配的上下文与误报控制**，然后再重建 EXE。

推荐的下一轮最小实现：

1. 给 `SkillCatalog.match()` 增加可选、可审计的 `context_text`；UI 传入当前已确认任务文本，必要时再合并已确认需求摘要。
2. `to-spec` 只补高辨识度复合词，例如“报名工具”“管理后台”“应用程序”“API 接口”“前端”“后端”“数据库”“客户端”“服务端”；不要裸加“工具/系统/开发”。
3. 匹配结果记录命中来自 `context_text` 还是关键工作字段，`match_reason` 不得把上下文词说成关键工作原话。
4. 新增至少一组 D2 正例（k1/k2/k3 均能得到 `to-spec`）和三组反例（课程规格、教学工具规格、文档开发规格均不推荐），同时保持现有通知与 goal checklist 反例。
5. 修改目录后重新计算记录/目录哈希，再运行全量测试；之后才重建 EXE并验证状态栏和发行链。

理由：这条同时影响比赛演示的旗舰能力和推荐可信度；如果先重建 EXE，只会把旧的 `no_match` 体验和过期状态栏一起固化，不能解决根因。

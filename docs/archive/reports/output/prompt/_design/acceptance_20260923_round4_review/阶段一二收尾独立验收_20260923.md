## P1：保留冲突编号、遗漏参与方，可以错误确认

定位：

- `src/promptsmith/m1.py:382` 只检查旧冲突编号是否仍存在，没有保护其仍有效的参与方。
- `src/promptsmith/session.py:500` 用模型返回覆盖原冲突记录。
- `src/promptsmith/session.py:274` 的协调逻辑删除只剩一方的冲突。
- `src/promptsmith/session.py:715` 的确认保护此时看到空冲突列表，无法阻止错误确认。

实际复现（不编辑会话 JSON，不绕过生产解析和应用入口）：

1. 按原 C2 路径建立冲突并编辑要求。此时冲突关联 `r4` 和 `r3`，两条要求都仍活动，冲突正确保留。
2. 下一轮合成模型响应保留相同 `conflict_id`，将 `existing_item_ids` 从 `[r4, r3]` 减为 `[r3]`，没有用户撤回或解决操作。
3. 输入构建、输出 Schema、语义校验和应用全部通过；协调后 `open_conflicts=[]`。
4. 调用用户确认所用的 `confirm_requirements()` 成功，两条互相矛盾的要求一起确认到版本 5。
5. 实际保存并加载，错误确认状态仍然存在。

复现数据沿用历史网站任务中的“加入在线付款／任何版本都不做付款”两条矛盾要求。它们只是用来测试冲突机制的任务内容，不是本产品的支付需求，也不要求增加收费功能。

独立复核项为 `observed_reference.json → cases.reduced_conflict_participants`。主验收者另外运行 `recheck_conflict.py`，在 `observed_primary_conflict_recheck.json` 再次记录：`incorrect_confirmation=true`、确认版本 5、保存重开一致。复现进程退出码 0 表示探针按预期捕获了漏洞，不表示该产品行为通过验收。

影响：M2 计划消费已确认的需求快照，这条路径会使“已确认且无冲突”的程序状态失去可靠性。因此是第一部分收尾阻断，而非新增产品功能要求。

最小修复方向：由程序保留未解决冲突及其仍有效的参与方；模型省略一方或更换参与方不能自动视为解决，应在应用前拒绝或保守保留。用户实际撤回、接受解决操作后的合法关闭通路要继续可用。不能只在提示里要求模型不要遗漏，也不能把修复做成所有冲突永久无法关闭。补入本条完整构建／解析／应用／确认／持久化回归即可，不需重做 C1、C3 或扩展 M2。

## 非阻断的恢复体验问题

替换探针将矛盾一方替换为与另一方完全相同的要求后，原冲突仍保留，继续阻止确认。证据为 `replacement_resolution`。这说明“通过替换解决冲突”尚不顺畅；不过本轮已验证手工撤回及接受撤回候选均能合法恢复，因此不另列第二个阻断。

它与上述 P1 是相反方向的边界：未解决时应保留，真正解决后应有明确可达的关闭路径。修补 P1 时应保留现有撤回通路；后续完善明确解决／替换机制时可使用此探针，不能通过允许模型任意删减参与方来解决。

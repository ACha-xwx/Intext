# M1 第二轮截断：现状与实施记录

## 修改前核查

- 调用链：UI `record_question()` → SessionState 保存用户原话、来源及 `answered/pending` 历史 → `start_analysis()` → `prepare_m1()` / `build_m1_input()` → `invoke_m1()` → API `complete_json()` → JSON / Schema / 语义校验 → `stage_m1_result()` → UI 刷新。
- 提示：第一轮与第二轮均为 `M1_system_v0.8.txt`。输入、输出 Schema 均为 `m1.v0.2`。M2 仍是 `M2_system_v0.1` / `m2.v0.1`，本问题不发生在 M2。
- 协议和模型由界面配置决定，默认是 DeepSeek / OpenAI Chat Completions / `deepseek-flash`。本轮没有读取密钥或发起真实调用，不能据默认配置断言用户那次失败的实际模型。实际值应以失败目录 `meta.json` 为准。
- 三协议结构化生成已经统一 8192：Chat/Anthropic 为 `max_tokens`，Responses 为 `max_output_tokens`。生成超时已经是 120 秒，连接测试/模型目录为 15 秒；本轮不能再按旧的 45 秒或缺少 token 参数假设修复。
- 连接探针已使用 8192，探针遇到长度停止单独标记 `probe_truncated`；正式生成仍严格拒绝截断。
- M1 输出没有整张 `requirements` 字段，已有 `proposals`、`gap_updates` 是变化建议。但 v0.8 仍要求完整重述未决 gaps/conflicts，且没有独立精简重试入口。
- 每次请求重新构建当前状态快照，包含活动需求、缺口、冲突、来源和回答历史；不是不断追加聊天消息。模型失败文本没有写入用户来源。没有自动重试。
- Chat 在 `finish_reason=length`、Responses 在 `status=incomplete`、Anthropic 在 token/context 限制处抛 `ApiError(kind=truncated)`；发生于业务 JSON 解析之前。旧代码丢失截断响应中实际可得的部分文本/用量/响应 ID。
- 用户点击“回答”时已经保存到内存 SessionState，可随后保存会话 JSON；不是请求成功后才写回答。失败仅写诊断、清理 pending request，UI 解除 busy 后按钮恢复“继续分析回答”。这不是自动磁盘保存。

## 本轮实现范围

1. 保留现有超时/输出预算与正式截断拒收。API 异常携带诊断，M1 workflow 写入真实 partial/raw、usage、停止原因；空用量保持 null。
2. 用独立版本增量提示处理 pending 回答，复用原 Schema 的字段形状。程序仅在增量模式恢复省略的旧缺口和旧冲突，再跑原严格语义/状态检查；完整模式历史保护不放宽。显式返回旧冲突却遗漏参与方仍拒绝。
3. 根据已保存的 M1 失败记录显示“精简重试本轮”，由用户单击发起一次请求。没有后台循环，也不设置失败后永久无法继续的硬锁。任务版本变化或成功应用后旧重试建议失效。
4. 分别记录/提示截断、超时、JSON 格式错误、网络错误。补 Tk + 本地 HTTP 的第二轮失败/重试/再失败/保存重开测试。
5. 通过回归、源码与发行检查后，只保留 `dist/PromptSmith.exe` 一个 PromptSmith 发行 EXE，移除旧产品副本；不删除虚拟环境中的 Python 等运行组件。

完成结果、实跑数量、发行指纹及验证边界另见本目录最终修复报告。现状核查不等于修复验收通过。

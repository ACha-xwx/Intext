# 缓存失效排查 · 完整操作手册

> 交给另一个 AI 独立执行。**全文自包含，不需要其他对话上下文。**
> 目标：判定 `api.changqiu.top` 上 Claude Code 桌面端 Fable 5.1 的 `cache_read_input_tokens` 恒为 0 的原因。
>
> **执行者不要是提出问题的本人** —— 他的请求走同一条通道，会污染读数。
> 说明：这套测试会真实产生 API 费用，动手前先确认额度。

---

## 第一部分：背景与已知事实

### 1.1 现象

同一会话（`session_id = 31df12da-de58-47a7-8750-2d1d1f323e31`），连续三条 Fable 5.1 流式请求（北京時間 2026-10-02）：

| # | 时间 | client_request_id | read | creation | body_bytes | 耗时 |
|---|---|---|---|---|---|---|
| A | 17:53:24 | `80db1311-9150-471c-8ea0-eb3ee3ce110e` | 0 | 188,426 | 1,068,768 | 231.5 s |
| B | 17:53:36 | `fb977f75-f3b4-445f-9a75-f846bd80e993` | **188,426** | 1,992 | 1,081,014 | 9.7 s |
| C | 17:53:56 | `466173fe-a799-4d63-989c-34a42d7d4e6d` | 0 | 191,001 | 1,083,432 | 19.0 s |

关键：**A→B 命中，B→C 未命中，间隔仅 3 秒**。5 分钟 TTL 无法解释。

### 1.2 已经在站内日志确认的事实

全部来自 `api.changqiu.top` 网关自身日志（新站，容器 `sub2api-changqiu`）：

1. 三条请求都是 `session_hash = 31df12da-…`、`selected_account_id = 420`、`account_name = ccmax`、`sticky_honored = true`。
2. 网关层的**会话粘性工作正常**：连续几十轮全部钉在 420，无漂移。
3. 17:53 时段内**没有**属于这三条请求的 failover / retry（该时段的 failover 事件都属于 gemini / deepseek 的其他请求）。
4. 站内**只有一个** ccmax 账号（ID 420）。**但号池在 ccmax 内部，网关看不到。**
5. 网关日志**不含**：缓存断点位置、断点前内容摘要、前缀哈希、上游实际账号。数据库 `usage_logs` 同样只有用量与元数据，**没有**这些。

### 1.3 两轮前置探针（已做过，结论要记住）

**第一轮**（固定前缀约 7K token，6 次）：

```
sync-1:  read=0      write=7,220     ← 首次创建
sync-2/3/4: read=7,220  write=0      ← 全部命中
stream-1/2: read=7,220  write=0      ← 流式也命中
```

结论：**网关同步与流式都正确透传 `cache_read_input_tokens`，`read` 字段可信。**

**第二轮**（加大到 26 万 / 41 万 token，流式）：

同样首次创建、后续全部命中。

结论：**"大请求"和"流式"本身不会阻止命中。**

### 1.4 因此剩下的可能（互相排斥的三类）

| 类别 | 含义 | 特征 |
|---|---|---|
| **R 路由类** | ccmax 内部在多账号间轮询，缓存不跨账号共享 | 相同请求**时好时坏** |
| **C 内容类** | 真实请求的前缀/断点每轮都变 | 相同请求**稳定命中**，真实请求稳定不命中 |
| **W 改写类** | 转发过程改写了请求体字节（重新序列化等） | 相同请求稳定命中，真实请求稳定不命中 |

**本手册的目的：先用 3 分钟把 R 排除或确认，再针对 C/W 取证。**

## 第二部分：阶段 A —— 区分路由与内容

### 2.1 原理

发给网关**字节完全相同**的请求，连发 6 次：

- **每次命中** → 路由稳定 → 排除 R，问题在真实请求内容（转阶段 B）
- **时有时无** → 命中 R（路由类），交给 ccmax 管理员
- **一次都不命中** → 与 1.3 的两轮探针矛盾，先检查环境是否变了

### 2.2 操作

```bash
# 1) 指到目标网关
export ANTHROPIC_BASE_URL="https://api.changqiu.top"
export ANTHROPIC_AUTH_TOKEN="<令牌>"

# 2) 用与真实请求同量级的规模（约 25.9 万 token，贴近真实的 108 万字节）
export PREFIX_MULT=23000
export PROBE_ITERATIONS=6
export PROBE_MODEL=claude-fable-5-1
export PROBE_STREAM=1

# 3) 跑
python tmp/cache_probe.py
```

可选环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `PREFIX_MULT` | 400 | 400≈4.5K token；**23000≈25.9 万 token**（贴近真实） |
| `PROBE_ITERATIONS` | 6 | 请求次数 |
| `PROBE_STREAM` | 1 | `0` 用非流式 |
| `PROBE_AUTH` | bearer | `bearer` / `x-api-key` / `both` |
| `PROBE_GAP_SECONDS` | 3 | 请求间隔 |
| `PROBE_RUN_ID` | 自动 | 本轮的标记，会写进 `metadata.user_id`，便于在网关日志里定位 |

### 2.3 产出

- `cache_probe_out/<RUN_ID>_{01..06}.raw.txt` —— 每条请求的原始响应
- `cache_probe_out/<RUN_ID>_summary.json` —— 结构化汇总
- 终端最后打印**判定结论**

### 2.4 成本提醒

`PREFIX_MULT=23000` 时每次约 25.9 万输入 token。6 次的总量显著（首次写入按 1.25 倍计）。
**想省钱可只跑 3 次**（`PROBE_ITERATIONS=3`）——判定只需要"第 2、3 次是否命中"。

### 2.5 判定 → 分支

| 阶段 A 结果 | 结论 | 去哪 |
|---|---|---|
| 第 2–6 次**全部命中** | 排除路由类，问题在真实请求 | **阶段 B** |
| **部分命中** | 路由/账号切换 | **跳阶段 C**（不用做 B） |
| **全不命中** | 与前置探针矛盾 | 检查 `base_url`、模型名、是否有中间层改写 |

## 第三部分：阶段 B —— 抓真实请求体并 diff

> 仅在阶段 A「全部命中」时执行。

### 3.1 原理

小前缀探针命中，说明网关机制正常；真实请求不命中，说明真实请求里有东西在变。
唯一能定位的方法是**把相邻两轮的真实请求体原样抓下来，逐字节 diff**。

### 3.2 操作

**步骤 1：启动透传代理**

```bash
export UPSTREAM="https://api.changqiu.top"
export PROXY_PORT=8787
python tmp/capture_proxy.py
```

代理把上行请求体原样落盘到 `cache_capture/`，同时逐块透传响应（不破坏流式）。**只落请求体，不落令牌。**

**步骤 2：把客户端指向代理**

桌面端经 CC Switch 注入端点（配置项 `inferenceGatewayBaseUrl`）。把该值临时改成：

```
http://127.0.0.1:8787
```

> 注意：桌面端不走 `ANTHROPIC_BASE_URL` 环境变量，是用 `~/AppData/Local/Claude-3p/configLibrary/*.json` 里的 `inferenceGatewayBaseUrl` 注入的。改完需要重启客户端。
> 若在命令行环境测试，直接 `export ANTHROPIC_BASE_URL=http://127.0.0.1:8787` 即可。

**步骤 3：正常使用 3–5 轮**

每轮说一句不同的话，让前缀有机会命中。**至少 2 轮。**

**步骤 4：分析**

```bash
python tmp/diff_bodies.py
```

### 3.3 产出与判读

`diff_bodies.py` 会报告相邻两轮的：**公共前缀长度**、**首个差异位置及上下文**、**具体哪个顶层字段在变**、以及最后一个请求体里 `cache_control` 断点的位置。

| 观察 | 结论 |
|---|---|
| 首差**落在新消息处**（`messages` 末尾），系统提示段完全相同 | 前缀稳定 → 查断点位置或转发改写 |
| 首差**落在系统提示 / 工具定义里** | 有个变量每轮在变 → 看 3.4 清单 |
| 首差**落在 `tools` 顺序或内容** | 工具清单不稳定 |
| 连续两轮请求体**完全相同**却仍 `read=0` | **转发层改写了字节** 或走了不同上游 |

### 3.4 重点排查：断点之前的变化源

按出现频率排：

1. **当前时间 / 日期**（"Today's date is …"）
2. 会话 ID、请求 ID
3. 工作目录、git 分支、git status
4. 文件清单 / 目录树（每轮重新扫描）
5. 工具列表顺序（动态加载的 MCP 工具）
6. JSON 键序不固定（重新序列化）

**这些只要出现在第一个 `cache_control` 断点之前，后面整段作废。**

### 3.5 额外注意：网关自身的改写开关

站内网关二进制里发现一批**默认开启**的请求改写开关：

| 开关 | 默认值 | 作用 |
|---|---|---|
| `enable_client_dateline_normalization` | **开** | 改写系统提示里的 "Today's date is …" |
| `enable_claude_oauth_system_prompt_injection` | **开** | 注入仿 Claude Code 的 system 块 |
| `enable_identity_patch` | **开** | 身份补丁 |
| `enable_fingerprint_unification` | **开** | 统一 `X-Stainless-*` 头 |
| `enable_metadata_passthrough` | 关 | 提示原文："May improve upstream cache hit rates" |
| `rewrite_message_cache_control` | 关 | 开启后剥离客户端断点 |
| `enable_anthropic_cache_ttl_1h_injection` | 关 | 强制 1h TTL |

**最可疑的一条**：注入的 system 块里有一项 `billing_header`，其说明原文写着 **"stays dynamic per request"**（每次请求都变）。若它落在断点之前，前缀每轮作废——与现象吻合。

**这一步只做记录，不要改开关**（用户要求只读）。

## 第四部分：阶段 C —— 交给 ccmax 管理员的核查清单

> 命中路由类（阶段 A 部分命中）时直接跳到这里。

请按这三个时间点核对（北京时间 2026-10-02）：

| # | 时间 | client_request_id | 站内 read / creation |
|---|---|---|---|
| A | 17:53:24 | `80db1311-9150-471c-8ea0-eb3ee3ce110e` | 0 / 188426 |
| B | 17:53:36 | `fb977f75-f3b4-445f-9a75-f846bd80e993` | 188426 / 1992 |
| C | 17:53:56 | `466173fe-a799-4d63-989c-34a42d7d4e6d` | 0 / 191001 |

**要问的问题：**

1. 这三条在 ccmax 内部分别落在**哪个实际上游账号**？重点：**B 与 C 是否同一个**。若是同一个，"账号轮询"解释即被排除。
2. B 与 C 转发出去的请求体是否**逐字节相同**（除末尾新增）？若被改写，改了什么？
3. 上游返回的原始 `usage` 里，这三条的 `cache_read_input_tokens` / `cache_creation_input_tokens` 各是多少？（用于确认站内记录没记错）
4. B 写入的缓存在 C 到达时**是否还存在于上游**？有无清理/驱逐/分片逻辑？
5. A 耗时 231 秒（正常 10–20 秒）期间，缓存是否被中断或重写？
6. ccmax 是否对 Anthropic 请求做过 `cache_control` 改写、断点重排或 TTL 强制？

## 第六部分：明确区分「已观察到」与「推断」

回报时必须保持这个区分：

**已观察到**（日志直接支持）：
- 三条请求同一会话、同一站内账号、串行、无网关层故障转移
- A→B 命中、B→C 不命中，间隔 3 秒
- A 耗时 231.5 秒
- 网关日志不含断点位置、内容摘要、前缀哈希

**推断**（证据支持但未证实）：
- B→C 内容几乎相同（191,001 ≈ 190,418 + 583）却完全未命中，更像**缓存查找/路由层**问题，而非"内容变了"
- A 的 231 秒可能相关，但**不能**解释 3 秒后的 C 失败

**盲区**：
- **站内 `account_id = 420` 相同，不能证明 ccmax 内部用的是同一个上游账号。** 号池在 ccmax 那层，站内看不到
- 现有证据**无法**区分"ccmax 内部轮询"和"转发改写了字节"

> 特别提醒：不要因为站内账号都是 420 就宣称 ccmax 实际上游账号相同。这不成立。

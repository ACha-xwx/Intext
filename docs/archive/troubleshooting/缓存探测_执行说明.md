# 判定缓存读取恒为 0 的原因：执行说明

> 交给另一个 AI/人执行。本文自包含，不需要其他上下文。
> **不要由提出问题的那个人执行** —— 他的请求会进入同一条通道，污染读数。

## 背景（一句话）

某网关的监控面板显示 `claude-fable-5-1` 的缓存**读取**恒为 0，且每轮请求都表现为**全量写入**；而 `claude-sonnet-5` 在同一时间读取正常（74–88K）。需要判定这是"真的没命中"还是"网关没把读取量记下来"。

## 为什么不能看监控面板

面板就是被怀疑的记账方，用它验证自己不算证据。**唯一判据是响应 `usage` 里的原始字段：**

| 字段 | 含义 |
|---|---|
| `cache_creation_input_tokens` | 写入缓存的量（约 1.25 倍单价） |
| `cache_read_input_tokens` | **从缓存读取的量（本文核心指标）** |
| `input_tokens` | 未命中、按原价计费的量 |

## 为什么发 6 次而不是 2 次

若网关在**多个上游账号间轮询**，缓存不跨账号共享。发 2 次可能恰好落到不同账号，得到假的"没命中"。重复序列能从**读数模式**直接区分三种情况。

## 执行

```bash
export ANTHROPIC_BASE_URL="<网关地址>"
export ANTHROPIC_AUTH_TOKEN="<令牌>"
export PROBE_MODEL="claude-fable-5-1"      # 可选
export PROBE_AUTH="bearer"                  # bearer | x-api-key | both
python tmp/cache_probe.py
```

脚本：**6 个字节完全相同**的请求（4 次同步 + 2 次流式），纯 ASCII 常量前缀约 4K token，带一个 `cache_control` 断点。只读环境变量，不写配置，不回显令牌。

**成本提醒**：6 次请求，各约 4K 前缀 token。先确认额度。

## 判定表

| 同步第 2–4 次的 read | 结论 | 修哪里 |
|---|---|---|
| **全部 > 0** | 缓存机制正常。问题在**真实业务请求**的前缀结构或路由 | 转做「第二步」 |
| **时有时无**（0 与大值交替） | **账号轮询**，缓存不共享 | 让网关方做请求粘性/固定账号 |
| **全部 = 0** 且 write 仍是全量 | 纯常量前缀都不命中 | 见下方「若全部为 0」 |

**若全部为 0**，还要看流式那两次：

- 流式 read > 0 而同步全 0 → **面板的同步列漏记**，不是缓存问题。
- 流式也全 0 → 真的没命中，或网关从不透传读取量。此时让网关方核对：转发时是否重写了请求体字节（重新序列化 JSON 会改变字节序，导致永不命中）。

## 第二步（仅当同步 read 全部 > 0 时执行）

说明缓存本身没问题，那么要抓**真实业务的请求体**。做法：在客户端与网关之间加一个本地透传代理，把每轮请求体原样落盘，然后 diff 相邻两轮，找出**哪个字节在变**。

重点怀疑 `cache_control` 断点**之前**的内容：当前时间、会话 ID、工作目录、git 状态、文件清单、工具列表。这类客户端最容易中招 —— 加在末尾的新消息本身**不会**导致重算。

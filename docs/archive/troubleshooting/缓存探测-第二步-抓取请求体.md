# 第二步：定位真实请求中导致缓存未命中的变化字节

> 交接给另一个 AI/人执行。承接「第一步」已完成的小前缀探针结论。
> **不要由提出问题的那个人执行** —— 他的请求会进入同一条通道，污染读数。

## 第一步已经确认的事

新站 `api.changqiu.top` 用固定前缀探测：sync-1 创建 7,220 token，之后 5 次（含 2 次流式）**全部命中** 7,220。

**因此：网关的缓存读写和流式用量透传都正常，`read` 字段可信。** 之前"面板把流式读取漏记"的猜测不成立，可以作废。

第一步的边界（必须承认）：探针只验证了**固定的小请求**。真实请求的前缀更长、断点更多、可能走上游不同的路由，探针通过不等于真实请求通过。

## 现在能确定的推论

真实面板数据：**每一轮** `read = 0`、`write ≈ 总量`。

缓存是**前缀匹配**：在末尾追加新消息**不会**让前面的内容失效。所以正常情况应该看到 `read` 很大、`write` 只有新增的一小块。

而 `read` **每一轮都恰好为 0**，只有一个解释：

> **第一个缓存断点就没有命中。**

如果变化发生在对话中段，前面的断点仍会命中，`read` 应该是正数。`read ≡ 0` 说明**从第一个断点起整段作废**。而第一个断点覆盖的是**系统提示 + 工具定义**——变化源就在这一段里。

## 站点歧义已排除

出现 `read=0 / write=261K` 的面板数据，**与第一步的探针是同一个站 `api.changqiu.top`**（已经确认）。

因此：

| | 前缀 | 结果 |
|---|---|---|
| 探测脚本 | 固定 7,220 token | 5 次全部命中 |
| 真实流量 | 261K–268K | 每轮 `read=0` |

**同一网关、同一时间，小请求命中、大请求全不命中。** 网关本身排除，差异只在请求内容。

### 但在装代理之前，先做这个 5 分钟测试

探针最大只到约 7K token，真实请求是 261K。**网关有可能按请求大小路由到不同的上游池**（大请求走另一组账号）。这个假设不必装代理就能证伪——把探针前缀调大重跑：

```bash
export PREFIX_MULT=23000        # 约 258,765 token，与真实请求 261,500 同量级
python tmp/cache_probe.py
```

| 结果 | 结论 | 下一步 |
|---|---|---|
| sync-2 仍命中（read ≈ 258K） | 大请求也能命中 → **是前缀内容不稳定** | 装代理做 diff（下面） |
| sync-2 的 read=0、write 仍是全量 | 大请求不命中 → **网关按规模路由到不同上游池** | 直接找网关方，不用做 diff |
| 报错或超时 | 网关对大请求有限制 | 记录状态码，找网关方 |

这一步的性价比最高：**它把"前缀问题"和"路由问题"直接分开**，而这两个的修法完全不同。

> 成本提醒：`PREFIX_MULT=23000` 时 6 次请求各约 258K 输入 token，费用明显高于第一次。先确认额度，也可以只跑前 3 次（把流式那两发注释掉）。

## 决定性测试：抓真实请求体并 diff

小前缀探针已经把网关洗清了，只剩真实请求。唯一能一锤定音的是**相邻两轮请求体的 diff**——直接看哪个字节在漂。

### 1. 启动抓取代理

```bash
export UPSTREAM="https://api.changqiu.top"
python tmp/capture_proxy.py
```

代理监听 `http://127.0.0.1:8787`，把上行请求体原样落盘到 `cache_capture/`，同时逐块透传响应（不破坏流式）。**只落请求体，不落令牌。**

### 2. 把客户端指向代理

```bash
export ANTHROPIC_BASE_URL="http://127.0.0.1:8787"
```

然后**正常用 3–5 轮**（每轮说一句不同的话）。至少要有 2 轮，让前缀有机会命中。

### 3. 分析

```bash
python tmp/diff_bodies.py
```

它会报告：相邻两轮的**公共前缀长度**、**首个差异位置及其上下文**、**具体是哪个顶层字段在变**，以及最后一个请求体里 `cache_control` 断点打在哪。

## 怎么读结果

| 观察 | 结论 | 处理 |
|---|---|---|
| 首差**落在新消息处**（`messages` 末尾），系统提示段完全相同 | 前缀稳定，问题在断点位置或路由 | 检查断点是否打得太靠后 |
| 首差**落在系统提示 / 工具定义里** | 有个变量在每轮变化 | 按下面清单排查 |
| 首差**落在 `tools` 顺序或内容** | 工具清单不稳定 | 固定工具顺序 |
| 连续两轮请求体**完全相同**却仍 `read=0` | 转发层改写了字节或走了不同上游 | 让网关方核对转发是否重新序列化 |

## 重点排查：断点之前有没有变化的内容

按出现频率排：

1. **当前时间 / 日期**（最常见）
2. **会话 ID、请求 ID**
3. **工作目录、git 分支、git status**（编码类客户端高频）
4. **文件清单 / 目录树**（每轮重新扫描，只要有一个文件变动就整段变）
5. **工具列表**（动态加载的 MCP 工具按不同顺序序列化）
6. **JSON 键序不固定**（重新序列化会改变字节序）

这些只要出现在**第一个 `cache_control` 断点之前**，就会让后面整段作废。

## 修法方向（拿到 diff 后再定）

原则：**把稳定内容放在前面、易变内容放在断点之后。**

- 系统提示拆成两段：**固定部分** + **动态部分**（时间、git、环境），断点打在固定部分之后、动态部分之前。
- 工具定义按**固定顺序**输出，且不因每轮环境变化而增删。
- 动态的环境信息（cwd、git status）改用**对话中段的 system 消息**追加，不塞回系统提示开头。

## 需要回报的内容

- 澄清：面板数据来自哪个站。
- `diff_bodies.py` 的完整输出（**首差位置 + 命中字段**是关键）。
- 最后一个请求体里 `cache_control` 的断点位置。
- 若两轮请求体完全相同却仍 `read=0`，贴出两轮各自的 `usage`。

**不要粘贴令牌**；请求体里若含密钥，回报前先删掉。

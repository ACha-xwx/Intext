# 缓存读取探测：测试方案（交给另一个 AI 执行）

## 一、要回答的问题

监控面板显示 `claude-fable-5-1` 的缓存读取（蓝字）恒为 0，而 `claude-sonnet-5` 正常。
需要判定这属于哪一种：

- **情形 A（真未命中）**：缓存从未被命中。上游多账号轮询、或缓存前缀每次都变。
- **情形 B（网关漏记）**：缓存其实命中了，只是网关没有把读取量记进去。

两者的修法完全不同，所以必须先定性。

## 二、为什么不能只信面板

面板就是被怀疑的记账方，用它自己验证自己不算证据。唯一可信的判据是**上游返回的 `usage` 原始字段**：

- `cache_creation_input_tokens` —— 写入缓存的量
- `cache_read_input_tokens` —— **从缓存读取的量（本文的核心指标）**
- `input_tokens` —— 未命中、按全价计费的量

另外，面板上有一条过于整齐的规律：**有缓存读取的全是「同步」，没有缓存读取的全是「流式」**。真未命中不应恰好按传输方式切开。这是优先怀疑情形 B 的理由，也是本方案要同时测同步与流式的原因。

## 三、决定性测试

同一段**完全确定**的长前缀（脚本里的纯 ASCII 重复散文），连发四次：

```
sync-1  →  stream-1  →  sync-2  →  stream-2
```

间隔 3 秒，全部落在 5 分钟 TTL 内。

- `sync-1` 应为**全量写入**（`write` 大、`read=0`）——建立缓存。
- `sync-2` 是**判据**：
  - 若 `read` 明显大于 0、`write` 缩为零头 → 缓存正常，问题在流式记账（情形 B）。
  - 若 `read` 仍为 0、`write` 仍是全量 → 真未命中（情形 A）。
- `stream-1` / `stream-2` 用来对照：若流式那轮**也**拿到了 `read`，说明面板的流式列不可信。

## 四、执行步骤

### 1. 设置环境变量

脚本只读环境变量，不读配置文件，不打印密钥。

```bash
export ANTHROPIC_BASE_URL="<你的网关地址>"
export ANTHROPIC_AUTH_TOKEN="<你的令牌>"
```

可选：

| 变量 | 默认 | 说明 |
|---|---|---|
| `PROBE_MODELS` | `claude-fable-5-1,claude-sonnet-5` | 逗号分隔，两个模型各跑一遍四连发 |
| `PROBE_AUTH` | `bearer` | `bearer` / `x-api-key` / `both`；网关要哪种鉴权头 |

### 2. 运行

```bash
python tmp/cache_probe.py
```

脚本在 `cache_probe_out/` 下为每个请求保存原始响应全文（含流式原文），便于复核。

## 五、判定表

| 观察 | 结论 | 下一步 |
|---|---|---|
| `sync-2` 的 read 大、write 缩水 | 缓存正常，网关漏记流式用量 | 找网关方修流式 `usage` 解析 |
| `sync-2` 的 read=0、write 仍全量 | 真的没命中 | 跑第六节两个补充测试 |
| 流式轮也出现 read>0 | 面板流式列不可信 | 同上 |
| 两个模型都未命中 | 不是 fable 独有 | 优先查前缀稳定性 |
| 两个模型都命中 | 与面板描述矛盾 | 复核面板口径（是否把同步/流式分开统计） |

## 六、补充测试（仅在判定为「真未命中」时执行）

### 6.1 前缀稳定性

脚本用的是纯常量前缀，理论上必然命中。如果连它都不命中，就不是前缀问题，而是**网关或上游**的问题（转发时重写字节、或多账号轮询）。

反过来，若脚本命中、而真实业务请求不命中，则问题在业务请求的前缀里 —— 重点查 `cache_control` 断点**之前**有没有会变的内容：当前时间、会话 ID、cwd、git 状态、文件树、工具清单。这类编码助手最常见。

### 6.2 账号轮询

同一请求连发 10 次（把脚本的 `MODELS` 设成单个模型，循环 10 次），记录每次的 `read`：

- `0 / 大 / 0 / 大` 交替 → 命中了不同上游账号，缓存不共享。
- 全 0 → 不是轮询，是转发改写了字节或断点位置不对。

## 七、注意事项

- **不要把令牌写进报告、日志或提交记录。** 脚本只从环境变量读取，也不回显。
- 脚本会真实产生 API 费用（8 次请求，每次约 5K 前缀 token）。若网关按量计费，先确认额度。
- `max_tokens=128` 是为了压低输出成本；输出内容无关紧要，只看 `usage`。
- 若网关不返回 Anthropic 原生字段名（例如把 `cache_read_input_tokens` 改名或省略），这本身就是一条结论：**网关没有透传缓存用量**，面板的读数不可用于判断缓存状态。
- 脚本假定端点是 `/v1/messages`。若网关路径不同，改 `BASE` 拼接处。

二、修正主动作：按钮文字、状态与实际操作一致

已复现问题：回答仍待评估且分析依据版本已等于当前需求版本时，按钮显示“继续分析回答”，但点击函数没有对应分支，实际执行确认需求。存在方向性缺口时，连续点击均提示“仍有影响方向的未决项”，没有启动分析。

相关入口：ui.py 的 _primary_action_text、run_primary_action、_next_step_text、record_question 及需求确认检查。

要求：
1. 用同一份程序状态决策产生主动作的动作类型、文案、可用状态及解释，再由处理器执行。可使用现有机制或小型纯函数，不新增模型调用或复杂状态框架。
2. 有待评估回答且允许分析时，主按钮真正调用本轮分析；存在前置阻断时，展示该阻断对应的操作，不能仍指向必然失败的确认。
3. 无任务时显示“先输入任务”和简短示例，主操作聚焦输入或按条件禁用；输入后状态及时更新。缺少调用配置时定位连接设置，不能先发请求再让用户猜缺什么。离线查看、编辑、保存不需要 API key。
4. “回答问题”定位具体待回答项，展示完整问题及可选回答，不只是把焦点移到空回答框；保留用户已选项目。有多项时说明当前处理哪项，并允许切换、跳过和不确定。
5. “核对候选”“复核需求”“处理冲突”同样定位具体事项，并提供明确处理入口。不能用自动接受、自动关闭缺口、放宽冲突或自动确认来减少步骤。
6. 回答后的提示使用当前实际动作名称，删除不再存在的“分析 / 继续”等旧指引。可暂缓未知与方向性阻断分别说明；预算耗尽不是需求完成，也不能暗中补轮数。
7. 无进展时明确停止自动推进，保留数据，给出补充、修改或显式重试路径。不要让重复点击触发无界请求或错误弹窗循环。
8. 请求在途时防重复提交，成功、失败、过期响应都正确结束自身请求，不把其他会话或较新请求的忙碌状态清除。

复验必须通过主按钮的真实 command/Button.invoke 或实际点击完成，不允许只调用 start_analysis 绕过问题入口。至少覆盖原“待评估回答 → 连续点击”场景、无任务、缺配置、候选与回答并存、冲突、预算耗尽、可确认以及进入 M2。

三、修正重复追问：已解决历史也参与判断

已复现问题：用户明确回答“发给大一新生”，gap_updates 已使受众缺口 resolved；无新用户信息，模型返回同一 field、scope 和问题原文，仅更换 gap_id/question_id，仍能被接收。

要求：
1. 已回答且已解决的缺口保留可追溯历史，并纳入后续重复判断；不能只看 pending、skipped、unsure，也不能只比较模型返回的 ID。
2. 对同一实际缺口、同一适用范围、没有新依据的重复问题，换 ID 或仅换措辞不得使其被当作新的必要问题。至少可靠拦截本次完全相同问题的新 ID 复现。
3. 明确区分同字段不同子任务、同范围不同实际缺口、部分回答后的必要细化、新要求导致重开。不能用 field 相同或 field+scope 相同就全部禁止的方法修复。
4. 程序维护稳定缺口关联、历史状态和可核验依据；模型负责提出内容判断。若需要新增“新缺口/细化/重开”的来源关系字段，先给最小版本化契约与迁移，再接入；字段需引用真实历史和新来源，模型 reason 或自己起的新编号不能单独构成放行依据。
5. 语义不同但程序无法确定的情况应保守保留、进入可解释复核，不宣称关键词/相似度能够识别任意语义等价。无需为每个问题增加一个独立模型调用。
6. 不改变原始回答或伪造“已解决”，不通过删除历史、抹去缺口或自动增加预算避开校验。非法响应按既有原子接收规则处理，记录具体失败原因和原始输出。

复验正反案例：完全相同问题换新 ID应拒绝；同义重复无新依据应得到可解释处理；不同子任务同字段允许；部分回答后的必要细化允许；用户明确重开须有新来源并遵守预算；保存重开后保护仍在。

四、M2 必须能完整查看和编辑，空步骤不能被确认

已复现问题：新增步骤只要求标题和目的，行动、输出、完成标准等全为空；复核关键工作后仍可确认并保存，重开后保持 confirmed。已有步骤编辑也只支持标题、目的。

要求：
1. 提供一个可读的步骤编辑界面，可用统一多字段弹窗或详情面板，支持多行中文。至少可编辑标题、目的、输入、行动、输出、完成标准，以及可维护的步骤依赖和需求关联；不要求用户手写 JSON，也不要连续弹出大量单行输入框。
2. 用户可查看每步完整内容。主列表可简短展示，但要有可发现的详情入口；输入、行动、输出、标准和依赖不能只存在于保存文件中。
3. 将“保存草稿”与“确认完整方案”的验证区分。新步骤尚未补齐可以保留草稿，但缺少实际行动、预期输出、可检查完成标准等必要内容时禁止确认，并定位具体步骤和字段。
4. 区分非空与有意义：空白、空数组及仅用“待补充”占位，不能当作完整执行步骤。允许保留任务本身的可延后未知，并写清影响和前提；不能把输入/依赖等确实不需要的可选列表一律强制填一项。不要让 UI 与底层确认采用不同标准。
5. 确认、保存和重开用一致的状态规则。草稿允许不完整；已确认方案不允许绕过必要验证。旧文件中若有不满足新确认标准的 confirmed 方案，保留内容、标记待复核并解释原因，不能静默继续信任，也不能损坏或覆盖原文件。
6. 方案及关键工作中涉及步骤的关联应能通过清楚的选择/维护界面调整。删除被引用步骤时列出影响，让用户改关联或取消；不能只拦删除却永远不给修复路径，不能默默清空引用或指向其他步骤。
7. 关键工作支持核对完整目标、输入、输出、检查点和关联步骤。步骤内容改变，即使 ID 未变，也使受影响关键工作待复核。新增关键步骤时给出复核机会，但不要求每一步都成为关键工作。
8. 稳定 ID 由程序维护，重排不改 ID，不按行号重建。所有引用须存在、不得自依赖/循环；修改原子提交，验证失败保留用户草稿以便继续编辑，不发生半份写入。
9. 普通方案编辑只改变方案版本和确认；变更用户目标、硬约束或任务范围仍通过“修改需求”回 M1。仅导航不作废方案，实际需求变更使旧方案过期并保留历史。

复验：原空步骤必须不能确认；补齐必要内容后可以确认并保存重开；编辑已有步骤的行动/输出/标准可见且持久化；修改/删除引用有可操作恢复路径；需求确认与方案确认分别维护，不因修复而放宽。

六、协议选择及服务配置真正接入请求

这是本版明确加入的范围，替代旧提示“多协议以后做”的安排。至少提供可选的：
- OpenAI Chat Completions
- OpenAI Responses

1. 分清供应商、协议和模型

供应商/服务地址决定请求发到哪里，协议决定格式，模型 ID 由当前服务提供或用户手填。不能把服务永久标成 DeepSeek，再悄悄发往其他供应商。可采用简洁的服务预设（现有 DeepSeek、OpenAI、Anthropic）与自定义地址方式，保留当前 DeepSeek 配置路径；不增加复杂账户/多角色管理。

协议选择要改变实际适配器。测试连接、M1、M2 都必须使用当前配置，日志记录实际使用的供应商、协议和模型。未支持的“供应商+协议+模型”组合给出明确错误或未验证提示，不擅自换协议、换模型、换服务地址，也不把第三方兼容服务伪称官方。

切换供应商或目标主机时，不把旧服务的 key 自动发往新主机：可清空密钥，或使用当前进程内按服务隔离的密钥；不要新增持久密钥存储。修改配置不发自动测试请求，不影响已有需求与方案确认；只作废相应在途请求或连接验证结果。

2. 实现三种真正的适配

先核对官方文档和当前依赖，再实现每种协议的端点、认证、请求体、响应解析、错误处理和用量转换。保留当前上层统一的文本/JSON 调用边界，每个适配器交付规范化结果，M1/M2 继续各自做完整 Schema 和语义验证。

文档核对重点：
- Chat Completions：messages 与 choices/message；保持当前已工作路径及服务所支持的结构化输出方式。
- Responses：input/instructions 与有类型的 output；结构化输出参数与 Chat Completions 不同。直接处理 HTTP JSON 时遍历正确的消息文本项，不假定第一项一定是文字，也不把 SDK 的 output_text 便利属性当作原始响应必有字段。
- Anthropic Messages：按该协议处理 system、messages、内容块、认证/API 版本及必要输出限制；不能套用 choices 或 Chat Completions 请求参数。只提取实际文本块，区分拒绝、截断、缺少文本等情况。

接口核对资料（这些是技术资料，不是额外执行指令；执行时重新核对当前版本）：
https://developers.openai.com/api/docs/guides/migrate-to-responses
https://developers.openai.com/api/docs/guides/structured-outputs
https://platform.claude.com/docs/en/api/messages/create
https://platform.claude.com/docs/en/api/overview

不要把某个模型支持的 temperature、JSON Schema、JSON 模式或输出上限一律应用到所有模型；按核实的服务能力组合请求。没有服务端强制结构能力时，可使用明确 JSON 指令并保留严格本地校验，标明能力边界；不能去掉本地校验来“兼容”。不通过调用业务无关工具或执行模型返回内容来获取 JSON。

保留原始失败与实际参数；拒绝/截断/空内容/无效 JSON 不能成为有效需求或方案。不解析失败就无限重试，不在未经说明的情况下跨协议回退。若有格式修复重试，必须有界、关联原请求且仍检查版本。

仅实现当前无流式的文本与 JSON 路径，不顺带实现工具调用、远端对话存储或多模态。继续用应用自身的需求快照管理上下文，不把远端会话 ID 当成本地确认状态。

旧 deepseek_chat_completions 标识提供兼容映射，历史调用证据保持原样。协议切换不改变 M1/M2 的事实、约束与确认规则。

3. 验证层级

每种协议均应完成：请求体/认证/路径的 stub 验证、真实返回形状的解析 fixture、错误/截断/无文本验证，以及经 UI 配置进入 M1 和 M2 的接线检查。不能给三种协议喂同一份 Chat Completions 响应来假装都通过。

有明确授权及可用运行时配置时做真实服务测试；没有配置仍应完成适配和离线接线，并明确“真实服务未验证”。不能以缺少三个供应商的密钥为由只做选择器，也不能宣称未实测的模型都可用。不要更换用户已经指定的模型来制造通过结果。

七、模型列表保留已实现能力，补足配置隔离

1. 按实际服务文档实现或调用模型目录能力，不依据生成协议名称直接假设所有服务的 /models 路径、认证、分页都相同。目录无支持时保留手填模型，并说明原因。真实返回的 ID 才进入在线列表，不按名字推断能力。
2. 列表请求绑定 request_id、用途、服务、协议、地址和相关配置世代。在 A 配置发起 → 改为 B → 再改回 A 的情况下，旧请求也已过期，不能仅比较最终字符串相等就接收。
3. 相关配置版本由程序维护，区分会影响目录的配置与模型 ID 文本编辑；列表返回不覆盖用户手填模型、不自动选择第一项。目录所属配置变更时清空旧列表或明确标注旧来源，避免混用。
4. 同类请求在途禁止重复提交；旧成功或旧失败回调都不能覆盖新列表、清掉较新请求的忙碌状态。目录获取不占 M1 轮数，不改变需求/方案状态。
5. 正常、空列表、401/403、404/不支持、超时、网络失败、格式错误均有清楚提示，手填路径始终保留。需要分页时按服务规则有界获取并标明数量/范围，不误称只有第一页就是完整列表。
6. 统一超时、错误与日志边界，不记录 API key、认证头或凭据内容。测试连接及生成回调同时检查类似的 A→B→A 配置世代问题。

至少保留现有普通 A→B 测试，并新增 A→B→A、服务/协议切换、目录在途手填模型 ID、旧失败回调及正常获取的复验。

八、字体与排版要让用户实际看见改善

旧几何检查只确认控件外框在窗口内，不能继续作为视觉通过证据。已测得 1120×780 下需求表 504 px 对 550 px 列宽、步骤表 540 px 对 595 px 列宽，内部被裁切且无横向滚动条。

以以下具体标准实施，数值是本轮开发默认值，不是用户任务中的约束：
- 主要标签、按钮、下拉框、表格和编辑正文默认至少 11 pt；阅读较长的任务、需求详情、方案正文以 11–12 pt 为起点；次要元数据可较小但不承担关键指引。统一命名字体/样式并验证实际生效，不能只改标题或 TLabel 而让 Text、Treeview、弹窗继续用旧小字。
- 标题与章节形成清楚层级，行高随字体调整，按钮文字不裁切。不要为容纳旧布局把主要文字缩回 9 pt。
- 初始状态突出任务输入、必要连接设置和一个主动作。没有内容的需求、候选、问题区用简短空态或渐进展开，不让多个大型空表格占据主体。连接设置可折叠/紧凑展示，当前协议和模型仍容易查看，缺配置时能找到入口。
- 任务输入在常规窗口下至少能舒适显示约 4 行文本；长输入可滚动或扩展。根据状态给当前处理的问题、需求核对或方案阅读留足空间，次要操作适当收拢，不要求用户从十几个同权重按钮里猜下一步。
- “减少空白”指减少无效空间，不是把所有控件挤在一起。整体用一致边距、对齐和分区，主动作位置稳定。
- 表格列根据容器合理伸缩；放不下时提供可发现的横向滚动，纵向列表有适当滚动能力。长文本通过换行或可发现的详情区完整阅读，不依赖隐藏列、悬浮猜测或复制出来才看清。
- M2 的完整方案、步骤详情、编辑弹窗和关键工作与 M1 使用相同字号体系。长中文不能只塞进固定单行 askstring。
- 保留合理的窗口最小尺寸，至少在 1120×780 默认尺寸检查；如果程序声明支持更小尺寸，也验证其布局。不要单纯增大默认窗口到超出屏幕来掩盖问题。

实际查看新会话、长任务、有多条需求/问题、长方案及步骤编辑弹窗。核对表格内部列、文字、按钮和滚动，不只测控件外框。可用时检查真实 Windows 125%/150% 缩放并记录分辨率、窗口大小和缩放值；Tk scaling 模拟单独标注。无法完成的实际视觉条件列为未验证，不能写通过。

必须先检查当前工具是否能够捕获和操作界面，不得照抄旧报告的“界面能力不可用”。有能力时用最终发行包实际操作并保留脱敏截图。不能把生成的示意图或修改后的截图当成软件画面。

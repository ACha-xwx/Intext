## 产品理解

帮助用户明确“想做什么”和“什么结果算合适”，保留用户已经说明的要求，支持修改、未知和逐渐形成的标准，输出可编辑、可复用、跨窗口独立可读的方案与提示。

输入任务 → 建议可修改类别并提取信息 → 按依赖追问 → 必要时局部示例反馈（后续） → 用户编辑确认需求 → 完整初始方案 → 用户确认方案 → 识别关键工作 → 已核验目录检索及推荐Skill → 选择或跳过 → 整合最终方案与提示 → 保存导出。下游文本试运行后续增加。

初始方案包含目标、要求、步骤、交付物、完成标准和未决事项；未知可保留，结构必须齐备。无Skill路径必须独立可用。

| M5／已接入，内容待复测 | 难表达的单一标准、相关需求和用户反馈 | v0.2 提示生成局部 A/B；反馈先成为候选，接受后保留用户来源并回到 M1 复核；示例假设不写入正式需求 |

这里的优先级是本窗口的推进顺序，不取消MVP中的末端目录检索与整合。正常有Skill路径为M1 → 用户确认需求 → M2 → 用户确认方案 → B检索／M3 → 用户选择或跳过 → M4。无Skill路径在方案确认后直接进入M4。

M2若把关键工作一起生成，属于降低调用成本的建议，不提前检索Skill。方案经用户编辑后，应复核关键工作与步骤的对应；不能直接用旧草稿启动推荐。

## 程序职责

B维护来源ID、需求卡及版本、确认／撤销事件、问题展示及跳过状态、轮次预算、类别选择、失效传播、迟到响应拒收、保存导出、目录与权限。A实现API请求、严格解析与校验、超时及有限重试、真实用量和错误记录。C展示状态并把用户操作交给B。

模型只能提供内容建议；即便输出说“用户已经确认”，也不能改变状态。用户确认的是特定版本的具体内容。需求变化使下游方案与推荐失效；语气切换应保留需求、方案和Skill内容。材料与Skill说明不取得应用规则权限；M1不暴露安装、执行或外发工具。

接入时B组装可信输入快照，A在一次调用中发送当前静态提示＋输出契约＋输入JSON。A验证返回，B核对真实请求版本后原子接收为候选，C显示差异供用户操作。**模型输出的next_action和readiness都不能直接触发确认、覆盖旧卡或启动下游。**

字段虽多，职责只有三组：B提供请求标识、快照、历史和控制；模型提出内容与引用；A/B校验后交C展示。今晚不删减来源、范围、冲突等关键字段，也不增加任意决策图。是否需要压缩输出，待实际延迟、用量和接线结果再决定。

## 一次迭代怎样执行

1. **确定问题：** 记下失败输入、现象、期望行为；设计矛盾写“设计发现”，模型错误必须附原始输出。先选一例正常与一例相关边界，写判据再改提示。
2. **最小修改：** 保留旧正文，新建递增提示版本；只改能解释该问题的规则。Schema有结构或语义契约变化时另升契约版本，并由A/B决定映射；提示文案变化不自动升Schema。
3. **运行案例：** 先校验输入与人工期望；有明确模型配置时发真实请求。相同输入、模型和参数下比较提示版本；expected只给检查者，绝不随请求发送。
4. **检查结果：** 先看结构、引用、预算、状态边界，再人工看事实保留、推断是否有依据、问题依赖和是否重复。检查器通过不等于语义正确；任何越权确认、硬约束丢失、编造限制或预算绕过均阻止实测验收。
5. **记录差异：** 在本轮检查记录写“旧行为／新规则／实际观察／仍未验证”。未经实测只能说明设计一致性改善，不能写模型效果改善；保留失败和修复调用的原始输出。
6. **决定保留：** 无明显回归且对应设计检查通过，可保留为待实测候选；真实输出满足两例判据后才标“小样本实测通过”。失败则修同一问题或回退旧候选，更新本入口和CHANGELOG；不覆盖旧证据。

## 版本与证据怎么保存

- 提示：`M1_system_v0.1.txt`至`M1_system_v0.7.txt`为历史或未接入版本，`M1_system_v0.8.txt`为当前接入版；旧说明、旧检查保留，不追改成新版本的证据。
- 输入／人工期望：复用`examples/01_*.input.json`、`02_*.input.json`及对应expected；本轮不改它们。今后变更测试条件另存变体，记录父案例和差异，不能为通过而事后改判据。
- 设计检查：当前真实调用、v0.2失败和v0.3复测见[检查记录](<设计检查_v0.3_20260923.md>)；v0.2设计检查和带SHA-256的结果继续保留在原文件及`_checks/`，旧结果不覆盖。
- 真实调用：至少保存实际发送的`input.json`、`system.txt`、`output.schema.json`、未改写的`response.raw.txt`、`meta.json`和`check.json`。当前程序证据在`verification/`及用户本地数据目录；严格解析失败时不美化或修补raw来冒充原始返回。
- `meta.json`记录证据类型`model_response`、模型／供应商、实际参数（含默认或未提供项）、提示／契约版本、请求和任务标识、文件哈希、调用时间、耗时、接口实际用量（缺失填null）、调用状态和失败原因；修复另编号并关联原调用。只存业务响应和必要元数据，不保存凭据或请求鉴权头。
- 未调用时记录`pending`且原始输出不存在；不创建“模拟raw”。人工expected始终标`manual_fixture`。每轮的未解决项留在对应检查记录，本入口只列最近阻塞和下一步，避免新增多套进度文件。

## 一、跳过问题后的统一行为

### 1. 跳过不是解决

用户点击“跳过”时：

- 记录用户确实选择了跳过；
- 保留对应 gap、来源和问题历史；
- 不把未知内容写成用户事实；
- 不让程序进入无法继续的状态；
- 普通细节可标为“稍后补充”，直接显示下一个问题或需求摘要；不额外弹窗、不追加确认步骤；
- 只有任务对象等关键内容仍不明确时，才在同一操作区说明具体缺什么，并提供下述处理方式。

不要让跳过后的问题直接从界面消失而只剩一个抽象的“未决项”。

### 2. 关键问题用一次猜测确认接住，不再原样反复追问

任务对象未知、不能直接写出具体内容时，可以让 AI 结合已知信息提出可能的理解。优先复用本次分析返回的解释；没有可用解释时，跳过操作最多触发一次正常分析请求，并显示“正在根据已有信息整理建议…”。同一未决项已经猜测过且用户仍选择跳过时，不自动再次发问。

例如，在用户已说“数值分析领域”后，可以询问：

> 你可能指 Jacobi 和 Gauss–Seidel 这两种迭代方法，是想讲这两种方法吗？

这是帮助用户识别对象的候选问题，不是声称“JGS”的标准全称已查实；不能把 Jacobi 与 Gauss–Seidel 说成同一个算法，也不能把截图中用户提到的二者关系直接当成已核实的数学事实。若当前模型没有可靠的候选解释，直接说明“我还不能判断具体是哪项内容”，不要硬猜。

提供三个操作：

1. **是这个意思**（存在明确候选解释时）
2. **我来补充**
3. **先做草稿**

按钮含义必须清楚：

- 默认只给一个最可能的解释，确有必要时最多两个；解释和选择放在同一处，不先让用户点“让 AI 猜”再进入新的页面；
- “我来补充”让用户在同一张卡中输入一句话，不要求重新填写整份任务；
- “先做草稿”立即结束对此问题的强制追问，继续整理能确定的部分。涉及未知对象的内容留空或标注待补充，不用猜测填满。

不再要求用户猜测内部的 gap、blocking 或版本含义。

### 3. AI 暂定理解必须可确认

这项能力优先合入现有 M1 分析调用，不另建一个必须依次经过的阶段。除现有结构外，需要承载以下信息；字段命名是建议，开发时应与现有 schema 一起校验和适配：

- 当前未知项 ID；
- 1～2 个候选解释；
- 每个解释的简短依据；
- 支持这一解释的上下文或“依据不足”说明，不生成没有依据的置信百分比；
- 一个继续追问，用来确认“哪个理解更接近”。

模型不能把候选解释直接写入正式用户需求。页面显示为：

> 你可能指的是：……

用户可以：

- **是这个意思**：只确认当前展示的解释，不附带接受隐藏的范围、预算、难度或时限；
- **我来补充**：在原位置输入正确含义；
- **先做草稿**：保留未知，继续完成能做的部分。

整个猜测流程最多增加一次确认，不要连续生成多轮候选，不要自动循环。

用户确认只证明“这是我要讲的对象”，不证明模型解释中的客观知识全都正确。程序记录推测来源与用户选择；问题是否解决应与该选择的范围匹配，不能顺便清除无关缺口。模型失败时仍能补充、先做草稿或保存，不把网络连接变成退出此状态的唯一途径。

### 4. “先做草稿”必须有可交付的出口

“先做草稿”是用户同意暂缺部分信息，不等于确认这些未知内容。优先复用现有草稿和未决事项机制；仅在现有结构不足时新增最少的内部字段，不能把某个新字段名宣布为已存在接口：

- 允许生成需求草稿或初始方案草稿；
- 在相关内容旁显示“待确认：JGS 的具体含义”；
- 允许查看、编辑、保存和导出带明显待补充标记的方案及提示草稿，不得到了下一页又因同一个已选择暂缓的缺口锁死；
- 草稿也包含目标、已知要求、工作步骤、交付物、完成标准和待补充事项；对象不明时，步骤应先核实对象，后写具体讲解，不编造算法、事实或结果；
- 不宣称已完成全部确认。结果页只展示一次清楚的待补充说明，并提供“补充信息”和“导出草稿”；正式确认保持其语义；
- 用户之后补充信息时，相关需求、方案和最终提示按现有版本规则失效并重新生成；
- 不得把待补充内容写成 `user_fact` 或 `confirmed`；可以记录用户允许先做草稿这一决定。

当前 M2、后续 Skill、最终结果与导出都可能有确认门槛，必须沿调用链核对。草稿路径不强制使用 Skill；保持完整初始方案先形成，再进入可选 Skill 的原则。不得通过伪造全部需求已确认来调用 M2；必要时为用户明确选择的草稿路径增加入口校验和来源标记。保存、导出及后续补充应能走通，不能只放开第一个按钮。

### 5. 主按钮必须与真实状态一致

当存在方向性未决项时，主按钮不能再显示“确认当前需求”，也不能点击后才弹出泛化错误。

根据状态只显示一个当前主动作：

- 开始任务：`开始整理`
- 有当前问题：`提交回答`，一次点击完成记录和必要分析，不再要求先“回答”再找“继续分析”
- 当前显示 AI 对关键术语的解释：`是这个意思`，旁边可补充或先做草稿
- 当前显示整理后的需求：`确认需求并生成方案`
- 当前采用草稿路径：`生成草稿`，按钮前说明“还缺 JGS 的具体含义，相关内容会标为待补充”
- 请求失败且回答已保存：`重试分析`
- 正在请求：`正在分析…`（不可重复提交）

主按钮的说明文字要直接说清“点击后会发生什么”。例如：

> 我还不确定 JGS 指什么。可以补充说明，也可以先生成待补充的草稿。

主动作、下一步说明、可用状态和入口校验应来自同一份状态判断，避免各写一套条件。历史会话保存重开后也必须能够识别“问题已跳过、缺口还在”的状态并显示处理入口，不要求用户重新开始。

不再把“增加 2 轮追问”放在主界面。预算保留在程序内部；达到上限后显示已有摘要，用户可主动选择“继续补充”或“先做草稿”。一次补充操作允许有限的新分析，但不能无限循环。不要把“两轮”改名为“两个问题”，这会改变含义。

## 二、把需求页改成单一路径

当前页面的问题是：引导问题在右侧，AI 建议在左下，需求列表在左上，用户需要在多个并列区域之间跳转。请改成一个有明确上下顺序的需求工作区，不要继续堆叠并列面板。

推荐结构如下，具体控件可沿用现有 Tkinter/ttk：

### 顶部：全局阶段和连接设置

- 保留一个全局阶段导航：`1 需求 → 2 方案 → 3 Skill（可选） → 4 结果`；
- 不再同时增加一套“输入、追问、接受、复核、确认”的子步骤导航；
- 当前阶段高亮；
- 模型连接设置默认在首次配置时展开，配置成功后收起到“模型设置”；保留多协议、模型列表、测试连接等功能；
- 每个阶段复用同一个主内容区和固定的底部操作区，完成一个阶段后自动进入下一阶段。顶部不再放第二个主按钮。

### 中部：只显示当前正在处理的内容

页面中央沿纵向使用同一主工作区。任务输入、回答问题、核对需求是这块区域的不同状态，不是三张需要用户来回找的并列表格。已有内容可通过折叠摘要查看，不因折叠而丢失。

内容只包括：

- 一句话说明当前状态；
- 当前问题或待处理未知；
- 回答输入框或 AI 暂定解释；
- 输入框支持直接自由补充，不必先从表格选中问题才能说话；
- 主按钮及少量辅助操作统一放在固定底部操作区，回答或核对完成后不跳到页面另一侧。

不要把这部分放到右侧窄栏，也不要让用户先看需求版本数字才知道该做什么。

### 核对需求：一次查看、一次确认

统一标题为“当前需求”。显示自然语言摘要或简单可编辑列表，AI 整理的新增内容直接在这份预览中标注，不另设“模型候选”工作台。

默认展示：

- 内容；
- 确有必要的“AI 建议”“待补充”标记；
- 编辑入口。完整来源、内部状态和版本放到详情中。

内部版本号可以留在详情或日志中，不要作为用户主要标题。

默认路径是“输入 → 回答少量问题 → 核对一份需求摘要 → 确认需求并生成方案”。禁止把“采用全部建议 → 逐条标记已复核 → 再确认需求”串成普通用户必经步骤。用户点击“确认需求并生成方案”时，程序按该页面实际展示的内容集中记录接受、复核和确认；必须先通过已有约束检查，再提交方案请求。

对于系统猜测的对象或相互冲突的要求，先在同一工作区让用户明确选择，不能藏在一键确认里。其余来自用户明确回答的整理内容可在一次总览确认中处理。高级用户仍可逐条编辑，不要求每个人都逐条点击。

### 可折叠区域：详细记录

把“模型候选”改称为 **“AI 建议”**。不要使用“模型候选”“接受候选”“忽略全部”等机器内部说法。

AI 建议是需求预览中的标记，不是另一个必经阶段。需要逐条操作时可使用：

- `采用这条建议`
- `修改后采用`
- `暂不采用`

详细来源、schema、request ID、运行证据和技术错误放进“查看详细信息”，默认收起。

### 全软件保持相同的操作位置

- 方案页：在主工作区查看和编辑方案，关键工作并入方案展示；底部“确认方案并继续”完成对当前展示方案的集中复核，内部仍验证覆盖与依赖。
- Skill 页：标题保留“Skill（可选）”，只说明“为方案选择可用的方法”。在同一底栏提供“使用所选方法”和“跳过，查看结果”；必须实际跳转，不止改变状态文字。
- 结果页：显示方案与最终提示，提供复制、保存、导出；语气切换和试运行保留但降低视觉权重；草稿状态明确标注。
- 修改已整理的信息后，直接进入“更新后的需求”预览并展示相关变化，原地确认；不要求用户先学习“版本失效”再逐条标记。内部必须保留受影响内容及旧结果历史。
- 默认正文使用清楚易读的系统中文字体，建议 12 pt，标题 16～18 pt、按钮 11～12 pt；以实际 DPI 检查为准。不要把所有面板同时撑成大块空表格。1366×768 和 1920×1080 下，当前问题、输入和主按钮应易于找到；保留现有滚轮、右键和键盘操作。

## 三、统一用户语言

全局检查 UI、弹窗、状态栏、按钮、帮助文本和导出预览，建立一个术语表并统一替换。至少统一为：

| 当前或容易出现的说法 | 统一说法 |
|---|---|
| 需求版本 | 当前需求 |
| 确认当前需求（独立重复按钮） | 确认需求并生成方案（主流程唯一入口） |
| 模型候选 | AI 建议 |
| 接受候选 | 采用这条建议 |
| 忽略全部 | 暂不采用这些建议 |
| 回答 → 继续分析回答 | 提交回答（一次点击记录并分析） |
| 精简重试本轮 | 重试分析 |
| 增加 2 轮追问 | 主界面移除计数；需要时提供“继续补充” |
| 未决项 | 还需要确认 |
| 影响方向的未决项 | 会影响结果方向，还需要确认 |
| blocking_direction | 仅作为内部状态，不能直接展示 |
| 暂不能确认 | 还不能确认需求 |
| 当前请求尚未结束 | 正在处理，请稍候 |
| 标记已复核 | 默认流程合并进需求或方案的集中确认，详情可保留逐项操作 |
| context / deliverable 等字段名 | 背景 / 交付内容等中文标签 |

规则：

- 一种状态只用一种用户称呼；
- 不向用户暴露 gap、版本、schema、pending、blocking 等实现术语；
- 不凭空创造“本轮”“精简重试”等没有上下文的短语；
- 每个按钮都用“动作 + 对象”表达；
- 文案优先使用用户当前脑中已有的词：问题、回答、AI 建议、当前需求、草稿、确认、继续。

错误说明采用“出了什么问题 + 已保留什么 + 现在能做什么”，例如“刚才没有收到完整结果，你的回答已保存。可以重试分析。”不要在主提示里展示 JSON、token、日志目录；详情中保留诊断信息。不要把“精简”机制删掉，只改用户看到的按钮及解释。

上表描述面向用户的语义映射，不是全仓库字符串替换。内部字段、日志和历史记录保留真实含义，技术版本号仍可在详情查看。

## 四、程序状态与模型职责

程序负责：

- 保存用户原话、用户决定、AI 建议和待确认项的来源；
- 判断当前主按钮和阶段；
- 防止重复提交和自动重试循环；
- 在任务修改、候选采用、暂定理解确认后正确使下游内容失效；
- 保存、重开和导出时保留“待确认”标记；
- 防止旧异步响应写入新状态。

模型负责：

- 提取用户新补充的信息；
- 对跳过的未知给出少量、带依据的暂定解释；
- 提出一次确认问题；
- 说明仍不确定的地方。

模型不能：

- 默默替用户决定 JGS 的具体含义；
- 因为用户跳过问题就删掉 gap；
- 将 AI 推测写成用户事实；
- 连续自动追问或自动重试；
- 通过改低重要性绕过程序确认门槛。

## 五、必须覆盖的测试案例

### 案例 A：JGS 跳过后不死锁

输入：`讲一下 JGS`。

1. 首轮提出“产出形式”和“JGS 所指”问题；
2. 用户回答“面向学生的学习讲义”“数值分析领域”；
3. 用户跳过“JGS 具体指什么”；
4. 页面在原位置说明缺少具体所指，并给出一次可能含义的确认；无可靠猜测时直接说明；
5. 用户可以选择“是这个意思”（有候选时）、“我来补充”“先做草稿”；
6. 无论选择哪一项，都能进入下一步或明确回到补充入口；
7. 不允许出现“主按钮建议确认，但点击后才说不能确认”的矛盾。

### 案例 B：接受 AI 暂定理解

AI 给出一个暂定解释；用户点击“是这个意思”；

- 解释被记录为用户确认的决定；
- 来源显示为“用户确认的 AI 建议”；
- 对应含义缺口可以解决，其他未解决问题按其真实状态保留；
- 不产生第二个同义需求；
- 导出内容独立可读。

### 案例 C：拒绝 AI 暂定理解

用户点击“我来补充”，输入一句话纠正解释；

- 原猜测保留在历史中，但不进入有效需求；
- 新补充进入新的分析请求；
- 仍只有一个清楚的下一步；
- 不自动连续调用模型。

### 案例 D：先做草稿

用户选择“先做草稿”；

- 可生成带待确认标记的需求草稿或方案草稿；
- 页面明确显示“JGS 具体含义待确认”；
- 能实际生成、查看、保存和导出草稿，不在 M2 或结果页因为同一个已暂缓缺口再次被拦回原处；
- 缺少对象时不生成具体算法讲解或其他假装已确定的内容；
- 保存后重开，待确认状态不丢失；
- 之后补充 JGS 含义可以重新分析并使相关草稿失效。

### 案例 E：普通无缺口任务

完整需求不应被新流程增加额外页面或额外确认。应保持：开始整理 → 核对一份需求摘要 → 确认需求并生成方案。用户提交回答一次就完成记录和必要分析，不再要求第二次点击“继续分析”。

### 案例 F：文案与布局

用真实 Tk 界面检查：

- 首屏能看到当前主动作；
- 用户不需要先看左下角或右侧才能知道下一步；
- 页面不同时显示多个同等强调的主按钮；
- 不再出现“需求版本”“模型候选”“精简重试本轮”等旧词；
- 缩放或滚动后主要区域仍可操作。

### 案例 G：跳过普通细节、预算耗尽和重复跳过

- 跳过篇幅等普通细节直接继续，不出现三选一处理卡；相关内容在摘要中标为待补充；
- 关键问题经过一次猜测确认仍被跳过时，进入草稿或明确的补充入口，不再次自动追问同一问题；
- 预算耗尽后仍可查看摘要、先做草稿、保存，不能靠反复“加 2 轮”才能恢复操作；
- 生成猜测时 API 失败也可补充或先做草稿；失败不自动发新请求。

### 案例 H：旧会话恢复和修改

- 打开现有“已跳过但仍有 blocking gap”的会话，不用改任务或重建会话就能补答；
- 直接补答保留已有问题和回答历史；采用解释记录来源和用户动作；
- 修改一条需求后只在同一核对区提示相关变化，不要求逐条点完所有旧需求才能分析；
- 一键核对只接受当前展示且用户明确确认的内容，不接受未展示候选，不丢失硬约束与冲突；请求失败不撤销已经保存的用户回答；
- 真实控件点击覆盖“提交回答”“是这个意思”“先做草稿”“确认需求并生成方案”，不能只验证按钮文字存在。

## 六、实施边界

- 优先在现有 Tkinter/ttk 结构上整理，不要为了视觉重做整个应用；
- 不新增在线 Skill 搜索、自动安装或复杂下游执行；
- 不改变三种 API 协议支持和最近完成的截断恢复逻辑；
- 不删除需求来源、版本失效和保存重开机制；
- 不为了让演示通过而静默接受未确认事实；
- 不引入多层向导、复杂设置页或大量弹窗；
- 如果当前数据结构无法无损表达“AI 暂定理解”，先做最小字段扩展和旧会话兼容，不要重写整个 session 模型。

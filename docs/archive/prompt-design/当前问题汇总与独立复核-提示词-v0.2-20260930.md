## 一、项目是什么

PromptSmith（需求引导式提示构建助手）。Python 3.11 + Tkinter 桌面应用，PyInstaller 单文件 EXE 发行。用于第八届全球校园人工智能算法精英大赛赛题二。

### 核心设计

模型的输出**永远只是候选，状态的更改权在程序手里**。模型返回的内容要经过 Schema 校验、语义校验、来源校验，进入待审候选区，必须由人点"接受"才落到正式状态。方案、Skill 绑定、最终结果同此。这条把"模型幻觉直接污染交付物"在架构层面掐掉了，是本作品最值钱的设计，也是答辩时最该讲的一点。

### 真实流程顺序（注意：不是线性 M1→M5）

**这里 v0.1 写错了，本版按方案原文与 UI 实际位置更正：**

表达任务 → 推荐可修改的任务类别并提取已有信息 → 针对缺口追问 → **必要时看局部示例并反馈（M5）** → 确认需求与标准 → 生成并确认完整初始方案（M2）→ 识别关键工作 → 检索与选择 Skill（M3）→ 增量整合（M4）→ 可选文本试运行、修订与导出。

关键：**M5 在需求澄清阶段，位于"确认需求"之前，不在 M4 之后。**

佐证：
- 方案原文 `output/需求引导式提示构建助手_参赛方案最终稿.md:55` 的流程描述
- UI 实际位置：M5 在第 1 个页签（输入与需求），M3/M4 在第 3 个页签（Skill 增强）

不要把 M5 描述为"末端步骤"或"Skill 之后的环节"。

### 4.1 事实链（作者已完整复现）

目录 `resources/skill_catalog/catalog_v0.1.json` 中，`to-spec` 的 `work_signal_groups` 有两组，**组间是 AND**：

- `software_context`：`软件 / 报名系统 / 软件系统 / 应用 / 网站 / 程序 / 软件开发`
- `specification_work`：`规格 / 用户故事 / 实现决定 / 测试决定 / 范围边界`

D2 真实会话（`.../real_d2_completion_.../D2/final_session.json`）的关键工作：

| id | 标题 | 含"软件" | 命中组 |
|---|---|---|---|
| k1 | 功能需求规格编写 | 否 | `specification_work` |
| k2 | 测试要点编写 | 否 | `specification_work` |
| k3 | 开发者可用性与演示标准复核 | 否 | `specification_work` |

三者**全部漏掉 `software_context`** → 整组 0 命中 → 组间 AND 失败 → `no_match`，`unmatched = ['k1','k2','k3']`。

2. 上文 3.x、4、5 每一条的核实结果：**成立／不成立／无法核实**（附理由）
3. 你新发现的问题
4. 如果只能做一件事，你推荐哪件，为什么
5. 你需要的、只能由人提供的东西（凭据、真机、人的决定）

## 八、真实调用预算（若你打算做真实调用）

`固定案例与证据边界.md` 写"建议调用总数不超过 14 次"，但已知历史口径混乱（见 3.7）。若本轮要补 M3／M4 真实内容，**先与用户确认预算和凭据**，不要自行发起调用。

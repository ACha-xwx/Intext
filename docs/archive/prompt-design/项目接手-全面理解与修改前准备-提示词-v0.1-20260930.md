一、先理解我们的目标与取舍

软件名称是 PromptSmith，作品暂名“需求引导式提示构建助手”，技术方向是提示工程。

用户通常知道自己想做什么，却未必能说清什么结果才算合适。软件通过提取已有信息、少量关键追问、必要的局部示例及反馈，帮助用户明确要求，然后形成可编辑、可复用、可交给另一个 AI 使用的完整方案和任务提示。

它不只是把一句提示扩写得更长，也不能宣称可以直接读出用户心中的想法。它面向写作、PPT 汇报、学习、方案策划与研究准备、数据分析与可视化、编程六类任务，并有通用入口；六类共用流程，不是六套独立系统。

当前目标是比赛展示：主要用户功能齐全，在简单、明确、可重复的场景下顺畅完成任务，便于录制演示视频。请关注普通用户会实际遇到的问题、功能缺口和主流程阻塞，不把低概率极端情况或商业上线级要求升级成当前必做项。UI 可用性需要关注，但暂不把整体美化排在主要功能之前。

本轮是理解与接手，不是无限期审计。先完成阅读和报告；后面我提出具体修改要求时，再基于现有实现开展增量修改。

三、理解这条主流程及不能破坏的边界

输入任务
→ 推荐可修改的类别并提取已有信息
→ 针对影响方向的关键缺口追问
→ 必要时用局部示例与反馈澄清标准
→ 用户编辑并确认需求
→ 生成完整初始方案与关键工作
→ 用户编辑并确认初始方案
→ 按关键工作检索本地 Skill 候选，可由 AI 分析解释
→ 用户选择或跳过
→ 整合最终方案与任务提示，复核确认
→ 复制、导出、保存重开；可主动进行短文本试运行。

必须保留的产品原则：

1. 不再设置“选择方法包”。先形成完整初始方案，再做 Skill 增强；不选 Skill 也必须得到可用结果。
2. 初始方案包含目标、要求、工作步骤、交付物、完成标准和未决事项。“完整”指结构齐备，不代表所有未知必须被解决。
3. 模型提出候选和建议；程序维护来源、版本、确认、失效、保存及调用状态。模型不能替用户确认，也不能凭空增加预算、技术选型或硬限制。
4. 已知信息要保留；问题按依赖少量提出。允许不确定、跳过和修改，不能把到达轮次上限当作需求已经完成。
5. 示例只帮助表达标准；选择一个示例不等于接受它所有特征。示例假设和反馈候选不能直接成为正式需求。
6. 新旧要求冲突要显式处理。上游变动后，下游结果是否仍有效由程序判断，不能悄悄沿用过期确认。
7. 中性与适度礼貌是最终提示的受控表达变化；事实、约束、方案和已选 Skill 应保持一致。访谈自然程度与最终提示礼貌程度是两回事。
8. 导出内容要独立可读。短文本试运行不代表软件能执行任意完整下游项目或自动运行 Skill。

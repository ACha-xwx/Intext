# JGS 真实测试问题与 M1-M2 内容质量修复执行提示

**版本**：v0.1
**日期**：2026-10-01
**用途**：交给另一个开发/修改对话，修复“讲解 JGS”真实测试暴露出的需求追问、初始方案和最终任务提示问题。
**本版性质**：基于一次真实测试的修改方案与验证要求，不代表已经完成代码修改，也不代表真实模型复测已经通过。

## 一、先读懂问题，再修改

本次真实测试的输入大致是：

1. 用户输入“讲解 JGS”。
2. 软件追问 JGS 指什么。
3. 用户回答“数值分析课程里面的一个知识点”。
4. 经过一次理解确认后，系统按 Jacobi 与 Gauss-Seidel 迭代法方向继续。
5. 用户补充自己是学生、零基础。
6. 软件导出的最终任务提示仍然主要是完整内部方案，包含 r1-r4、工作步骤、关键工作、来源和完成证据；“零基础学生”只作为末尾附注出现。

这说明问题分为两层：

- **需求访谈层**：追问补齐了 JGS 的领域和对象线索，但没有补齐会显著影响讲解方式的学习基础与学习目标。
- **交付提示层**：完整方案和最终任务提示没有分工。最终提示没有把已确认信息重新编成下游 AI 可以直接执行的独立任务，而是把内部管理信息一起带出。

不要把本次问题解释成“每个任务都要多问很多问题”。本次目标是：在确认任务对象后，再问一个最有价值的学习定位问题；信息足够后停止追问，允许用户带着可延期未知继续。

## 二、不可改变的产品原则

1. 需求会逐轮累积，已经确认的信息不重复询问。
2. 用户的确认只表示本次任务采用该理解，不宣称缩写在所有场景都必然如此。
3. 用户明确说“我是零基础学生”，应进入正式需求正文，不能只放在用户附注中。
4. “零基础”不能只写成标签，必须转换为可执行的讲解要求：从必要前置开始、首次出现的符号要解释、公式逐步引入、使用小型算例演示。
5. 初始方案是内部结构化方案；最终任务提示是给另一个 AI 直接使用的独立提示。二者不能简单复制。
6. 最终交付物必须仍然是用户要的内容，例如“帮助学生学懂 JGS 的讲解”，不能被改写成“写一份讲解计划”。
7. 教学例子、自测题、代码演示等可以作为建议，但不能在用户未要求时被伪装成硬性需求；可以纳入方案的可选教学措施。
8. 用户跳过学习程度问题时，流程不能卡住。程序应允许按保守的入门级默认继续，并在需求卡中用自然语言提示“讲解会按入门方式处理，如需更深可以再调整”，不要突然显示没有铺垫的内部术语。
9. 追问不是越多越好。只问会改变讲解方向的问题；当前 JGS 案例通常 2—3 次关键追问已经足够。

## 三、M1 需求理解与动态追问的修改要求

### 3.1 追问优先级

对“讲解/学习某个概念”类任务，按以下顺序判断：

1. 任务对象或术语含义是否不清；
2. 学习者是谁、基础大致如何；
3. 学习目的是否会改变内容组织，例如从头理解、复习、做题或准备考试；
4. 只有在确实影响交付形式时，才询问篇幅、时间、格式等细节。

同一轮默认只问一个问题；两个问题只有在高度相关且用户容易一起回答时才允许并列。不要为了达到轮数而追问。

### 3.2 JGS 场景的期望追问链

当用户只输入“讲解 JGS”时，推荐行为是：

- 第 1 问： “这里的 JGS 具体指什么？它属于哪门课或哪个领域？”
- 用户回答“数值分析课程中的一个知识点”后：如果模型已有可靠线索，可给出一次待确认理解：“我先按数值分析中的 Jacobi 和 Gauss-Seidel 迭代法来理解，可以吗？”
- 用户接受该理解后：继续问一个高价值问题：“你之前学过线性方程组或迭代法吗？这次是想从零开始理解，还是主要复习公式、做题？”

如果用户此时已经主动说“我是零基础学生”，就不要再问同一个问题，应把该信息直接吸收为需求。可以只补问学习目的，若学习目的不会改变交付方式则直接进入需求复核。

### 3.3 信息归类

- “我是学生、零基础”是用户关于自身情况的事实；
- “请按零基础方式讲解”是用户对讲解方式的明确要求；
- “先用直观例子，再讲公式”如果是系统建议，必须保持为建议，只有用户采纳后才成为正式要求；
- 模型对 JGS 的 Jacobi/Gauss-Seidel 理解在用户确认后，可以作为本次任务的已采用范围，不要在下游提示里再次当作未确认偏好。

### 3.4 跳过和不确定

用户跳过“学习基础/学习目的”问题时：

- 保留该未知，但不阻断生成初始方案；
- 默认采用安全的入门讲解方式；
- 在用户可见文字中说明默认依据，例如“你暂时没有指定学习基础，我会先按入门方式组织，之后可以再调整”；
- 不能把“跳过”写成“用户已确认零基础”，也不能反复换句追问。

## 四、M2 初始方案的修改要求

初始方案仍然要完整，但内容应围绕下游任务本身组织，至少包括：

- 任务目标：帮助当前学习者理解数值分析中的 Jacobi 与 Gauss-Seidel 迭代法；
- 已确认的学习对象和学习者信息；
- 讲解顺序：问题背景、必要前置、直观含义、公式、同一小算例的逐步演示、两种方法的区别、停止条件和收敛提醒；
- 真实交付物：面向该学生的可直接阅读的 JGS 讲解内容；
- 完成标准：学生能说出两种方法的核心区别，并能跟着算例完成至少一轮更新；
- 未决事项：学习目的、期望深度等确实未说明的内容，以及它们对讲解的影响；
- 可选教学措施：简单自测题、对比表或代码演示，必须标记为可选，不得假装是用户硬要求。

方案中可以保留步骤、输入、输出和检查标准，但避免把 `r1`、`r2`、`KW1`、`S1` 等内部 ID 直接暴露给最终任务提示。

必须检查：方案中的最终交付物是“JGS 讲解”，不是“JGS 讲解工作计划”。计划只是软件内部用于组织工作，不能取代下游 AI 要完成的讲解成果。

## 五、最终任务提示的修改要求

最终提示不得直接等于完整方案正文加一句“请根据以下任务说明完成工作”。应增加一个独立的编译/整理步骤：

1. 从已确认需求中提取任务目标、对象、学习者、交付形式和硬约束；
2. 将尚未确定的内容写成自然的可调整说明，不把未知编造成事实；
3. 删除内部 ID、来源追踪、方案依赖、完成证据、未采纳建议等管理信息；
4. 输出一份离开当前聊天也能读懂的提示；
5. 保持事实、范围、用户硬约束和已选主题不变。

本次 JGS 最终提示至少应包含以下有效信息：

- 本次按用户已确认的 Jacobi 和 Gauss-Seidel 迭代法来讲；
- 面向一名对该内容零基础的学生；
- 先解释它们解决什么问题，再逐步引入符号和公式；
- 用同一个简单线性方程组演示两种方法，写出初始值和至少前几轮计算；
- 清楚解释 Jacobi 使用上一轮值、Gauss-Seidel 会使用本轮已经更新的值；
- 简要说明停止条件和收敛并非无条件成立；
- 不重新追问已经确认的 JGS 含义；
- 如果学习目的仍未知，可以采用通用入门讲解，并在开头或结尾留出继续调整的入口。

最终提示不应包含：

- “r1 偏好”“需求 r2”“S1 术语核对记录”等内部引用；
- “具体受众未指定，待确认后调整”这类与“零基础学生”冲突的句子；
- 要求下游 AI 先再次核实已经由用户确认的 JGS 含义；
- 把讲解稿、例子和检查题一律写成用户已经明确要求的固定交付包；
- 把工作计划作为最终学习材料。

## 六、建议的最终提示示例

以下只是本次修复后的目标形态，不代表已经通过真实模型测试：

```text
请面向一名对这部分内容零基础的学生，讲解数值分析中的 Jacobi（雅可比）和 Gauss-Seidel（高斯—赛德尔）迭代法。本次对话中确认的“JGS”按这两个方法来理解。

请直接进行教学，不要只给学习计划：

1. 先用通俗语言说明它们要解决什么问题，以及为什么可以通过迭代逐步求解。
2. 涉及必要前置知识时先简短解释；每个新符号第一次出现时说明含义，不要一开始堆出大量矩阵公式。
3. 选一个简单的二元线性方程组，用同一个例子分别演示两种方法，写清初始值、每一步使用的数值和前几轮结果。
4. 结合算例解释两者的核心区别：Jacobi 使用上一轮的值，Gauss-Seidel 会立即使用本轮已经更新的值。
5. 简要说明什么时候可以停止，以及为什么不能假设所有问题都会收敛；暂时不展开复杂证明。

内容要由浅入深，同时保留必要公式和计算过程。最后给出一个很短的自测问题，帮助我检查是否真正理解了两种方法的区别。如果我之后说明了学习目的或基础，请据此调整深度和例子。
```

## 七、需要用户补做的最小测试集

不需要重新做一轮全面验收。为了确认这次修改方案足够，建议只补做下面 3 个场景：

### 测试 A：复现并修复当前问题

输入：“讲解 JGS”。

按程序正常回答问题，提供“数值分析课程中的一个知识点”，接受软件给出的 Jacobi/Gauss-Seidel 理解，再观察是否继续询问学习基础或学习目标。

期望：不超过一个新的关键问题；问题应直接影响讲解方式；最终需求正文中出现零基础或未知学习基础的自然说明；最终提示不出现内部 ID。

### 测试 B：一次性提供完整学习信息

输入：“我想从零开始学习数值分析中的 Jacobi 和 Gauss-Seidel 迭代法，是学生，暂时只想理解概念和基本计算。”

期望：不再重复询问 JGS 含义或零基础；可以直接进入需求复核/初始方案；最终提示应直接面向学生学习，不应要求下游 AI再次确认术语。

### 测试 C：用户跳过学习基础问题

在软件询问学习基础或学习目的时选择“跳过/不确定”。

期望：流程不阻断；需求中保留未知；软件用自然语言说明将先按入门方式处理；仍然能够生成完整初始方案和可执行最终提示。

## 八、验收判据

同时满足以下条件，才认为本轮修改达到预期：

1. 术语不清时会问，术语已经确认后不重复问；
2. 对学习类任务至少识别学习者基础或明确保留未知；
3. 追问数量少而有用，不形成固定长问卷；
4. 用户补充的信息会进入正式需求正文，而不是只进入附注；
5. 初始方案的最终交付物仍是用户需要的学习内容；
6. 最终任务提示是独立、可直接执行的提示，而不是内部方案的原样导出；
7. 跳过/不确定不会使流程卡住；
8. 真实模型至少通过测试 A；测试 B、C 用于确认没有重复追问和阻断回归。

## 九、实施边界

本轮优先修改 M1 的学习类追问规则、M2 的学习任务方案约束和最终提示编译逻辑。不要因为本次 JGS 测试而新增复杂页面、强制固定三轮追问、把所有任务都改成教学模板，或提前引入 Skill、在线搜索和下游任务试运行。

完成修改后，必须把“设计检查”“程序测试”“真实模型复测”分开记录。没有真实模型复测，不得写成“内容质量已验证”。

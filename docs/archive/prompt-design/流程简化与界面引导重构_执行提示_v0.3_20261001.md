# PromptSmith 流程简化与界面引导重构执行提示

版本：v0.3  
日期：2026-10-01  
交给：负责修改 PromptSmith 的开发对话  
项目：C:\Users\yph\Documents\ChatGPT\aicomp

这是完整执行提示，可独立使用。v0.1、v0.2 留作历史，本次按 v0.3 执行。本版重新组织了内容，纠正“短标签就是通俗”“缺信息和 AI 推测都叫待补充”的理解；保留用户例子，并减少重复规则。本文件属于提示设计，未修改程序、模型提示资源或 EXE，不能作为软件实测结果。

## 先理解用户真正介意什么

用户希望软件功能齐全，但使用时简单自然：知道现在在做什么，知道下一步该点哪里，遇到不确定的内容也能继续。不能为了内部逻辑严密，就让用户学习程序的状态、在几个表格之间来回找按钮，或者反复确认同一份内容。

下面保留用户的表达。它们是这次改动的重要依据，不要在实施时又把意思压成泛泛的“优化体验、统一术语”。

> “不要因为功能太多而使得用户的使用过程过于繁杂。”
>
> “最好不要总是跳转页面，就算跳转也要比较舒适地跳转。”
>
> “你不要觉得把那些人能用自然的话语说出来的意思改成了所谓的‘待补充’这种貌似简洁的话就合适。”
>
> “有的时候不如用长一点的话来提醒，只不过你要注意，不能让页面冗杂。”
>
> “比如说这个‘待补充’，你就可以通过在旁边一个小的红色字体提醒‘此理解由AI预测生成，请自己查看一下’。”
>
> “我是通过例子然后让你理解的。”

这里不是要求禁止“待补充”这个词，也不是要求所有提示都变长、变红。用户要的是：先从他刚才的操作和眼前的内容出发，让他说得通、看得懂，再适当精简。若前面已经解释了哪一项没确定，后面用一个短标记可以；没有解释过，就突然出现一个状态词，不行。

本次要一起做好三件事：流程能继续；提示符合当前语境；页面干净。不能只改词语，不修跳过后的死路；也不能为了说明清楚，在每个角落贴满提醒。

## 1. 用 JGS 的真实过程理解问题

用户输入“讲一下 JGS”，回答了“学生学习讲义”和“数值分析领域”。软件又问 JGS 具体指什么，用户选择跳过。

随后出现了三个矛盾：
- 问题从列表消失，用户没有明显的补答入口。
- 主按钮和下一步提示仍引导他确认需求。
- 点击确认却报“仍有影响方向的未决项”，既没把原因讲清，也没带他去解决。

临时让用户改顶部任务文本，还会触发重新复核。这使用户不得不从右边的问题跳到左下方“模型候选”，再跳到左上方需求和复核按钮。用户的原话是：

> “先在右侧的引导问题，完了之后到左下方模型候选……完了之后到左上方的需求版本。”

所以本次不是修一条报错文案。要让“回答、跳过、补充、核对、继续”在一条清楚的路径中完成。

### 跳过普通细节，就直接继续

例如用户暂时不想定讲义字数。记录这个选择，转到下一个真正必要的问题，或者直接显示需求摘要。不必弹窗、加一个处理步骤，也不必立刻显示“待补充”。

如果后面确实用到字数，写“你还没定字数，可以在这里补充”；不会影响当前结果的细节，不用持续提醒。用户明确说“字数不限”时，应记录为已明确的选择，不能仍把它当缺口。

### 关键含义不清，可以让 AI 帮忙猜一次

结合“数值分析领域”，AI 可以提出一个有上下文依据的解释，再让用户判断。例如：

> 你提到数值分析，我猜你可能想讲 Jacobi 和 Gauss–Seidel 这两种迭代方法。是这个意思吗？

在这段推测旁边用小字提示，保留用户建议的表达思路：

> 此理解由AI预测生成，请自己查看一下

落到具体界面时，可自然整理成：

> 这是 AI 根据已有信息推测的，请看看是否符合你的意思。

这不是标准答案或固定模板。只有确实有这一推测时才显示。不能根据这个例子就把 JGS 的全称硬编码为上述方法，也不能声称 Jacobi 与 Gauss–Seidel 是同一种算法。用户确认的是“我要讲的对象”，不代表模型写出的数学知识都因此得到验证。

默认给一个有依据的解释，必要时最多两个。没有合理解释就直说还不能判断，不硬猜。优先合入正常的 M1 分析返回，不另开“开始猜测 → 查看猜测 → 选择解释”三步。若必须新增请求，一次操作最多触发一次；同一问题猜测后又被跳过，不自动反复追问。

当前区域提供与内容相符的选择：
- 有一个解释时：“是这个意思”。
- 用户想纠正：“我来说明”，原地出现或聚焦输入框。
- 暂时不想继续回答：“先做草稿”。

最多突出一个主要选择。若有两个解释，选项必须说清各指什么，不能两个都叫“是这个意思”。没有解释时，不显示空的确认按钮。

### 先做草稿，要先讲清会怎样，再直接执行

草稿不是本次新增的必经阶段，只是用户不想继续补充时的出口。

区分下面两种情况，不要都贴上“待补充”：

| 实际情况 | 合适的说明示例 | 不能做的事 |
|---|---|---|
| AI 已给出一个解释，用户还没确认 | “这是 AI 根据已有信息推测的，请看看是否符合你的意思。” | 把猜测写成用户事实，或者让用户误以为自己漏填了字段 |
| AI 仍不知道 JGS 指什么 | “JGS 的具体含义还没确定。我可以先整理讲义结构，这部分等你说明后再完善。” | 没有任何解释就贴“待补充”，或者编造具体讲解填满空白 |

用户点“先做草稿”前，应已看到上述适用说明；点下后直接做能做的部分，不再让他去另一页点一次“生成草稿”。如果用了未确认的假设，相关内容旁说明是推测；如果确实缺少信息，说明缺哪项、影响哪部分。不能把两者混成一类。

结果至少可以查看、编辑、保存和导出。不能在需求页放行，到方案页或导出时又因同一项把用户卡回去。结果中保留未确定内容及其影响，不声称已经全部确认；以后补充时可以更新相关内容。

如果要使用“待补充”或“待确认”这样的短标记，必须紧邻前面已解释过的内容，用户能对应到具体事情。短标记只是方便扫读，不能承担完整解释。也不要求每份 AI 生成内容都附一条警告；用户明确提供的信息、普通排版整理，无需重复提醒。

## 2. 主流程只保留用户真正需要做的几步

默认路径：

输入任务 → 必要时回答 → 核对需求 → 核对方案 → 得到方案和提示

信息足够时省去追问。Skill、局部示例、语气设置、试运行保留，但不是每位用户的必经步骤。

### 一个工作区，一个明显的下一步

- 主要内容沿上下顺序展开。任务输入、当前问题、需求核对在同一工作区接续，不做三个同时抢注意力的大面板。
- 主按钮固定在同一区域，当前位置和下一步说明放在内容附近。历史内容收成可展开的摘要，不丢失、不挤占当前操作。
- “提交回答”一次完成记录和必要分析，不要求先点“回答”，再去找“继续分析回答”。用户可以自由补充，不必先选中表格行才能输入。
- 一次回答可以包含多个信息。默认问一个关键问题；两个短问题紧密相关时可在同一区域一起回答，不为此新建翻页步骤。
- AI 整理出的内容进入同一份可编辑的需求预览。用户核对后一次确认，不再依次“采用全部 → 逐条已复核 → 确认需求”。
- 重要猜测和互相冲突的硬要求，要在这份预览中清楚处理，不能借一键确认接受用户没看过的内容。
- 修改信息后原地显示相关变化，不重新要求用户回答所有问题。已跳过的问题可直接补答，不能靠重写整个任务来恢复。

按钮示例应结合实际状态使用，不是要求把这些按钮同时摆出来：

| 用户现在正在做什么 | 主要操作 |
|---|---|
| 已输入任务，准备开始 | 开始整理 |
| 已填好当前回答 | 提交回答 |
| 正在判断一个 AI 推测 | 是这个意思 |
| 已核对需求预览 | 确认需求并生成方案 |
| 已了解缺少什么，想先推进 | 先做草稿 |
| 分析失败，回答仍保留 | 重试分析 |

显示哪个操作、点下去做什么、是否允许执行，应使用一致的状态判断。不能页面建议确认、点击却报早已能判断出的不能确认。忙碌时防重复提交，失败后恢复可用操作。

轮数限制留在内部。不要把“增加 2 轮追问”变成用户必须理解的救命按钮，也不要把两轮改叫两个问题。达到预算后显示现有内容，让用户主动补充或先做草稿，程序保持有界请求，不自动循环。

### 方案、Skill 和结果也保持这条路径

方案包含目标、要求、步骤、交付物、完成标准、未确定事项；关键工作在方案中一起看，不再要求去另一张表逐条打勾。

默认可点“确认方案并生成提示”，直接获得无 Skill 的完整结果。旁边保留“添加 Skill（可选）”入口，用户没打开就不必再点一次“跳过 Skill”。

用户需要 Skill 时，在方案附近按需展开。完整初始方案必须先形成并由用户确认，再按关键工作检索真实目录；在入口文案中讲清确认并查找的动作，不由后台偷偷确认。选择、无匹配或取消后，都能在同一工作区继续；选用导致的实质变化应展示给用户。

结果提供复制、保存、导出。试运行和语气选项降低视觉权重，不能要求先试运行才允许导出。草稿出口也要贯通，未确定部分沿用前面已经说明的含义，不另冒出一套陌生状态词。

## 3. 页面简洁，切换也要让人跟得上

可以用“需求 → 方案 → 结果”作轻量进度提示，但这不是要求再建三张必须手动切换的页面。能原地更新就原地更新。顶部不再并排摆多套阶段导航和操作按钮。

首次配置时展示模型设置，配置好后收起。原有多协议、模型获取、测试连接等能力保留入口。空的问题表、空的建议表和大块无内容区域不占主界面。详细来源、版本、请求记录、日志放到详情。

用户点“确认需求并生成方案”后，原地显示进度，成功后在可预期的位置展示方案。如果等待时用户主动去看别的内容，就提示“方案已生成，可以查看”，不要强制抢回页面。返回查看时保留输入和合适的滚动位置，查看本身不触发重新生成或失效。

无需专门添加动画。标题、内容和操作位置稳定，返回不丢东西，就能让切换舒适。不要在每次成功、跳过、保存后弹一个必须关闭的窗口；需要保护未保存修改时仍要保护数据。

正文以实际阅读舒服为准，可从 12 pt 中文系统字体、16～18 pt 标题起步。检查 1366×768、1920×1080 以及实际缩放下的裁切和拥挤。保持滚轮、右键、键盘和焦点操作。

用户提出的小红字提醒要这样理解：
- 放在确需说明的推测附近，文字足以读清，不缩成难辨的小字。
- 可用适度强调色，不用大面积红色或错误弹窗，把正常的猜测过程渲染成故障。
- 颜色是辅助，话本身必须说清含义。
- 同一项说明不在标题、状态栏、正文和弹窗重复四次；无新增影响时不要求反复确认。
- 页面干净主要靠减少并列内容、重复操作和多余说明，不靠把一句自然的话压成两个生硬的字。

## 4. 文案要承接用户的动作，不能靠换一组标签解决

保留用户已经熟悉的称呼，例如“当前需求”“AI 建议”“方案”。同一个对象不在不同位置轮流叫“需求版本”“有效需求”“需求卡”。需要说明版本时可在详情展示，不要求用户靠版本号判断下一步。

术语一致不等于每种情况只能套同一句话。例如下面这些表达的对象不同，要根据实际过程选用：

| 前一步发生了什么 | 下一句应该让人明白什么 | 示例 |
|---|---|---|
| 用户提供了数值分析这个领域 | AI 为什么会这样猜 | “你提到数值分析，我猜你可能指……” |
| AI 写出了一个尚未确认的解释 | 需要用户检查的是哪段理解 | 在该段旁写“这是 AI 根据已有信息推测的，请看看是否符合你的意思。” |
| 用户跳过了字数 | 不必再强迫回答，仍能继续 | 直接继续；需要说明时写“先不限定字数，你之后可以再改。” |
| 用户缺少具体术语含义但愿意推进 | 草稿会做到哪里 | “我先整理讲义结构，具体讲解等你说明 JGS 的含义后再完善。” |
| 请求失败 | 回答有没有丢、现在怎么办 | “刚才没有收到完整结果，你的回答已保存。可以重试分析。” |
| 用户确认了猜测 | 这次选择产生了什么结果 | “好，按你刚才确认的这两种方法整理讲义。” |

以上都是适用条件下的例子，不得无视输入套用。“先不限定字数”表示暂时不采用这个约束，不等于用户已经承诺字数不限，内部记录要区分。

重点检查这些问题：
- 用户跳过了，不能说“感谢补充”。
- 只是记录了回答，还没分析，不能说“已经理解清楚”。
- 仍在猜，不能说“已经确认”。
- 普通重试不用说“精简重试本轮”；精简是内部机制，按钮写“重试分析”，旁边说明回答已保存即可。
- 有充分铺垫时，短词可以用；没有铺垫时，先写清事情。不要把“待补充”换成另一个同样突兀的短标签，就认为完成改进。
- “是这个意思”是自然的确认回答，不必强改成“动作 + 对象”的官方句式。

主说明通常一两句即可，但不设机械字数上限。多几个字能把事实和后果说清，就保留；跟当前决定无关的背景、规则、技术细节收进详情。

## 5. 实现时保留可靠性，但别把内部步骤搬给用户

先读当前代码和最新交接，文件或行号变化时以实际实现为准：

- src/promptsmith/ui.py、session.py、workflow.py、api.py；
- output/prompt/_design/ 中当前 M1 提示、增量提示及输入输出 schema；
- 需求确认、问题记录、保存重开、主按钮、方案与最终结果相关测试；
- verification/m1_truncation_fix/修复与交接_20261001.md。

前面已经核实：确认函数会阻断方向未知，但主按钮和下一步文案没有同步判断；跳过移除了待答问题；直接修改任务会清理问题和回答历史。请检查当前是否已有别处修复，不重复采用过时结论。截断、超时和协议支持已有独立改动，不能按早期 8 token、45 秒的描述重做。

实现要求：
1. 用户原话、用户选择、AI 推测、仍未知内容，内部继续分别记录来源。确认一次展示内容可以合并多个内部更新，但模型不能替用户确认。
2. 推测解释优先由现有 M1 调用返回，关联具体问题和缺口。必要的新字段属于本次设计，修改时同步 schema、校验与旧会话兼容，不能假装现有接口已经支持。
3. 采用一个解释只解决其对应问题，不附带接受模型增加的预算、技术选型或其他范围。拒绝解释时不让它进入有效需求。
4. 直接补充应保留已答历史。打开旧会话发现跳过后仍阻断，也要有同样的原地补答和继续入口，不要求重新开始。
5. 用户允许先做草稿，是一个可保存的决定；不把它写成全部未知已解决。沿 M2、可选 Skill、最终结果、导出完整核对这条路径，必要时补最少的草稿入口校验，不绕过所有确认规则。
6. 修改内容、需求或 Skill 后，保留原有下游失效与历史机制。异步结果不得覆盖新会话或更新后的内容；只查看、折叠或返回不应使结果失效。
7. 一次提交记录并分析，失败保留输入，重试不得重复追加同一回答。猜测失败仍可直接补充或保存当前草稿；离线时不假装模型已生成方案。
8. 不删除此前截断识别、有限重试、三协议支持、保存导出和资源打包。不要为体验优化重写整个业务模型、换 UI 框架或引入与本次无关的功能。

先完成默认短路径与跳过后的出口，再整理可选能力入口。严密性体现在这些内部规则上，用户不用逐个“批准状态转换”。

## 6. 每次优化后，再自己用一遍

每完成一批有意义的优化，检查受影响的普通操作。交付前再从头到尾走一次，不止看单元测试通过。

至少包含下列场景：

| 场景 | 要看到的实际行为 |
|---|---|
| 信息完整的普通任务 | 不强制追问，不经过 Skill、示例、试运行也能生成并导出可用结果 |
| JGS 跳过关键问题 | 原位置接住，给一次有依据的理解确认或直接补充入口；不能“引导确认 → 报不能确认” |
| 接受或纠正 AI 猜测 | 用户知道确认的是哪段话，选择有来源，纠正不丢历史，不额外跑多个确认页面 |
| 用户继续选择跳过 | 不反复自动追问；先说明草稿会缺哪部分，用户点一次即可推进到可保存导出的结果 |
| 跳过普通细节 | 不新增三选一处理卡、不制造额外确认 |
| 失败、重试、保存重开 | 回答和用户选择仍在，操作入口清楚，没有强迫重填或重复记录 |
| 修改和返回查看 | 只处理受影响内容；查看不失效，后台完成不抢走用户当前编辑位置 |

**自检必须包含语言和界面，不止函数结果。**

按使用顺序把文字连续读一遍：用户刚才做了什么，他知道哪些信息，为什么此刻看到这句话，下一步按钮是否顺理成章。如果需要开发者在旁边解释，说明还要改。

尤其复查以下两组：
- “AI 推测了一段解释”与“根本没有这项信息”，是否用了不同且准确的说明。
- “之前已解释过，短标签可帮助扫读”与“之前没提过，突然出现短标签”，是否区分开。

再实际点一遍，检查主按钮位置、多余点击、空面板、红字堆叠、重复弹窗、跳页和焦点。读完页面能否看出当前要做什么；少了一次点击之后，是否反而默默接受了用户没看到的猜测。

记录简短结果：“发现什么 → 改了什么 → 如何复查 → 结果”。发现问题先修，再针对性复查，不扩展成罕见场景专项。没有实际界面操作，要明确写未验证；本地桩不等于真实模型内容通过。

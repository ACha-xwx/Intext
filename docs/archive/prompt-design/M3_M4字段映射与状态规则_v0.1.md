# M3/M4 字段映射与状态规则 v0.1

日期：2026-09-28。本文对应本轮源码接线；真实模型内容效果仍未实测。字段若与代码不一致，以生产代码和测试中的当前接口为准，并在下次版本更新本文。

## 1. 版本与权威数据

会话格式为 `promptsmith.session.v0.2`，兼容读取 `promptsmith.session.v0.1`。会话格式版本独立于 M1/M2/M3/M4 提示和 Schema 版本。M1 v0.5、M2 v0.1 的提示正文及输出契约不在本轮修改。

| 数据 | 唯一权威位置 | 说明 |
|---|---|---|
| 用户正式需求及确认版本 | `SessionState.requirements`、`requirement_version`、`confirmed_requirements_version` | 仅当前已确认需求进入末端输入；模型不能改确认状态 |
| 初始方案及关键工作 | `SessionState.plan` | 只允许以当前任务、需求、已确认方案版本作为 M3/M4 基线 |
| 目录候选及 M3 解释 | `SessionState.skill_state.candidate_batch`，解释写入 `m3_analysis` | 目录筛选和 AI 解释分别标注；M3 只提出匹配分析，不代替用户选用 |
| 用户实际选用的方法 | `SessionState.skill_state.bindings` | 每条绑定保存目录记录快照、hash、关键工作、步骤、能力和前提评估；`selected_skills` 是兼容镜像 |
| 末端结果、建议与用户附注 | `SessionState.final_result` | 结构化内容为权威来源，`canonical_body` 是可校验渲染缓存 |
| 末端有效性 | `delivery_revision` 与 `final_result.basis` | 来源变化使旧结果失效；单纯语气切换不改变语义版本 |
| 未完成调用 | `DeliveryWorkflow` 的进程内请求表 | 不写成已完成的会话业务状态；关闭/重开后不能恢复旧调用资格 |
| API Key | 当前 UI 进程内配置 | 不进入 Session、请求证据目录、资源或导出 |

旧 `selected_skills` 字符串会迁移到 `legacy_selection_unresolved`，不自动变成有来源快照的正式绑定。未知或损坏的未来会话格式明确拒绝；旧内容缺少来源依据时保留为 stale，不自动确认。

## 2. M3 候选解释

1. 程序前置检查当前需求和方案仍有效、初始方案已确认、候选批次有批次号和目录 hash，且批次至少有一个候选。
2. `prepare_m3(request_id, connection_version, target_environment)` 从当前候选批次、关键工作、任务/需求/方案版本和运行条件构造输入，并在工作流内登记请求快照。
3. 用户显式点击“AI 分析候选”后，`invoke_m3(...)` 通过当前配置选定的既有三协议客户端调用模型，验证 JSON Schema 与跨字段引用，并写入实际 raw、请求、模型、用量（实际不可得为 `null`）、耗时及检查结果。
4. `apply_m3(...)` 重新校验 request id、模块用途、session token、连接版本、请求 epoch、候选批次 id/hash、目录记录 hash、方案和需求版本。有效分析写入 `candidate_batch.m3_analysis`；失败不覆盖候选，迟到响应不写入业务状态。
5. M3 的来源、能力编号、前提、候选 ID 都必须属于当前批次。AI 推荐不是用户选择；选择由 `SessionState.set_skill_state(...)` 原子更新 bindings 后才发生。

关键公开函数：`build_m3_input`、`parse_m3_response`、`DeliveryWorkflow.prepare_m3`、`invoke_m3`、`apply_m3`、`cancel`、`invalidate_requests`。

## 3. M4 方法增量整合

1. 前置条件：当前需求和初始方案已确认；至少一个当前有效 Skill 绑定；每个绑定只使用已核验目录快照中允许的方法适配；不存在指向过期需求、方案、步骤或绑定的引用。
2. `prepare_m4(...)` 深拷贝已确认基线、关键工作、步骤、未知项、当前 M2 建议决定、绑定和适配前提，生成 M4 输入。对未知前提保留 `unknown` 及其阻断属性，不由模型或目录静默改成满足。
3. `invoke_m4(...)` 通过既有三协议客户端调用；解析器拒绝选中绑定外的能力、步骤、前提、变化引用、重复贡献或漏掉绑定。每个绑定至少有一个具体贡献，含输入、方法动作、输出、检查点和必要 fallback。
4. `apply_m4(...)` 先对会话副本组装完整末端草稿和待处理变化，完整校验后再提交最终结果、归档、版本和运行摘要。失败或迟到响应保留已有效草稿、需求、绑定及用户操作。
5. 模型不重写基线，不直接确认新范围、成本、权限或假设。新增变化在 `content.pending_changes` 带 `change_id`、`generation_request_id`、绑定归属、影响类型与 `decision=pending`；关联变化的贡献在确认前按 `review_required_ids` 阻断。
6. 用户逐项调用 `decide_m4_change(..., accepted|rejected)`。接受仅适用于不改变硬约束的变化，写为带 `source_change_id` 与 `origin_binding_ids` 的附加内容；拒绝保留明确记录。硬约束变化需返回需求/方案上游处理。决策会撤销旧确认并更新结果版本。
7. 取消绑定后必须重新生成：单来源贡献/已采纳变化随来源撤除；多绑定共享内容收缩到仍存活来源；不依赖绑定的人工附注保留；依赖已取消绑定的编辑保留在 `unapplied_edits`，等待用户决定。

关键公开函数：`build_m4_input`、`parse_m4_response`、`DeliveryWorkflow.prepare_m4`、`invoke_m4`、`apply_m4`，以及 finalization 的 `build_final_draft`、`stage_final_draft`、`decide_m4_change`。

## 4. 请求、失败与版本规则

`DeliveryWorkflow` 的请求快照绑定用途、请求 ID、运行时会话实例 token、连接配置单调版本、模块 epoch、任务文字、类别、需求确认、方案确认、Skill 选择 revision 和内容指纹。M3 额外绑定候选批次、目录 hash 和候选记录 hash；M4 额外绑定 binding fingerprint、记录 hash、`delivery_revision`、当前最终结果 ID/revision。

同类新请求会作废旧 epoch；取消、会话替换、连接 A→B→A、候选/绑定变化、方案/需求变化及最终草稿编辑都会拒绝旧响应。调用期间 `invoke` 不写业务状态；错误证据如实记录可得的实际响应与用量。只有 `apply` 的版本检查通过后，程序才一次性接收业务结果。重复 apply 和重用请求 ID 均拒绝。

重开会话不恢复运行时 API Key 或旧请求资格。加载时验证最终正文缓存、basis、绑定快照和确认版本；损坏缓存会重渲染并撤销旧确认，来源过期则保留内容为 stale。

## 5. 接口与验证边界

M3/M4 共用 `api.client_for_config` 支持的 OpenAI Chat Completions、OpenAI Responses 与 Anthropic Messages 适配器，以及 `RunEvidenceWriter`。提示/Schema 位于 `output/prompt/_design/`，由 `PromptSmith.spec` 作为资源随单文件包带入；目录数据位于 `resources/skill_catalog/`。本地目录只允许 `method_adaptation`，不安装或执行原版 Skill。

本轮三协议 stub 只能证明请求端点、认证头、结构解析、状态应用和错误边界可复跑；不能证明真实模型推荐/整合内容恰当。若没有安全可用的既有运行时配置，真实 M3/M4 内容调用记为“未执行”。F1–F3 保持暂缓，不据此声称已修复或复测。

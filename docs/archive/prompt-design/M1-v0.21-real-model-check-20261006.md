# M1 v0.21 真实模型检查记录

日期：2026-10-06  
模型：DeepSeek `deepseek-flash`  协议：OpenAI Chat Completions  
场景：用户提出“给零基础学生讲解 JGS”，随后回答“数值分析领域里的 JGS，但不知道正式名称”。

## 检查过程

1. 首轮输入任务后，模型返回 `status=ok`，将 JGS 含义列为影响方向的阻断缺口，`model_judgment.continue_interview=true`，并提出要求补充语境的自然问题。
2. 输入“数值分析领域里的 JGS，但不知道正式名称”后，模型没有返回 `input_error`，也没有要求用户先写正式全称。它保留“数值分析领域”这一用户事实，并生成了一个标为 `pending_interpretation` 的候选解释，同时用确认选项继续询问。
3. 接受该候选后，模型继续追问 JGS 的方法范围，并补充询问最终交付形式；方法范围被标为阻断缺口，交付形式被标为可以稍后确定的缺口。

## 结果判断

- **流程判断：通过。** 三轮均返回 `status=ok`，没有因简称不明中断或向用户显示技术错误。
- **模型判断对接：通过。** 每轮都有 `model_judgment`，并与 `gaps`、`readiness`、`next_action` 和问题相互一致。
- **用户事实与模型推测分离：通过。** “数值分析领域”作为用户事实保存，JGS 的具体解释作为待确认候选保存，未直接写成用户已经确认的事实。
- **继续追问能力：通过。** 确认术语候选后，模型转向方法范围和交付形式，没有停在术语确认上。

## 限制与后续

这次检查证明的是提示、状态和程序联动在一个真实场景中能够继续推进，不等于候选解释本身已经经过外部资料核验。演示或正式使用时，待确认候选仍需由用户确认；若需要事实准确性，应另行接入真实检索结果。还应在一个非编程任务和一个编程任务上各重复一次，观察不同任务类别下问题数量和追问重点是否合适。

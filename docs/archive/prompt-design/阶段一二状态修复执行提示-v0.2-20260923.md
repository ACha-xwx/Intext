## C1：建立可靠的缺口处理流程，不靠关键词决定已解决

现象：问“报名表单需要填写哪些信息？”，用户回答“这个要问负责报名的老师”或“先收姓名，联系方式等老师确认后再补”，缺口仍立即被删除。现有代码把“未命中不确定／部分回答词典”当作“已经完整回答”。

本次必须实现的行为：

- 提交自由回答先保存原话、来源、问题与具体 gap 的对应关系，并使旧分析及确认依据失效；不能仅凭非空、未命中关键词、命中选项或相同 field/scope 就关闭缺口。
- 在原有下一轮 M1 调用中，由模型判断回答是否解决具体缺口。程序消费明确的更新建议并维护状态，不要求为每个回答增加一次独立模型调用。
- 必要时扩展结构化接口，以承载具体 gap 的“解决、部分补充、仍未知、不再适用”建议以及依据。字段命名由你结合现有代码确定；例如目标 gap ID、动作、来源引用、剩余未知是可选设计方向，不是已经存在的接口。
- 程序检查目标确实存在、来源确实属于当前输入、建议基于当前有效版本且动作合法。模型省略旧 gap、返回空列表、指向错误 gap、引用伪造或旧来源、返回迟到结果，都不能自动关闭当前缺口。
- 部分回答可以提出已明确内容的需求候选，同时保留具体剩余未知。未经用户接受的候选不能被当成已经采纳的决定。
- 真正完整回答必须能通过可达的正常流程关闭对应 gap；其他同字段、同范围的独立 gap 不受影响。闭合依据保留在历史中，保存重开可追溯。
- 用户明确撤销相关范围时，可以有依据地标记“不再适用”；不能仅因前置 ID 被归档，就把未知当作已经解决。
- 允许保留 `can_defer` 未知继续核对和确认；方向性阻断仍需处理。不要把修复做成“所有未知永远保留”或要求用户消灭全部未知才能继续。

关键分工：语义判断由模型提出；版本、有效引用、状态更新和确认由程序维护。不要以继续扩充否定词词典作为这次修复的主要方案，也不要把“引用原文存在”单独等同于“语义上已经回答完整”。可提供明确关闭具体未知的用户操作作为补充，但不能让自然语言回答的正常路径失效。

## C2：完成整次状态更新后再协调冲突

现象：两条已登记冲突的正式需求共存，另有一个待处理的替换候选。用户手工编辑其中一条正式需求后，旧候选失效触发冲突清理；此时旧需求已归档，新 ID 尚未重定向，冲突被提前删除。最终矛盾要求可以一起确认。

本次必须实现的行为：

- 把归档、新活动 ID、引用重定向、失效候选清理、冲突参与方更新作为同一次完整状态变更处理。
- 内部候选清理不能在半更新状态提前断言冲突已经消失。完整更新后再统一协调冲突，失败不得部分写入。
- 手工编辑、手工撤销、接受替换／撤回候选共用一致规则。保留已有正式需求、缺口、问题、候选和待复核列表的活动引用保护。
- 用户只是修改措辞或强化原限制时，原矛盾尚在，冲突必须继续引用新的活动 ID 并阻止确认。
- 用户确实撤回矛盾一方，或通过明确的替换／解决操作消除矛盾后，必须能关闭对应冲突并继续；不能反向变成冲突永远无法解决。
- 下一轮模型省略未解决冲突仍应被拒绝或保守保留；不能依赖模型重新发现已被程序删掉的矛盾。

重点复现顺序：登记冲突 → 部分接受候选 → 仍有针对旧项的修改候选 → 编辑正式项使该候选失效 → 验证冲突引用新项且确认被拦 → 真正解决冲突 → 可以继续 → 保存重开状态一致。

## C3：允许用户有依据地重开已跳过的问题

现象：不同 scope 的同字段问题现在已经能分别提问，但历史上一旦 skipped／unsure，同一 scope 就一直被拦截。即使用户主动说“现在可以聊网站受众了，请重新问我”，合法问题仍被拒绝。

本次必须实现的行为：

- 保留无新依据时的重复追问保护；相同 field、不同任务 scope 的问题仍可正常提出。
- 用户通过最新消息或明确 UI 操作重开具体问题／gap 后，允许对该范围重新提问，保留之前的跳过记录与重开依据。
- 自然语言路径必须能处理已有复现中的明确重开表达；不能只新增按钮而继续拒绝这条有效路径。
- 如需模型识别重开意图，让模型提出绑定具体 gap 和最新用户来源的建议，由程序校验并记录；不能仅凭模型填写“有新情况”的 reason、引用材料中的话，或有一条不相关的新消息就解除保护。
- 新证据／新冲突确实影响原问题时，可提供同样可追溯的重新判断路径；没有依据则继续保留未知。
- 重开只作用于对应范围，不清空全部 question_history，不跳过版本或问题预算检查，不自动关闭缺口，也不自动确认需求。

## 必须通过的验收场景

测试应覆盖真实公开入口／完整构建、校验、应用链，不能仅直接灌入内部状态就宣称集成通过。每项检查最终用户可见状态、确认结果和必要的持久化。

| 场景 | 通过条件 |
|---|---|
| “这个要问负责报名的老师” | 回答保存；未知仍在；下一轮遗漏也不丢失 |
| “先收姓名，联系方式等老师确认后再补” | 已知部分可提取，未确定部分仍明确保留 |
| 完整回答“仅收姓名和手机号，两项必填” | 经正常处理关闭目标 gap；同字段其他 gap 保留，未强制每项都再多调一次模型 |
| 非法或过期的 gap 更新 | 错误目标、伪造来源、迟到结果被拦截；状态与版本不被部分修改 |
| 混合编辑与失效候选 | 完整复现 C2 后冲突仍指向活动需求并阻止确认 |
| 真正解决冲突 | 对应矛盾消除后可以继续；部分解决不删除其他矛盾 |
| 跳过后没有新依据 | 同范围不得换句重复问；不同范围可以问 |
| 用户明确重开 | “现在可以聊网站受众了，请重新问我”使相应问题可重新询问，原历史仍在，预算不被绕过 |
| 伪造重开依据 | 模型 reason、自说自话的来源或无关新消息不能解除保护 |
| UI 正常闭环 | 输入 → 回答／跳过 → 继续分析 → 接受／编辑 → 必要复核 → 确认 → 保存重开可达，不出现只能靠手改 JSON 恢复的状态 |
| 历史功能回归 | 业务失败保留、原子接受、旧版本拒收、程序复核保留、依赖更新、截断与充分性门槛、详情展示保持正确 |

增加少量等价表达和顺序组合验证机制，不为每个中文同义词写专门分支。保留原测试覆盖；若语义修复使旧断言不再合理，例如“提交完整回答立即删除缺口”改为“分析确认对应信息已补足后关闭”，可更新断言但须说明原因并补正常路径，不能通过删测试或放宽校验制造全绿。

## 本轮目标

### 1. 把供应商、协议和将来的扩展路线说清楚

当前配置区分别展示：

- 供应商：当前为 DeepSeek。
- 协议：界面名称准确显示为“OpenAI Chat Completions”；可加简短说明“当前供应商按兼容接口方式调用”，不得让用户误以为请求发往 OpenAI 官方服务。
- API 地址、API key、模型 ID：仍按当前供应商配置。URL 和支持能力以该供应商实际接口为准。

协议是请求与响应格式，不是供应商。检查 UI 文案、代码常量、调用日志、错误文本和用户可见帮助。内部记录需要改名时，为历史 `deepseek_chat_completions` 记录提供只读兼容或版本映射，不重写旧调用证据，不伪称历史使用的是新的 ID。

未来可能分别支持 OpenAI Responses 和 Anthropic Messages，但它们只是路线图，不是本轮实现范围。只保留一个足以承载协议适配器的边界；不新增空实现、无用抽象或多协议选择器。此后增加其他协议必须各自实现并测试请求、响应解析、结构化输出能力、错误处理及供应商差异。不得把“OpenAI-compatible”当作所有供应商对所有端点均兼容的保证。

### 2. 为当前供应商读取可选模型列表

在现有连接设置中增加“获取模型列表”操作，使用当前供应商、API 地址及当前运行时 API key 请求该供应商实际支持的模型目录端点。保留可手工输入模型 ID 的路径；列表为空、接口不支持、鉴权失败、网络失败或响应格式不符时都不能卡死 UI，也不能让用户失去手工输入或使用已有模型 ID 的能力。

当前 OpenAI 官方 `GET /models` 文档列出 `id` 等模型标识字段：
https://developers.openai.com/api/reference/resources/models/methods/list

此文档只说明 OpenAI 端点。对 DeepSeek 或其他 OpenAI-compatible 供应商，必须核对实际服务能力和 base URL 规范，不得因协议标签相同就假设 `/models` 一定可用。若当前供应商的官方文档没有承诺该端点，应将获取列表作为“尽力尝试”的可选操作，按可理解错误返回，并保留手工输入；不得把模型列表内容硬编码为在线结果。

要求：

- 请求在后台线程运行；Tk 控件只在主线程更新。UI 明确显示加载、成功数量、空列表和失败状态，不阻塞窗口。一次获取在途时重复点击不并发提交。
- 请求绑定当前连接配置快照；期间 API 地址、供应商或 key 变化，旧列表不得写入新配置。返回结果不得自动覆盖用户期间手填的模型 ID，也不自动选中第一项。按供应商地址规范拼接目录端点，避免重复 `/v1` 或拼到 `/chat/completions` 后面。
- 列表只将真实返回的 model ID 填入可选控件；保留手工输入。不根据名字推断模型能力、访问权限、Chat Completions 支持度或 JSON 模式可用性。最终调用仍通过现有测试连接／实际请求验证。
- 不把 API key 放入日志、错误详情、请求记录、会话、导出或截图文字。不要改成持久保存密钥；不要照搬参考图里的 AES-GCM 存储、模型温度、最大输出、重试、配额、计费、Agent Model、启用开关等无关设置。
- 不发起真实付费 API 请求来验收，除非已有用户明确提供且授权的运行时配置。优先用本地 HTTP stub 测 `/models` 正常、空列表、401/403、404/不支持、超时、格式错误和 key 不泄漏。

### 3. 为文本编辑控件补齐右键辅助菜单

给常见可编辑文本控件提供平台可用的右键菜单，至少包括撤销（控件支持时）、剪切、复制、粘贴、全选；按控件状态禁用不适用动作。只读列表或结果区域仅提供合理操作（如复制所选文本），不可编辑区域不出现会误导的粘贴项。使用系统剪贴板和现有 Tk 控件能力，菜单位置跟随指针，不截断中文，不改变用户选区。已有 Ctrl+C/V/X/Z/A 快捷键继续工作。

不要逐个控件复制实现或引入外部 UI 框架。对输入框、任务多行文本、回答框、可编辑需求文本等当前实际控件做一次完整操作检查；Text/Entry 不同能力要分别处理。

### 4. 让用户一眼看出现在该做什么

现有窗口已有“下一步”文案，但用户仍会迷失。检查真实状态和布局，整理为每个状态只有一个清楚的主动作及简短原因；不要把按钮“分析/继续”当作永远通用答案。至少覆盖：无任务、连接配置缺失、正在请求、请求失败可重试、当前有待回答问题、候选待处理、受影响需求待复核、冲突未解、仍有待评估回答、需求可确认、需求已确认。M2 尚未实现时明确显示“需求已确认，初始方案功能待接入”，不要给出无效的进入按钮；M2 接入后再引导进入。步骤导航应显示当前所在步骤；未开放的步骤说明所需前置条件，不显示成可点但无操作的空页面。主动作突出，同时保留必要的修改、跳过、不确定和保存等次要操作。

建议是程序基于真实会话状态确定的导航文案和主按钮；模型的 `next_action` 和 `readiness` 仍只是内容建议，不能改变确认、版本、页面访问权限或自动触发调用。需求编辑、确认和冲突保护继续由程序负责。没有必要为显示一个主动作再增加一次模型调用。

### 5. 调查并处理“分析/继续”疑似反复分析

用户报告现象为“分析/继续疑似会进入死循环”，目前还不知道是界面重复提交、模型重复追问、状态无进展还是别的问题。先检查按钮绑定、busy/worker 生命周期、完成回调、自动重试、`remaining_rounds`、问题历史及现有日志，使用可重复的 fixture 或本地 HTTP stub复现。不要先假设模型在程序里递归调用，也不要仅改按钮文案。

明确实现并测试以下保护：

- 一次分析在途期间，重复点击不能创建并发请求；完成回调无论成功失败都恢复正确的按钮状态。
- 程序不自动无限重试或自动递归调用模型。网络重试次数有界且与追问轮数分离。
- 以当前契约的 `field + scope + gap_id` 及问题历史识别重复追问；同一缺口的已回答/已跳过问题不会因为换了措辞而重复出现，也不能通过新造 gap ID 绕过历史。不同子任务、不同缺口不能仅因 field 相同就一并封锁。新证据支持的必要细化或用户明确要求重开时沿用现有受控通路，仍须通过来源、依赖和预算校验。
- 分析结果没有新增有效需求候选、缺口状态变化、合规新问题或其他可见进展时，应明确提示“本轮没有形成新进展”，保留全部用户数据，不自动再次调用，并解释可编辑/补充什么后继续或如何手动重试。
- 可选地用本地输入快照与结构化输出比较识别重复结果；比较必须以 task/category/活动需求/缺口/答案/问题状态等业务内容为主，不使用整段 assistant_text 文本作为唯一指纹。不能因为“结果重复”就删除缺口、自动确认或无限阻止用户在显式修改后重新分析。
- 追问预算耗尽或用户选择跳过时，停止本轮自动追问，保留未知并提供编辑/复核路径；轮数上限不代表需求完成，不自动确认，也不暗中重置预算。
- 对 API 失败保留已有任务和需求，可显式重试。成功无进展与网络失败要区分，日志保存必要的状态差异和错误类型，不记录密钥。

如最终发现无实际无限循环，报告实际复现或未复现证据，并修复可明确说明的重复提问/重复提交体验，不要虚构已定位的根因。

### 6. 收紧窗口排布

以当前 Tkinter/ttk 结构为前提做定向版式改进：整体可读字号适度增大、任务输入和需求内容留足阅读面积、删掉造成大片空白的固定高度/多余留白，主动作位置稳定，长内容可滚动，调整窗口大小时布局伸缩合理。对 1120x780 及常见 125%/150% Windows 缩放作实际目视或可用性检查；不许文字、按钮、滚动区互相遮挡。无需追求网页式卡片视觉，不迁移 Qt/Web，不照抄参考图的管理后台结构。

用户提供的“智能体模型”截图只用于理解“清晰区分供应商、协议、API 地址、密钥、模型目录”的信息层级和简洁留白，不是功能清单或技术规范。除本提示明确要求的当前模型列表读取能力外，不新增截图中的费用、额度、并发、温度等设置；不增加 Agent/案例分析模型。

用户说“现在虽然有 Skill 界面，但还没有真正实现 Skill 功能”，本轮按原参赛方案理解为：把“已核验目录 → 关键工作匹配 → 候选解释 → 用户选择/跳过 → 方法整合 → 最终提示”做成真正可操作、可保存、可恢复、能影响最终输出的产品闭环。

### 2.1 固定产品流程

```text
输入任务
→ 推荐可修改的类别并提取已有信息
→ 针对关键缺口自然追问
→ 用户回答、跳过、修改或继续
→ 用户编辑并确认需求
→ 生成完整初始方案
→ 用户编辑并确认初始方案
→ 识别方案中的关键工作
→ 从本地已核验 Skill 目录筛选真实候选
→ 可选：AI 解释候选与适配关系
→ 用户选择、取消、逐项跳过，或全部跳过
→ 整合已选 Skill 方法；没有选择时生成无 Skill 结果
→ 用户复核最终方案和提示
→ 选择中性或适度礼貌语气
→ 复制、保存 JSON、导出 Markdown
```

M1 需求理解和 M2 初始方案必须先完成。Skill 只能在方案确认后出现，不能提前影响需求访谈或初始方案内容。

### 2.2 软件最终输出的层次

- 软件当前生成的是“方案和提示词”；
- 提示词要指导另一个 AI 完成用户任务，例如写讲义、写通知、做分析或开发软件；
- 软件在本阶段不直接替用户完成讲义、通知、报告或程序代码；
- 方案中的“交付物”和“完成标准”描述下游 AI 应完成的任务成果，不能把用户目标改成“只写一个计划”；
- 导出的提示词必须脱离旧聊天也能理解，不能出现“按之前说的”“采用第二版”等指代。

### 2.3 Skill 的产品含义

本阶段的 Skill 是**真实目录中已经核验过的工作方法记录**。产品要真正实现的是方法被匹配、选择、解释、整合并进入最终提示的闭环；它不是插件安装器，也不在本轮成为任意外部执行引擎。

程序应能：

- 从真实本地目录读取 Skill 记录；
- 根据已确认方案中的关键工作筛选候选；
- 明确显示候选为什么匹配、需要什么输入、会产生什么输出、适用于哪些步骤、有哪些前提和限制；
- 允许用户选择一个或多个具体方法，也允许取消选择或跳过整个 Skill 环节；
- 把已选方法转化成最终方案中的具体动作、输入、输出、检查点和必要的 fallback；
- 保存目录记录快照、来源哈希和选择依据；
- 目录变化、来源失效或方案变化时让旧选择失效，而不是静默继续使用；
- 没有合适候选时显示“没有找到合适的方法”，仍能完成无 Skill 的最终提示。

不能：

- 编造 Skill 名称、链接、能力、许可证、安装状态或执行结果；
- 只显示一串名称就称为推荐完成；
- 从网上临时搜索并把未经核验的网页内容当作可选 Skill；
- 自动安装、执行、发布 issue、调用外部工具或产生费用；
- 因为选择 Skill 就改变用户硬约束；
- 把 Skill 的建议直接变成用户已经确认的要求；
- 因为没有 Skill 或用户跳过 Skill 而卡住流程。

如果当前目录只有少量记录，先把已有真实记录做成完整可用闭环；目录扩充是后续工作，不要为了“看起来丰富”编造更多记录。当前目录已知只有少量已核验记录时，必须验证它们在匹配、选择、整合和导出中真实生效，而不是先扩充假记录。

## 3A. 四项新增设计的详细实现要求

### 3A.1 复杂度自适应追问

当前 `SessionState` 默认是 `max_questions=2`、`remaining_rounds=2`。这只能作为旧版本的默认值，不能继续被当作所有任务的固定上限。请把追问预算改成由程序根据任务复杂度、已识别信息和仍未解决的方向性缺口动态决定。

#### 复杂度判断

程序不需要建立复杂的通用决策树，但必须有可解释、可测试的轻量判断。至少使用以下信号：

- 是否只有一个主要交付物；
- 是否包含多个交付物或多个任务动作，例如“写活动方案并做汇报 PPT”；
- 是否涉及多个类别或混合类别；
- 是否存在影响任务方向的未知目标、受众、范围、输入材料、评价标准或关键限制；
- 是否存在冲突或需要用户决定的解释；
- 已识别的关键工作数量；
- 用户输入是否已经给出清晰的目标、交付物和硬约束。

建议使用三个用户不可见或弱显示的内部等级：`simple`、`medium`、`complex`。等级只是预算依据，不得变成要求用户先理解的专业分类。

#### 预算建议

以下是实现参考，必须以当前未解决问题为准，不能机械凑满：

| 复杂度 | 建议最多追问数 | 建议最多轮数 | 使用原则 |
|---|---:|---:|---|
| simple | 0—2 | 1 | 已知信息足够时直接进入需求复核，不为了使用预算而提问 |
| medium | 2—4 | 1—2 | 只补会影响交付方向或质量标准的问题 |
| complex | 4—6 | 2—3 | 按依赖逐轮补齐多个交付物、关键工作或硬约束；每轮仍只给少量最重要问题 |

预算必须保存在会话状态中，例如：

```json
{
  "complexity": "medium",
  "complexity_basis": ["存在两个交付物", "受众尚未明确"],
  "question_budget": {
    "max_questions": 4,
    "max_rounds": 2,
    "questions_asked": 1,
    "rounds_used": 1,
    "budget_revision": 1
  }
}
```

要求：

- 模型每次只返回当前最重要且有依赖关系的问题；程序根据真实返回数量更新计数；
- 如果没有方向性缺口，即使复杂度为 `complex` 也不得继续追问；
- 已知信息不得重复询问；已回答、已跳过和已明确不确定的问题不能无新依据重复出现；
- 前提未知时，不连续追问依赖它的细节；
- 用户一次回答多个问题时，一轮只增加一次，逐项登记来源和处理状态；
- 用户选择跳过时，可以把该项转为未决事项并继续，不得把流程卡死；
- 达到预算不等于需求完成。若仍有方向性缺口，明确标记影响，并允许用户选择“先整理草稿”或继续补充；
- 预算在任务类别、目标、交付物或关键约束改变后重新评估，但不得让已经解决的问题重新出现；
- UI 只用自然语言提示，例如“还需要确认 1 个会影响结果的问题”，不要把 `remaining_rounds`、`budget_revision` 等内部字段直接展示给用户；
- 程序是预算和结束状态的唯一维护者，模型返回的 `next_action` 不能直接强制进入下一步。

结束条件应同时检查：目标和下游交付物已识别、硬约束已登记、关键方向缺口已解决或明确保留、冲突已处理或可见、未知项有影响与后续确认时点。满足这些条件时，简单任务应快速进入需求确认，复杂任务才继续必要追问。

### 3A.2 最终提示必须重新编排

当前 `render_task_prompt()` 只是给完整方案正文加一句开头。请不要继续把 `render_canonical_body()` 的内部正文直接当作最终提示。

必须把“内部完整方案”和“给下游 AI 的可执行提示”分成两个视图：

- **内部方案视图：** 可以保留来源、需求 ID、关键工作 ID、步骤依赖、版本、审核信息，供程序、用户复核和审计使用；
- **最终提示视图：** 从当前有效的结构化内容重新投影，面向另一个 AI，简洁、专业、独立可读，不暴露内部编号和审计字段。

最终提示建议按以下自然结构生成，具体段落可根据任务复杂度增减：

```text
你要完成的任务
目标与交付物
已确定的要求和硬性限制
已有材料与可用输入
建议的工作步骤
完成后应交付什么
检查标准
仍不确定的信息及处理方式
不能擅自补充或假设的内容
```

要求：

- 保留用户事实、用户决定、硬约束、未知项和所选 Skill 方法的实际作用；
- 把步骤依赖改写成人能直接执行的顺序，不出现 `s1`、`k1`、`requirement_id`、`binding_id` 等内部字段；
- 不输出来源原话、目录 hash、版本号、审计状态、模型调用记录或程序状态；除非用户本身要求这些内容成为下游交付物；
- 不把“方案”改写成“只做计划”。如果用户要活动方案和汇报 PPT，最终提示必须同时要求产出活动方案和汇报 PPT；如果用户要学生讲义，最终提示必须要求讲义，而不是只要求讲义大纲；
- 中间交付物可以写进步骤，但不能替换最终交付物；
- 用户未提供的信息写成自然的未决说明和处理规则，不突然丢出孤立的“待补充”；
- 语气切换只改变开头和少量礼貌表达，不改变正文事实、范围、约束、步骤、交付物和标准；
- 简单任务的提示应短而完整，复杂任务的提示可以更详细，但不得重复内部方案整段内容；
- 最终提示正文需要独立可复制到另一个 AI 窗口使用，不依赖旧聊天。

建议新增明确的渲染函数或等价职责：

```text
render_internal_plan(content)      # 内部完整方案
render_prompt_projection(content)  # 面向下游 AI 的重新编排
render_task_prompt(projection, tone)
```

最终结果至少保存 `prompt_body`、`prompt_hash` 或等价字段，与内部 `canonical_body` 分开。正式导出和复制默认使用最终提示投影；用户需要查看审计细节时再展开内部方案。

### 3A.3 界面收敛成一个主流程

当前界面把“当前需求—方案—Skill—结果”放在多个并列区域，复杂任务时容易让用户不知道现在处在哪一步。请沿用现有 Tkinter/ttk 和滚动、右键、字体能力，做必要的结构收敛，不另起全新 UI 框架。

目标是一个主工作区、一个当前阶段、一个主要动作：

```text
顶部：任务进度（需求 → 方案 → 方法 → 提示）
中部：当前阶段的主要内容
底部：一句自然的下一步说明 + 一个主按钮
次级：返回、保存、查看详情、复制、导出等放进次级按钮或折叠区
```

具体要求：

- 默认不要让四个页面像四个并列任务一样同时争夺注意力；可保留内部页面，但只突出当前阶段，其他阶段以状态或次级入口显示；
- 在需求阶段，主动作只能是“整理需求”“继续补充”或“确认当前需求”中的一个，由当前状态决定；
- 在方案阶段，主动作只能是“确认方案并继续”或“返回修改需求”；不要同时突出“确认方案并查找 Skill”等把后续实现细节塞进按钮的长句；
- 在方法阶段，主动作只能是“生成最终提示”；选择、取消、查看详情和跳过是辅助操作；
- 在结果阶段，主动作是“复制提示”或“保存/导出”，不再让用户猜测是否还要回到前面；
- Skill 页面只在初始方案确认后出现。简单任务没有合适候选时，应直接给出“没有找到合适的方法，可以直接生成最终提示”，不要强迫用户进入复杂页面；
- 复杂任务才展开关键工作、候选和方法前提；简单任务默认折叠详细说明；
- `返回当前需求`、`确认方案并查找 Skill` 等动作改成符合当前上下文的自然短语；
- 不同时显示多个“下一步”按钮；
- 页面语言统一使用“当前需求”“初始方案”“可用方法”“最终提示”等稳定词语，不在同一功能中混用“需求版本”“模型候选”“方法包”等不同叫法；
- 任何失败、跳过和无匹配状态都必须在当前页面给出下一步，不弹出只有错误信息而没有操作出口的对话框；
- 保持现有 12pt 左右字体、滚动和右键辅助功能，减少空白和过多并列框，不为了重排而改变业务状态。

### 3A.4 复杂任务必须指向真实最终成果

M2、M4、最终提示和导出都要增加“最终交付物保持”检查。

程序和模型都必须区分：

- 用户真正要交付的成果；
- 为完成该成果而设计的步骤、计划、草稿和检查记录。

例如：

- “设计校园活动方案，并做一份汇报 PPT” → 最终交付物至少有活动方案和汇报 PPT；
- “写一篇面向新生的讲义” → 最终交付物是讲义，不是“讲义写作计划”；
- “分析销售数据并生成图表” → 最终交付物包括分析结论和图表/可视化结果；
- “开发报名系统” → 最终交付物是系统实现及必要的测试/说明，而不是只生成需求规格计划。

实现要求：

- M1 将多个明确交付物分别登记，不能只保留一个主类别字段；
- M2 的 `goal`、`deliverables`、`completion_criteria` 必须覆盖用户原始交付物；
- 至少保留 `downstream_deliverables` 或等价程序字段，标明哪些是用户最终要得到的成果；
- 如果方案只有“计划、步骤、大纲、检查表”等元级产物，却没有用户要求的下游成果，程序校验失败或把该项标为需要重新生成；
- M4 只能补充方法，不得把最终交付物替换成 Skill 的中间产物；
- 最终提示投影必须把用户真正要的成果放在开头和交付要求中；
- 导出 Markdown 可以同时展示“方案”和“最终提示”，但标题要让用户看出最终提示是交给下游 AI 的正文。

为此新增至少两类回归案例：

1. 单一简单写作任务：少量追问，短提示，直接得到用户要的通知/短文提示；
2. 混合复杂任务：活动方案＋汇报 PPT，允许更多必要追问，但最终方案和提示必须同时保留两个交付物。

## 4. 本轮实现范围

按以下顺序实施，保持范围集中，不做无关重构。

### S0：现状审计和最小设计

1. 确认当前 UI 中 Skill 入口、按钮、页面和状态变量分别对应什么；
2. 确认当前 `skill_catalog.py` 是否能加载、校验、筛选真实记录；
3. 确认 `delivery_workflow.py` 是否真正调用 M3/M4，还是只使用 fixture、空回调或局部占位；
4. 确认 `finalization.py` 是否把选择的方法落进最终正文；
5. 确认保存和重开是否保留候选批次、选择、目录快照、最终结果及失效原因；
6. 确认 `render_task_prompt()` 是否仍直接复制内部方案正文；如果是，单独列为必须修复项；
7. 确认当前追问预算、复杂度判断和用户可见文案，不能只看 `max_questions` 的默认值；
8. 确认多个并列页面和主按钮是否造成用户无法判断当前步骤；
9. 用一个简单任务和一个包含多个交付物的复杂任务做现状回放；
10. 不改变已通过的 M1/M2 需求访谈逻辑，除非某个接入缺陷直接阻止完整流程。

### S1：统一会话状态和版本失效

如现有实现已有等价字段，沿用现有字段；不要重复建两套权威状态。至少保证下面语义成立：

```json
{
  "delivery_revision": 0,
  "skill_state": {
    "revision": 0,
    "status": "not_started",
    "basis": null,
    "candidate_batch": null,
    "bindings": [],
    "last_error": null
  },
  "final_result": {
    "status": "not_started",
    "revision": 0,
    "confirmed_revision": null,
    "basis": null,
    "content": null,
    "canonical_body": null,
    "body_sha256": null,
    "tone": "neutral",
    "review_required_ids": [],
    "unapplied_edits": []
  },
  "complexity": "simple",
  "complexity_basis": [],
  "question_budget": {
    "max_questions": 2,
    "max_rounds": 1,
    "questions_asked": 0,
    "rounds_used": 0,
    "budget_revision": 1,
    "reason": "由程序根据当前任务动态计算"
  },
  "downstream_deliverables": []
}
```

必须保证：

- 需求、类别、初始方案、关键工作改变后，旧 Skill 候选、选择和最终结果变为 stale 或被明确清理；
- 目录记录变化、来源文件缺失或哈希不一致后，相关绑定失效；
- Skill 选择发生变化时递增 `skill_state.revision` 和必要的 `delivery_revision`；
- 纯语气切换不改变语义版本和正文 hash；
- 成功的 M3/M4 只能生成草稿，不能自动确认；
- 失败调用不能清空已有有效结果，不能把旧结果伪装成新结果；
- 迟到回调不能写入新会话或新版本；
- 保存重开后状态、按钮和下一步入口一致。

追问预算必须从旧的固定字段迁移到可解释的动态字段。简单任务保持小预算，复杂任务才允许更多轮次；预算不能由模型自行提升，也不能为了“用满额度”提问。

旧会话必须显式迁移：旧的 `selected_skills` 字符串不能自动当作新版有效绑定，应该保留为待重新选择的历史信息。

### S2：实现真实本地 Skill 目录闭环

#### 目录读取

- 使用 `resources\skill_catalog\catalog_v0.1.json` 及其真实来源记录；
- 校验 schema、唯一 `skill_id`、记录 hash、来源路径、来源快照 hash、能力、输入、输出、前提和适配边界；
- 不能因目录错误返回 `no_match`。目录错误、来源缺失、来源 hash 不匹配应显示可理解的错误并保留手动继续/跳过入口；
- 程序打包和源码运行都使用 `paths.py` 的资源定位方式，不能写死开发机绝对路径；
- EXE 内如果只有目录摘要，必须按当前发行策略检查，不得声称原文已随包安装。

#### 关键工作匹配

输入必须来自用户已确认的 M2 方案，不使用未确认需求和旧方案。每个关键工作至少包含：

- `key_work_id`
- 标题和目标
- 关联步骤
- 输入
- 输出
- 检查点
- 当前任务语境

匹配结果必须按关键工作分组，至少包含：

- `candidate_id`
- `skill_id`
- `record_hash`
- `record_snapshot`
- `key_work_id`
- `step_ids`
- `match_score`
- `match_reason`
- `matched_work_signals`
- `match_evidence`
- `selection_allowed`
- `compatibility`
- `adaptation_prerequisite_ids`
- `limitations`

匹配理由要区分来自“关键工作”和“任务描述”的依据。不能因为任务类别相同或名称相似就推荐。

#### M3 AI 候选解释

只有用户点击“分析这些方法”或等价按钮时才调用 M3。目录筛选本身不冒充 AI 推荐。

M3 输入只能包含程序筛出的真实候选及其记录快照。模型只能引用 `candidate_id`，不能生成新的 Skill。正常结果需要说明：

- 对应哪一个关键工作和步骤；
- 具体能力如何帮助该工作；
- 需要哪些输入；
- 预计产出什么；
- 需要哪些前提；
- 哪些前提未知；
- 是否可以只做方法适配；
- 有哪些限制和 fallback；
- 为什么不推荐其他候选，或者为什么无匹配。

模型不得设置 `selected`、`confirmed`、`installed`、`execution_status` 等程序状态。

M3 失败、超时、截断或结构无效时：

- 保留目录候选；
- 显示“AI 解释失败，仍可根据目录信息选择或跳过”；
- 不自动重试；
- 用户明确点击后才允许再次请求；
- 不阻断无 Skill 路径。

### S3：实现用户选择、取消和跳过

UI 操作要围绕用户当前问题设计，避免多余页面和专业化词语。

推荐文案：

- 页面标题：`可用方法`
- 说明：`下面的方法来自本地已核验目录，只会在对应工作中提供参考。你可以选择、取消，或跳过这一步。`
- 候选按钮：`选择这个方法`
- 已选按钮：`取消选择`
- 整体按钮：`跳过方法选择`
- 继续按钮：`生成最终提示`
- 无匹配：`没有找到合适的方法，可以直接生成不使用 Skill 的提示。`

避免使用“模型候选”“方法包”“精简重试本轮”等没有上下文铺垫的词。一个页面只突出一个下一步动作；跳过后应明确告诉用户“将直接生成不使用 Skill 的最终提示”。

选择规则：

- 选择只能来自当前候选批次；
- 只能选择 `selection_allowed=true` 的候选；
- 可针对不同关键工作选择不同方法；
- 同一 `(skill_id, key_work_id, usage_mode)` 不能重复绑定；
- 选择后显示方法、对应工作、来源和前提；
- 取消选择后不得在最终结果中残留其贡献；
- 全部取消等同于无 Skill 路径，但应保留用户操作记录；
- 跳过不清空方案，也不让流程卡住；
- 如果某个方法前提未知，用户可以保留为条件性草稿，但最终确认前必须存在可执行 fallback，或明确取消该方法。

### S4：实现 M4 方法整合

M4 只接收：

- 已确认需求快照；
- 已确认初始方案；
- 当前用户明确选择的绑定；
- 对应目录记录快照和关键工作；
- 真实前提状态。

M4 不得重写整份基线方案。程序负责保留基线，模型只返回每个选中绑定的增量。

每个方法增量至少包含：

- `binding_id`
- `key_work_id`
- `step_ids`
- 具体方法动作
- 需要的输入
- 预期输出
- 检查点
- 前提判断
- fallback
- 新增范围或成本变化（如有，必须标记待确认）
- 与用户硬约束的兼容性

整合结果必须落到最终方案和最终提示的具体段落/步骤中。例如“使用 to-spec”不算完成；必须写成“在需求已确认后，按问题陈述、用户故事、实现决定、测试决定整理规格，并输出哪些文件/文本，检查什么”。

M4 处理规则：

- 不得新增用户没有确认的预算、日期、权限、技术选型、发布动作或工具依赖；
- 不得把 Skill 原文中的安装、issue 发布、命令执行变成软件动作；
- 方法与硬约束冲突时返回冲突，不替用户决定；
- 前提未知但存在合法 fallback 时，标为条件性方法并保留影响；
- 没有合法 fallback 时，不能确认该方法已整合，但仍可取消它并完成无 Skill 结果；
- 用户拒绝某一项变化后，依赖该变化的动作必须停止或切换到明确 fallback；
- M4 失败不覆盖以前的最终草稿；
- M4 成功后最终结果只能是 `draft`，等待用户确认。

### S5：无 Skill 路径必须完整可用

以下三种情况都要进入同一个无 Skill 结果路径：

1. 目录没有候选；
2. 用户主动跳过；
3. 用户选择后全部取消。

无 Skill 结果必须包含：

- 原任务和类别；
- 已确认需求；
- 初始方案和关键工作；
- 未决事项及影响；
- 系统建议与用户尚未决定的内容；
- 完整的下游任务步骤、交付物和完成标准；
- 可独立使用的最终提示词。

无 Skill 路径不额外调用模型，不显示“缺少 Skill 所以不能继续”。

### S6：最终方案和任务提示

使用一份结构化最终内容作为唯一来源，再分别渲染内部方案和面向下游 AI 的提示投影：

- 内部最终方案预览；
- 面向下游 AI 的重新编排提示预览；
- 中性提示词；
- 适度礼貌提示词；
- Markdown 导出。

语气切换只能改变开头包装和极少量礼貌表达，不得改变：

- 用户事实；
- 用户决定；
- 硬约束；
- 未知事项；
- 方案步骤；
- 交付物；
- 完成标准；
- Skill 方法、前提、fallback 和检查点。

增加程序校验：最终提示中必须出现用户真正的下游交付物；不能只出现“计划、步骤、方案设计、检查清单”等元级产物。如果检测到最终提示只描述如何规划用户任务而没有要求完成用户成果，阻止确认并给出“需要重新整理最终提示”的可操作入口。

最终提示必须明确告诉下游 AI：

- 要完成什么；
- 依据哪些已确认要求；
- 哪些信息仍未知；
- 不能自行补什么；
- 应按什么步骤工作；
- 输出什么；
- 如何检查完成；
- 遇到冲突或缺口时先指出，不要默默编造。

最终提示默认不包含内部编号、来源原话、目录 hash、版本号、审计状态、模型调用记录或程序状态。内部方案仍可保留这些信息，供程序和用户展开查看。

### S7：保存、重开、导出和失败恢复

必须测试并实现：

- 保存 Skill 候选批次、目录 hash、来源快照、M3 结果、用户选择、取消和跳过记录；
- 保存复杂度等级、预算依据、已用问题/轮次和动态预算版本；
- 保存内部最终方案、重新编排后的 `prompt_body`、提示 hash、语气和确认状态；
- 重开后恢复正确页面和下一步按钮；
- 需求或方案变化后显示旧结果已过期并要求重新筛选；
- 目录记录变化后旧绑定进入 stale，不静默使用；
- M3/M4 失败保留已有内容；
- 超时、截断、迟到返回不进入正式结果；
- Markdown 导出独立可读，不依赖聊天上下文；
- 导出文件默认展示“最终提示”正文，内部审计信息放在可选的方案说明区，不把编号和来源堆进提示正文；
- 不在会话 JSON、日志、导出或 EXE 中保存 API Key。

## 5. 程序与模型的职责边界

### 程序负责

- 当前任务、类别、需求和方案版本；
- 用户确认、拒绝、编辑、选择、取消、跳过；
- 候选来源、目录 hash、记录快照和绑定；
- 版本失效、请求身份、并发和迟到保护；
- 失败、超时、截断和用量日志；
- 保存、重开、导出、权限和密钥生命周期；
- 是否允许进入下一步骤。

### 模型负责

- 从输入快照提出候选解释、匹配理由和方法增量；
- 说明适用范围、前提、限制和 fallback；
- 保留未知和冲突；
- 生成自然的说明文字；
- 严格输出 Schema JSON。

模型任何字段都不能直接改变程序确认状态。即使模型写“用户已确认”“Skill 已安装”，程序也只能把它当普通文本或判为无效。

## 6. 必须补齐的测试矩阵

不要只运行原有测试。根据实际代码增加或修改测试，至少覆盖以下场景。

### 6.1 目录和匹配

1. 正常加载真实目录；
2. 目录为空，返回 no_match；
3. 目录 JSON 损坏，返回目录错误而不是 no_match；
4. 来源文件缺失；
5. 来源 hash 不一致；
6. 关键工作匹配正确的候选；
7. 只有任务描述命中但关键工作不满足时不误推荐；
8. 候选与宿主或禁止动作冲突；
9. 多个关键工作对应不同候选；
10. 单个候选重复选择被拒绝。

### 6.2 M3

1. 正常候选解释只引用真实 `candidate_id`；
2. 模型编造候选 ID 被拒绝；
3. 模型编造链接、许可证、安装状态被拒绝或忽略；
4. no_match 仍可继续；
5. M3 截断、超时、HTTP 错误和 Schema 错误都可恢复；
6. M3 失败不清空目录候选。

### 6.3 选择、取消、跳过

1. 选择一个候选后状态正确；
2. 取消后最终结果没有残留贡献；
3. 全部跳过进入无 Skill 路径；
4. 没有候选时直接继续；
5. 跳过、保存、重开后仍能继续生成最终提示；
6. 选择不允许的候选被程序拒绝；
7. 选择后修改方案，旧候选失效。

### 6.4 M4 和最终结果

1. M4 只生成选中绑定的增量；
2. M4 不能删除或弱化基线要求；
3. 新增范围需要待确认；
4. 前提未知但有 fallback 时可形成条件草稿；
5. 没有 fallback 时不能确认；
6. 取消绑定后其贡献和依赖编辑被移出当前正文但保留历史；
7. 无 Skill 方案完整可确认；
8. 语气切换不改变正文 hash；
9. 最终提示包含下游任务目标，而不是把任务改成“只写计划”。

### 6.5 UI 和发行链

1. 用户从输入任务到导出提示能走完；
2. 每个阶段只有清晰的下一步；
3. 跳过不会卡死；
4. M3/M4 失败后按钮恢复；
5. 不会自动循环调用；
6. 保存重开状态一致；
7. 源码启动和项目外单 EXE 启动一致；
8. EXE 内当前提示、Schema 和关键代码与源码版本一致；
9. `--smoke-test` 退出码为 0；
10. 不把真实 API Key 打进日志、JSON、证据或 EXE。

### 6.6 新增的复杂度、提示投影和混合交付物测试

1. 简单任务没有方向性缺口时不发起多余追问；
2. 简单任务的追问预算不被统一扩大到复杂任务的上限；
3. 中等任务可以在需要时增加一轮，但不重复已回答问题；
4. 复杂任务在多个交付物和方向性缺口存在时获得更高预算；
5. 复杂任务达到预算后仍保留未决项和影响，不把需求标成全部完成；
6. 用户一次回答多个问题时，程序正确登记多个来源而不额外增加轮次；
7. 最终提示不包含 `requirement_id`、`step_id`、`key_work_id`、`binding_id`、目录 hash 或来源审计字段；
8. 最终提示包含用户真正的下游交付物，而不是只包含计划或大纲；
9. “活动方案＋汇报 PPT”经过 M1、M2、M4、导出后仍有两个最终交付物；
10. “讲义”任务的最终提示要求生成讲义正文，不会被替换成讲义工作计划；
11. 语气切换只改变包装，不改变重新编排后的提示正文 hash；
12. 内部方案仍可查看完整来源和审计信息，但复制/导出的默认提示保持简洁；
13. 用户在单主流程中不会同时看到多个同等级“下一步”按钮；
14. Skill 无匹配、跳过和 M3 失败时仍能从当前页面生成最终提示；
15. 保存重开后复杂度、预算、当前阶段、最终提示投影和主按钮状态一致。

## 8. 完成标准

只有同时满足以下条件，才可以向用户报告“本轮实现完成”：

- 用户无需选择 Skill 也能生成、确认、复制、保存和导出最终提示；
- 有真实目录记录时，程序能按关键工作给出候选并保留来源；
- M3 真实调用路径已接通，且模型不能创造候选或改变程序状态；
- 用户可以选择、取消和跳过，选择结果真正影响最终方案；
- M4 真实调用路径已接通，且只返回已选方法的增量；
- 方法增量真正落入最终方案和提示的具体步骤、输入、输出和检查点；

- 目录错误、无匹配、前提未知、失败、截断、超时和迟到返回都有可恢复路径；

- 新 EXE 构建、烟测和项目外业务链通过；

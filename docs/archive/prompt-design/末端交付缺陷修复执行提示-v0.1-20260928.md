# 末端交付缺陷修复执行提示 v0.1

用途：把本文完整复制到另一个开发对话，让开发模型在当前仓库内直接完成本轮修复、测试、构建和交接。本文件是执行指令，不是实现结果证明。开发模型必须根据实际代码调整文件名和调用点，并在报告中写明映射。

## 0. 任务目标

项目根目录：

    C:\Users\yph\Documents\ChatGPT\aicomp

上一轮末端交付已经接通了无 Skill 路径、目录候选、M3/M4 结构和导出链，但独立验收发现几处状态一致性缺陷。本轮只修复这些已确认缺陷，目标是：

1. 用户拒绝 M4 变化后，依赖该变化的动作不能继续被确认或导出；有合法替代方案时要真正使用替代方案，没有替代方案时必须进入待处理状态。

3. 每轮 M4 生成拥有独立身份。上一轮的 pending、accepted、rejected 决策不能误套到新一轮同名变化上。
4. 正常 v0.2 会话重开不能把当前 selected_skills 镜像误报为旧 v0.1 遗留选择。
5. 普通非软件任务不能只因出现“需求”等弱词就被错误推荐软件 Skill。
6. Skill 目录补齐已有调研记录支持的来源信息，并区分来源记录、本地正文核验、依赖可用性和实际执行验证。
7. 交给另一个 AI 的 canonical body 必须包含已确认关键工作和 requirement coverage，不只在内部 JSON 中保留。
8. 尚未生成最终草稿时不能导出空的“最终/草稿”文件；M4 复核和覆盖导出要能从 UI 完成。

执行模型必须直接完成实现和验证，不只提交计划，不在第一项完成后询问是否继续。

## 4. 必须保持的数据不变量

实现可以沿用现有等价字段，但必须满足以下语义。字段名不同要在映射文档中说明。

### 4.1 来源与版本

最终结果的 basis 至少能追溯：

- task_id
- requirement_version
- plan_id、plan_version
- selection_revision
- 当前生效的目录记录 hash
- 当前生效的 Skill binding id

最终结果还需要一个单调的最终内容或交付版本，用于防止用户编辑、建议决定变化后旧 M4 返回覆盖新状态。纯 tone 切换可以不增加语义版本。

M4 请求的上下文至少捕获：

- session identity 或 session generation
- generation_request_id
- delivery revision
- selection revision
- final content/decision revision
- 方案和关键工作版本
- 当前 binding 快照及 record hash

apply 前必须逐项比对。连接从 A 改成 B 再改回 A、同一文件重开、用户在等待期间编辑附注或接受/拒绝建议，都不能让旧响应重新生效。

### 4.2 M4 变化的身份和决定

每个 M4 生成都是一个独立 generation_request_id。变化唯一身份使用：

    (generation_request_id, change_id)

首次接收模型返回时由程序把本轮变化初始化为 pending。模型不能返回 accepted 或 rejected 作为最终决定。

每条变化至少保留：

- change_id
- generation_request_id
- title/description
- affected binding_ids 或 key_work_ids
- proposed scope/cost change
- dependency references
- legal fallback（若有）
- decision：pending、accepted、rejected
- decision source、time、reason

旧一轮的 decision 不能按 change_id 字符串自动套用新一轮。旧一轮已经 accepted 的内容只有在其 origin binding 仍然生效、来源仍然有效并且被明确保留时才能进入新草稿；它不能再次作为本轮 pending 变化追加。旧 pending 和旧 rejected 必须归档或保持明确的历史状态，不得悄悄变成新一轮 accepted。

### 4.3 绑定和贡献归属

每个 Skill 派生方法、method_action、accepted_addition、fallback 和待处理变化都保留 origin_binding_ids。取消一个 binding 时重新计算仍存活的依赖：

- 只服务被取消 binding 的内容撤下；
- 仍被其他 binding 使用的共享内容保留；
- 独立的用户附注保留；
- 需要多个 binding 才成立的贡献，如果依赖集合不再完整，必须停用或回到待处理，不能假定仍然可用。

原版 Skill 前提与本期方法适配前提分开保存。原版需要 issue tracker、特定宿主、命令或模板，不代表本期已经具备这些能力。只有 adaptation_prerequisites 影响本期 method_adaptation 的可用性；原版不可执行时要显示为边界和限制。

### 4.4 确认门槛

review_required_ids 只记录程序已识别、用户有明确操作入口的阻断项，不要把所有未知事项或所有未采纳建议都塞进去。

confirm_final() 至少检查：

- 当前基线、binding 和目录记录仍有效；
- canonical body 结构完整；
- 所有本轮阻断变化已接受、拒绝并完成 fallback，或已取消相关 binding；
- 依赖已拒绝变化的 method_action 不再生效；
- 没有未保存的用户编辑；
- 没有待用户处理的 review_required_ids；
- 可暂缓的未知项和独立未采纳建议不会被伪装成确定要求。

失败时返回可解析的阻断原因，不能只返回 False 或让 UI 静默不动。

## 5. P1 修复一：拒绝 M4 变化必须改变生效内容

当前已知问题：src/promptsmith/finalization.py 的拒绝逻辑只记录 rejected，却仍让依赖该变化的 method_actions 出现在 canonical body，随后还能 confirm/export。

按以下语义修复：

1. 找出每个 method_action、步骤、检查点和新增范围的 origin/change 依赖。不要通过搜索 Skill 名称或正文字符串判断依赖。
2. 用户拒绝变化时：
   - 若变化有合法 fallback，停用被拒绝的动作并应用 fallback；
   - 若没有合法 fallback，停用依赖动作并创建明确的阻断复核项，或要求用户取消相关 binding；
   - 不得把被拒绝的新增范围留在无条件执行步骤中；
   - 不得自动改写用户硬约束。
3. 取消变化决定或重新选择 binding 时，从 baseline 加上仍生效的 binding contributions 和已接受变化重新组装，不要对旧正文做脆弱的字符串删除。
4. 重开会话后继续保持 rejected、停用动作和 fallback 的关系。
5. UI 中清楚显示：变化是什么、受影响的动作是什么、fallback 是什么、没有 fallback 时下一步是取消 binding 还是回上游修改。接受和拒绝必须是实际可用的控件。
6. 增加测试覆盖：接受、拒绝有 fallback、拒绝无 fallback、撤销决定、取消 binding、保存重开、拒绝后 confirm/export。

验收要求：构造一个 method_action 明确引用 change-1 的案例，拒绝 change-1 后 canonical body 不得出现该 action；有 fallback 时必须出现 fallback；无 fallback 时 confirm_final() 和正式导出必须失败并给出阻断理由。

## 6. P1 修复二：正式导出写入前重新验证

当前已知问题：src/promptsmith/exporter.py 只看 status 和 confirmed_revision。确认后方案来源变化、最终结果未及时标 stale 时，仍能写出“最终版本”。

实现以下门槛：

1. 导出区分 draft 和 final：
   - not_started 没有正文时，两者都不能写入“暂无正文”的伪文件；
   - draft 只能导出已有草稿，并醒目标为草稿/待确认；
   - final 只能导出当前已确认且校验通过的结果。
2. formal/final 导出在真正写文件之前重新调用等价于 validate_current_final(..., require_confirmed=True) 的完整校验。校验必须发生在文件选择对话框结束后、覆盖确认后、原子写入前，因为等待对话框期间会话可能变化。
3. 校验至少包括 basis、plan/requirements version、selection revision、binding record hash、canonical body hash、change decisions、review_required_ids、用户编辑保存状态。
4. 失败时不写文件，保留用户已有文件和当前编辑内容，并在 UI 显示具体原因。
5. 覆盖已有文件必须是显式用户决定；UI 不得永久传 overwrite=False 导致用户无法覆盖，也不得无确认覆盖。取消覆盖应保留原文件。
6. 对 exporter 直接调用和 UI 成功路径都增加测试。测试中模拟“打开文件对话框后修改方案/决定”，确认正式写入被拒绝。

## 7. P1 修复三：重复 M4 生成按轮次隔离

当前已知问题：重建草稿时继承上一轮 accepted_additions、pending_changes 和 change_decisions，再追加新变化；复用 change_id 时会产生重复 UI ID 和无法定位的决定。

实现要求：

1. 每次 prepare/invoke/apply 都生成新的 generation_request_id。请求身份不能只依赖随机字符串，还必须绑定当前 session、版本快照和单调 revision。
2. 新一轮草稿从当前 baseline、当前仍生效 binding、明确仍生效的历史 accepted contributions 重新组装。不要把上一轮 pending/rejected 决定原样复制到本轮。
3. 新一轮 proposed_changes 和 change_decisions 使用本轮 generation_request_id 命名空间。即使模型返回同一个 change_id，也必须是另一条独立记录。
4. 旧轮次归档保留，至少记录 generation id、输入 basis、raw/解析结果、决定和失效原因；当前结果只引用当前轮。
5. 用户在 M4 等待期间修改建议决定、用户附注、binding 或上游方案时，旧响应必须拒收且不能覆盖新内容。
6. 处理中重复点击不能发出相同请求；取消后迟到响应不写入。
7. 增加 A→B→A 选择、同名 change_id 两轮生成、保存重开、旧响应迟到和重复点击测试。

## 8. P2 修复：v0.2 会话迁移和状态恢复

当前已知问题：session.py 对所有版本都把 selected_skills 加入 legacy_selection_unresolved。v0.2 中该字段是 bindings 的兼容镜像，正常重开也会产生旧遗留警告，跳过 Skill 甚至变 stale。

迁移规则：

1. 只对真正的 v0.1 会话执行旧字符串选择迁移。旧字符串只能作为历史展示或待人工绑定，不能自动成为已确认 binding。
2. v0.2 会话以 skill_state/bindings 为权威来源。selected_skills 若存在，只验证它是否等于 bindings 的唯一 skill_id 镜像；不再生成 legacy_selection_unresolved。
3. skipped、no_match、candidates_ready 等合法状态重开后保持原状态，不因镜像字段存在而 stale。
4. 缺字段、记录 hash 不一致、未知未来版本或损坏缓存要降级为待复核/拒绝加载，并保留原始内容；不能静默补成已确认。
5. 增加 v0.1 旧字符串、正常 v0.2 selected_skills 镜像、v0.2 skipped、损坏 bindings、目录记录变更和未来版本测试。

### 9.2 弱关键词误匹配

1. 使用关键工作标题、任务类别、输入输出和具体动作的组合语境，不让一个通用子串直接达到可选门槛。
2. 软件规格、领域建模、特定宿主持续执行目标的候选，必须分别有对应工作类型和必要前提。
3. 普通通知、学习笔记、营销文案等任务不得因为出现“需求、方案、整理”等通用词自动命中软件 Skill。
4. 无足够匹配时返回 no_match；不要为了让页面有候选而降低门槛。
5. 候选数量限制、排序、selection_allowed 和 mismatch reason 要有单元测试。

至少覆盖：

- 社团摄影招新通知：no_match；
- 已确认的软件报名系统规格整理：to-spec 可候选，并解释具体对应；
- 领域术语/实体关系工作：domain-modeling 可候选；
- 只想写一份通用执行清单：goal-prompt 不能因“目标”一词直接命中。

模型若参与解释，只能在程序给出的候选 ID 中排序/说明。名称、能力、来源和 hash 一律由程序目录回填。

## 10. P2 修复：canonical body 补齐完整工作结构

交给另一个 AI 的正文必须独立可读，不能依赖“按之前说的”“第二版”或聊天上下文。结构化内容和可读正文必须由同一个 canonical source 渲染，不能维护两份互不一致的正文。

至少固定呈现：

1. 任务目标和范围；
2. 已确认事实、用户决定、系统建议、未知/待确认项及来源；
3. 需求列表和 requirement coverage；
4. 关键工作列表，每项包括 work_id、目的、输入、输出、依赖、步骤和完成证据；
5. 完整工作步骤；
6. 交付物；
7. 完成标准；
8. 当前生效的 Skill 方法适配、输入输出、运行前提和限制；
9. 已接受补充；
10. 被拒绝/待处理变化与其是否阻断；
11. 仍未解决的事项和停止边界。

被拒绝变化及其依赖动作不得出现在无条件执行章节。无 Skill 时仍输出完整的第 1-7 项，并明确没有使用 Skill。key_work 与 requirement coverage 不能只存在于 JSON。

## 11. UI 最小修复

沿用现有 Tkinter/ttk、右键菜单和滚轮路由，不借本轮重做 UI 框架。只修复与状态和交付直接相关的断点：

1. final_result 为 not_started 时，导出按钮禁用或点击后明确阻止；不能生成空文件。
2. M4 review_required 项的“处理”入口直接定位到相应变化的接受/拒绝/取消 binding 控件，而不是只跳到通用方案页。
3. 当前存在文件时，导出流程提供明确覆盖确认；覆盖成功路径和取消路径都有测试。
4. 状态文案显示“待确认、已过期、无匹配、已跳过、已拒绝需处理”等真实程序状态，不能让用户误以为模型已经确认。
5. 用户修改上游方案后，UI 显示 Skill/最终结果已失效和下一步动作；保留旧快照供追溯。
6. 异步回调使用发起时捕获的 session/workflow 身份，不直接引用可能已经被 new/open session 替换的 self.workflow。

## 12. 必须新增或补强的回归测试

测试名称可按现有风格调整，但每项必须有可运行证据：

- R01：拒绝有 fallback 的 M4 变化会停用旧动作并呈现 fallback。
- R02：拒绝无 fallback 的变化阻止 confirm 和正式 export。
- R03：拒绝/接受/取消决定保存重开后保持一致。
- R04：正式导出前方案版本变化被拒绝；写入前验证而不是只在按钮点击时验证。
- R05：not_started 草稿/正式导出均不写空文件。
- R06：已有文件的显式覆盖成功；取消覆盖保留原文件。
- R07：同名 change_id 在两次 generation_request 中可以独立决定。
- R08：上一轮 pending/rejected 不会自动成为本轮 accepted/pending 的同一条记录。
- R09：M4 等待期间修改附注、建议决定、binding 或方案后，旧响应被拒收。
- R10：处理中重复点击、取消和迟到响应不会污染当前会话。
- R11：v0.2 selected_skills 镜像重开不生成 legacy_selection_unresolved。
- R12：v0.2 skipped 重开仍为 skipped，不被降级为 stale。
- R13：v0.1 旧字符串选择只进入迁移/待复核，不自动绑定。
- R14：目录来源字段、快照 hash、许可记录和五级核验状态能正确加载。
- R15：摄影社招新通知返回 no_match；“需求”弱词不能使 to-spec 可选。
- R16：软件规格整理和领域建模工作仍能匹配合适候选，并列出未满足前提。
- R17：canonical body 包含 key_work、requirement coverage、Skill 适配和待处理项。
- R18：共享贡献在取消一个 binding 后只在仍有依赖时保留。
- R19：三协议本地 HTTP stub 仍走现有通用适配器，不能出现 DeepSeek 专属路径。
- R20：UI 无 Skill 完整闭环、M4 复核、保存重开、导出成功路径均能操作。

不要为了维持旧测试数量而删除或无理由放宽旧断言。若旧断言断言“后两页永远 disabled”，应改成新的真实入口门槛测试，并在变更清单中说明原因。

## 13. 测试、编译、构建和 EXE 验证

完成代码后至少运行：

    .venv/Scripts/python.exe -m pytest -o addopts='' -q
    .venv/Scripts/python.exe -m compileall -q src run_promptsmith.py scripts
    .venv/Scripts/python.exe run_promptsmith.py --smoke-test
    pwsh -NoProfile -File scripts/build.ps1

若命令因环境缺少依赖失败，记录原始错误和已完成的替代检查，不能报告为通过。

构建要求：

1. 构建前备份当前可运行 dist/PromptSmith.exe。
2. 按现有 PromptSmith.spec 的单文件方式纳入必要 schema、模板、目录资源；不能写开发机绝对路径。
3. 记录新 EXE 的路径、大小、SHA-256、构建时间和资源清单。
4. 在项目目录外临时位置启动新 EXE，至少完成 smoke-test 和一个离线无 Skill 业务链：加载资源、打开/保存 JSON、生成最终草稿、正式导出。验证失败时恢复不了旧 EXE 也不能删除备份。
5. 不用真实密钥做构建验证，不把 EXE 启动成功等同于业务链通过。

真实模型项：

- 没有明确安全运行时配置时，不调用真实模型，完成 fixture/stub 和离线路径后把 M3/M4 内容质量标为未验证。
- 有授权且有安全配置时也要使用通用三协议客户端，保存 request_id、输入版本、返回模型、usage、耗时和失败原因；不回显密钥。
- 任何本地 fixture、结构 Schema 通过和程序组装结果都不能写成“真实模型内容质量通过”。

三、第一部分：模型配置与 M1 交互

1. 供应商与协议分开表达

连接区分别展示供应商、协议、API 地址、API key 和模型 ID。当前基线供应商为 DeepSeek；当前协议显示为“OpenAI Chat Completions”，可补充“按兼容接口方式调用”。不要因协议名称而让用户误以为请求发往 OpenAI 官方服务。供应商、地址和实际能力以当前配置及服务为准。

检查 UI、帮助、错误提示、日志和代码中的命名。内部标识若需要变化，为旧 deepseek_chat_completions 记录提供兼容映射，保留原始历史证据，不重写旧记录来制造新协议已被使用的印象。

为未来协议留清楚的调用边界即可，不增加空实现、多协议选择器或无用抽象。未来增加 OpenAI Responses、Anthropic Messages 时应分别实现和验证；本轮不得假设不同协议或供应商的端点、能力和响应结构通用。

2. 获取当前供应商的模型列表

在现有连接区加入“获取模型列表”，使用用户当前配置的 API 地址、供应商和运行时 API key。开发时核对当前供应商官方文档中的目录端点、认证及 base URL 规则；不能仅凭“OpenAI-compatible”标签假定支持某个端点。无法核实或端点不可用时，说明限制并保留手填路径，不用硬编码结果冒充在线获取。

要求：
- 保留手动填写模型 ID。正常列表只展示服务实际返回的 ID，不能从名字推断聊天、结构化输出、访问权限或其他能力。
- 请求在后台执行，Tk 控件仅由主线程更新；设置有界超时。在途重复点击不创建并发请求，所有结束路径恢复正确的操作状态。
- 展示正在获取、成功数量、空列表和失败原因。401/403、404/不支持、超时、网络失败、非预期格式分别给出可理解的处理提示。
- 按该供应商地址规范构造端点，避免重复 /v1 或追加到 /chat/completions 后面；不要擅自替换用户配置的服务地址。
- 请求绑定连接配置快照。供应商、地址或 key 在途变化后，旧结果不得写入新配置；可用本地配置版本判断，无需持久保存密钥。返回列表不自动选中首项，不覆盖期间手填的模型 ID。
- 列表请求不占 M1 追问轮数，不修改需求或方案确认。列表获取失败不阻止使用已有或手填模型 ID；最终能否生成仍由实际请求验证。
- API key 不进入日志、会话、错误详情、导出、截图文字或运行证据，不新增密钥持久化。
- 先用本地 HTTP stub 验证路径、认证及边界；真实供应商验证按后文统一规则进行。

3. 文本右键菜单

为常见可编辑控件提供剪切、复制、粘贴、全选，以及控件支持时的撤销；按只读、禁用、选区和撤销能力启用或禁用菜单项。只读结果可复制，不提供误导性的修改操作。复用系统剪贴板和 Tk 控件能力，菜单出现在指针附近，保留中文选区，键盘快捷键继续可用。

做可复用的绑定，不逐个控件复制逻辑；区分 Text、Entry、可编辑下拉框等能力。覆盖任务输入、回答、需求编辑、结果查看，并让后续 M2 编辑控件复用。不要引入新的 UI 框架。

4. 明确下一步操作

按程序实际状态给出一个清楚的主动作及简短原因，并保留修改、跳过、不确定、返回和保存等必要次要操作。不让“分析/继续”成为所有状态的统一按钮。

覆盖无任务、调用配置缺失、请求中、失败可重试、待回答、候选待处理、需求待复核、冲突未解、回答待评估、需求可确认、需求已确认。存在多个事项时按实际依赖引导，不因一个候选未处理就无必要地禁用所有回答操作。

主动作和导航由程序状态决定；模型 next_action、readiness 只作内容建议，不能改变权限、确认、版本或自动启动请求。不为生成导航文案额外调用模型。

开发中 M2 尚未接入时可暂时说明，最终交付必须提供可用的“生成初始方案”入口并清除占位。未实现的 Skill、最终提示及导出步骤不得显示为可操作功能。已有会话的离线查看、编辑和保存不要求 API 配置；真正调用时再校验连接条件。

5. 调查“分析/继续”疑似反复分析

这是待定位的用户现象，不预设为递归或无限循环。检查按钮绑定、busy/worker 生命周期、完成回调、网络重试、问题历史、剩余轮数和日志，用可重复的 fixture 或本地 HTTP stub 复现。

实现并验证：
- 一次分析在途时不能重复提交；成功、失败和失效响应均正确结束请求生命周期，不污染其他会话或较新请求的 busy 状态。
- 不自动递归分析或无限重试。网络重试、格式修复次数与 M1 追问轮数分别维护，有明确上限。
- 结合 field、scope、gap_id 和问题历史识别重复追问，不能只按 gap_id 字面相等判断；同一缺口换措辞或新造 ID 不应绕过历史。不同子任务或不同缺口也不能仅因 field 相同就一并封锁。
- 区分已解决、部分回答、跳过和不确定。必要细化、新证据或用户明确要求重开，沿用现有受控更新与重开通路，通过来源、依赖、范围和预算校验；不把“回答过”直接等同于“已经解决”。
- 无新增有效候选、缺口变化、合规新问题或其他可见业务进展时，提示“本轮没有形成新进展”，保留数据，说明可补充或修改什么以及如何显式重试，不自动再次调用。
- 如比较输入快照或输出指纹，应比较任务、类别、活动需求、缺口、回答和问题状态等业务内容；不能仅比较 assistant_text，也不能把确定性去重说成能识别任意语义等价。
- 追问预算耗尽时停止继续追问，保留未知并给出编辑/复核路径；单个问题被跳过后不自动复问该缺口。轮数耗尽不等于需求完成，不自动确认，不暗中重置预算。
- API 失败与成功但无进展分别记录和提示；失败保留原有需求及业务状态，可由用户显式重试。

报告具体复现、根因及修复证据。若未复现无限循环，如实说明验证了哪些保护，不因增加防重复点击就宣称所有反复分析问题都已解决。

6. 字号与布局

在现有 Tkinter/ttk 上做定向改进：整体字体更易读，任务、需求和方案获得合适的阅读面积，减少固定高度造成的大片空白，主操作位置稳定，长内容可滚动，窗口缩放时布局合理伸缩。新 M2 页面沿用同一风格。

检查 1120×780 窗口和可测试的 Windows 125%/150% 缩放，避免文字、按钮和滚动区遮挡或裁切。可实际检查的条件留下截图或记录；不能测试的条件明确列为未验证，不用修改字号冒充系统缩放测试。不迁移 Qt/Web，也不重做整个软件视觉系统。

参考图只用于理解模型配置的信息层级和留白。除本提示明确要求的模型目录能力外，不据图添加设置或管理后台功能；图片无法访问不影响按文字要求推进。

四、内部检查点与共用能力

第一部分完成后做针对性 API、控件、状态和重复提交/无进展检查，确认 M1 需求确认、冲突、未知及保存路径没有回归，直接进入 M2。中途无需重复完整打包。

M1、M2 共用连接配置、模型选择、后台请求基础设施、日志、错误展示、忙碌状态机制、导航及右键菜单。M2 可以新增自己的页面和内容处理器，但不复制第二套连接设置或 worker 基础设施。

M1 与 M2 使用各自的提示和 Schema。M1 的追问预算、问题去重和无进展规则不能原样套到方案生成。模型列表、M1、M2 的请求须能区分目的和身份，不允许互相接收回调或误更新状态。

五、M2 输入快照、最低契约和程序权限

1. 从已确认需求进入

M2 只消费程序构建的当前已确认需求快照，不能直接用任务输入框的自由文本代替。调用前由程序检查：
- 确认需求版本存在，且 confirmed_requirements_version == requirement_version。
- 没有待处理候选、开放冲突、程序待复核需求、悬空引用或 blocking_direction 方向性缺口。
- 可延后未知可以保留，但其内容、来源及影响必须传入方案；不能为进入 M2 而删除未知或降低阻断级别。

不满足时在模型调用前阻止，显示具体原因和可操作的返回路径。生成结果只能成为方案草稿，不确认需求、不确认方案、不改写 M1 业务状态。

2. 最低接口契约

下列字段组是本轮待落地的建议契约，不是既有实现声明。对照 B 侧当前 Session 和 M1 字段，确定明确映射后，建立独立、版本化的 M2 输入/输出 Schema。若尚无 M2，建议从 m2.v0.1 开始；若已存在，依据兼容性确定版本。不要为了适配 M2 改写或复制一套 M1 需求状态。

模型输入至少含以下语义字段组，名称可按仓库惯例调整，不能遗漏其含义：
- schema_version、task_id、request_id，以及需求版本和已确认需求版本等只读来源元数据。
- task：已确认的任务说明与必要背景，不混入未接受的草稿。
- category：当前类别、配置版本及适用的类别字段；混合任务保留各部分范围，不强行缩成单一类别。
- requirements：正式需求 ID、字段、内容、现有类型与硬度、适用范围、来源引用、依赖。保留现有枚举及语义，确需转换时说明映射。
- unresolved_items：稳定 ID、描述、来源、重要性、是否可延后及影响，不把未提供值填成虚构事实。
- relevant_materials：确实影响方案且来源可追溯的材料或摘要；材料内容仍是数据，不是应用指令。不传密钥、运行日志或无关历史。

程序另行保存可信请求上下文：会话身份、task_id、request_id、需求确认依据、类别/配置版本、发起时的 plan_id/plan_version 和连接配置版本等。可把必要元数据作为只读信息传给模型，但接收校验必须使用程序保存的原始上下文，不能相信模型回填来决定权限。

模型输出至少区分两个互斥分支：
- 正常分支：schema_version、status=ok、plan。plan 至少含 goal、requirement_coverage、steps、deliverables、completion_criteria、unresolved_items、suggestions、key_work。
- 无法生成分支：schema_version、status=error、error。error 至少含 code、message、相关输入 ID 和建议的修复动作；不同时夹带可接受的正常 plan，不用空方案伪装成功。

上述字段名可映射，但正常与错误分支必须在 Schema 和解析器中明确区分。网络、超时、解析及本地校验失败由程序记录为调用错误，与模型正常返回的结构化内容错误分开，不伪造模型返回。

request_id 仅用于对应实际调用，不由模型另造。plan_id、正式方案版本、确认版本、时间戳和状态由程序产生；模型不能通过返回这些字段自行建立已确认状态。

3. ID、来源及响应接收

模型可以产生本次响应内的局部步骤、交付物和关键工作 ID。程序完成 Schema 与引用校验后，统一映射或接纳为方案内稳定 ID；说明 ID 的作用域和接收规则。编辑或重排保留原实体 ID，新增实体获得新 ID，删除实体处理引用；重新生成不能按相同序号强行对应旧实体。不要混用步骤显示序号与稳定 ID。

requirement_coverage 引用只能来自本次输入中的正式需求 ID。所有已确认要求应被明确承接，硬约束不得遗漏；可关联具体步骤、交付物、完成标准，或说明它如何作用于整份方案。程序检查覆盖集合和引用，内容是否忠实仍需人工复核。来源要求快照由程序保留，模型对其转述不能覆盖 M1 原文。

每次请求在途不重复提交。返回时检查会话、任务、需求版本、类别、连接上下文和发起时的方案版本仍适用；期间切换会话、改变需求或编辑旧方案后，迟到结果不得覆盖新状态。相同响应只接收一次。失败、非法或过期响应保留原草稿及用户修改，不发生半份方案写入。

4. 接口交付必须可直接对接

除 M2 提示正文和输入/输出 Schema 外，提供：
- M1/Session → M2 输入 → 模型输出 → 方案持久化的字段映射表，注明字段来源、空值语义和维护方。
- 至少一份可校验的正常输入 JSON、正常输出人工样例，以及一份结构化错误输出人工样例；另有边界输入及预期行为。
- 局部 ID 接收/映射、错误码、失败展示、入口拒绝、过期拒收及版本失效规则。

人工样例标为 fixture，只作开发和校验材料，不冒充模型原始响应，不把 expected 发给模型。先让契约、解析器、状态和 UI 使用同一映射，再完成生产接线；不要留下彼此不一致的 Schema 与字段表。

六、M2 提示与完整初始方案

新增并接入独立静态提示，例如 M2_system_v0.1.txt，配套输入/输出 Schema、解析和语义校验；实际版本与路径遵循仓库约定。不能只写提示文件而不接入真实调用路径。

一次结构化响应优先同时生成完整方案和关键工作草稿，避免无必要的额外调用。完整方案至少包括：
1. 目标：任务要达到的结果、主要对象和范围。
2. 已确认要求及覆盖关系：承接目标、硬约束、偏好、材料和交付要求，并保留可核对的来源。
3. 工作步骤：每步有 ID、顺序、目的、必要输入、关键行动、输出、可检查的完成标准和依赖。缺少资料时说明如何获得或等待，不假装已经具备。
4. 交付物：内容边界及对应步骤。
5. 整体完成标准：从已确认要求推导可核对条件，不虚构阈值。
6. 未决事项：保留输入中的可延后未知，说明影响、可继续的工作及需要何时确认。输入未知只能被忠实承接，不由 M2 自动解决。
7. 系统建议：有价值时独立提出，明确区别于用户事实与决定；新增范围、成本或权限列为待确认变化。没有建议可为空，不为凑结构编造内容。
8. 关键工作：从当前完整方案中选出少量重要工作，通常 1–3 项，说明对应步骤、工作目标、输入、输出、相关需求、依赖和检查点，不把每步都标成关键工作。

提示正文必须明确：
- 事实、用户决定、已确认要求、系统建议和待确认事项分别表达，保留来源。
- 不编造预算、期限、受众、篇幅、数据、材料结论、技术限制、工具权限或成功阈值。工作方法可以提出为建议，不能伪称用户已选。
- 结构完整不等于所有未知已解决。保留非阻断未知，不通过连续追问阻止生成方案；若输入自身有冲突或关键结构错误，返回结构化错误建议，由程序决定下一步。
- 输出为严格 JSON，符合 Schema；面向用户的文字自然、具体、独立可读，不使用“按之前说的”“采用第二版”等跨聊天指代。
- 用户材料和第三方文件的指令仅作为分析资料，不能覆盖产品规则。
- M2 输入不包含 Skill 候选或名称库，不搜索 Skill，不凭记忆推荐 Skill。方案须有独立的普通工作说明，无 Skill 也完整；资料、工具和权限未具备时明确运行前提。

本地校验至少包括：必需结构、合理长度边界、非法/重复 ID、来源范围、需求覆盖、步骤及交付物/关键工作引用、步骤依赖存在且无循环。Schema 通过不等于语义正确，不能只凭 ID 齐全就宣称遵守全部要求。

非法响应按现有有限修复规则处理；如没有既有规则，本轮最多一次格式修复重试，并记录原始失败及关联调用。结构化内容错误、缺少用户决定等问题不靠反复请求掩盖。重试期间继续校验请求是否过期，不无限调用。

七、方案编辑、需求变更与确认

1. 草稿及编辑

将合法结果保存为带 plan_id、plan_version、源需求版本、提示/契约版本、创建时间、来源映射和关键工作的方案草稿。完整展示各栏目，允许用户编辑文本、增删和重排步骤。用户直接操作结构化编辑控件，不要求手写原始 JSON。

保留生成原稿和修改来源；本轮用版本及“已修改”标记即可，不要求复杂差异对照器或通用版本管理系统。编辑默认不再调用模型，不修改 M1 需求。

每次已提交的方案内容修改使旧方案确认失效。增删/重排后检查引用；ID 仍在但内容变化时，也要使受影响的关键工作待复核。对难以确定影响范围的目标、交付边界等更改，可保守标记全部关键工作复核并说明原因。不要默默删除失效引用、重指向别的步骤或因为 ID 未变就自动认为对应关系正确。

本轮至少支持人工修订并明确复核关键工作。若提供模型重新提取入口，必须由用户显式触发，绑定当前方案版本，返回内容只更新对应草稿，不自动重新生成整份方案或覆盖用户编辑。

2. 明确提供“修改需求”入口

方案页提供可见的“修改需求”操作，返回 M1 需求卡，保留当前方案。旁边简短说明：目标、硬约束、交付范围等已确认要求需要在需求卡中修改并重新确认。

区分两条路径：
- 普通方案编辑：只更新方案版本并撤销方案确认，不因此改写需求版本；相关关键工作按影响复核。
- 实际需求变更：走 M1 现有编辑、来源、冲突、复核和确认逻辑；有效需求版本变化后，旧方案保留但标记为过期，不能用于后续模块。

仅点击“修改需求”、打开需求页或返回而未实际修改，不因导航本身递增需求版本或作废方案。用户明确撤销需求确认时，沿用既有确认规则，M2 入口随之关闭。

程序不能仅靠关键词宣称自动识别任意自由文本中的需求变化。方案复核区并列展示关键要求，提示用户若改变已确认要求则使用“修改需求”；对于已经标记的冲突或待复核事项，必须处理后才能确认。不要求每次措辞调整都弹出需求变更询问。

需求重新确认后，本轮至少提供“基于新需求重新生成”恢复路径，保留旧方案及其修改。若实现“复核后沿用”，必须逐项复核受影响内容、建立绑定新需求版本的新方案版本并再次确认；不能仅改 source_requirements_version 就使旧方案恢复有效。不为此新增复杂自动合并系统。

3. 独立确认方案

只有用户明确确认当前方案版本后，程序才记录 confirmed_plan_version。前置条件包括来源需求仍有效且已确认、方案结构及引用有效、关键工作和已标出的阻断事项已处理。明确可延后的未知不因仍存在而一律禁止确认。

方案确认不等于接受独立列出的全部可选建议，也不替代需求变更确认；涉及新增范围或成本的建议保持待确认，不能悄悄成为硬约束。

关键工作可随生成作为草稿出现，但只有与用户最终确认的当前方案一致、且复核完成后，才具备后续使用条件。本轮不实际启动 Skill 检索。

八、JSON 保存与整体用户路径

复用现有会话保存机制，支持草稿、已编辑及已确认方案的保存重开。方案、来源快照、版本、确认依据、未决项、关键工作及复核状态均应保留；重开不触发模型请求，不保存 API key。

更新会话 Schema 时对旧文件提供默认值或迁移，旧 M1 会话重开后不凭空拥有已确认方案。未知的新格式明确报错，不按旧格式静默截断。沿用原子保存和错误反馈，写入失败保护原文件。重开时重新检查版本及引用一致性，不能仅凭保存的显示文字就把过期方案当成有效。

最终路径：
输入任务 → 分析提取 → 回答/跳过/修改 → 确认当前需求 → 生成初始方案 → 编辑及核对方案与关键工作 → 确认当前方案 → 保存 → 重开。

返回路径：
方案页点击“修改需求” → M1 实际修改 → 旧方案标记过期 → 重新确认需求 → 基于新需求生成或明确复核 → 再次确认方案。

M2 接入现有初始方案步骤，复用连接区、导航、字号、滚动和右键菜单。明确展示需求前置不足、可生成、生成中、失败可重试、草稿待核对、关键工作待复核、可确认、已确认、来源需求变化导致过期及保存失败。每种状态给具体原因和下一步，不保留“待接入 M2”作为完成结果。

九、统一验证与验收范围

先用现有测试工厂、人工 fixture 和本地 HTTP stub 验证程序行为，再在具备授权与运行时配置时验证真实供应商及模型。人工 expected 不发给模型。不要为静态文案重复堆大量测试，重点覆盖状态、权限、引用、并发和持久化。

1. 类别与内容覆盖

六类任务及通用入口均做最小有效输入的契约与接线检查：writing、presentation、learning、planning_research、data_analysis、coding、general；实际枚举若已更新，应以代码为准并说明映射。每类只传与任务相关的字段，允许未知，不要求所有类别字段一律填满。通用入口至少有一个混合任务案例，检查不同部分的范围和交付物未被丢失。

内容验收至少包括一个编程任务和一个非编程任务，例如写作或 PPT；至少一例保留可延后未知。编写检查判据时，明确类别特有要求如何进入步骤、交付物及完成标准，例如 PPT 的受众/时长/核心结论、学习的基础/目标/可用时间、数据分析的指标定义/数据情况等；未给出的内容仍保留未知。

另准备边界输入和错误样例，覆盖入口拒绝、非法模型输出及编辑后失效。若仅使用人工输出或 stub，只能说明契约和接线通过；没有真实生成的类别标为未实测。即使两例真实通过，也只说明对应样例通过，不能宣称全部类别模型效果稳定。

2. 必须记录的验证项目

- 协议与供应商正确区分，旧标识兼容且历史证据不重写。
- 模型列表正常、空、鉴权失败、不支持、超时、网络失败、格式错误；端点及认证正确，密钥不进证据；配置变化及用户手填模型 ID 时迟到结果不覆盖。
- 文本右键菜单与快捷键，覆盖 M1、M2、中文选区、可编辑和只读控件。
- M1 在途重复点击、换措辞/新 gap ID 的重复问题、无进展、部分回答、跳过/不确定、预算耗尽、新证据/明确重开、网络失败重试；未知、冲突和确认保护无回归。
- 七个入口使用共同 M2 通路，类别字段不丢失；编程与非编程内容案例有逐项判据，正常方案保留可延后未知且不编造条件。
- M2 缺少需求确认、确认过期、候选/冲突/待复核/方向性缺口/悬空引用时，在调用前阻止。
- M2 缺项、重复 ID、非法来源或交叉引用、循环依赖、结构化错误及格式修复上限；失败不覆盖原草稿，原始响应和错误可复核。
- 方案步骤增删、重排及内容改写后，稳定 ID、引用和关键工作复核正确；普通方案编辑不改需求版本。
- 在途重复点击、需求/类别/配置变化、切换会话、编辑旧方案、重复回调均不覆盖较新状态或重复接收。
- 仅导航至“修改需求”不使方案失效；实际修改需求后方案过期，重新确认与恢复路径可用；确认方案不能绕过需求确认或待处理的阻断事项。
- 草稿和确认方案保存重开一致，旧 JSON 可迁移、未知新格式报错、保存失败保护原文件，无密钥，无重开自动调用。
- 完整走通正常路径，以及确认方案后返回修改需求的路径，主动作与禁用原因清楚。
- 源码烟测、相关全量回归、现有 PyInstaller 构建及产物烟测；M1/M2 当前静态提示和 Schema 资源实际装入产物。历史测试数量不作为本轮应通过数量。
- 主窗口和 M2 页的长文本、1120×780、可测试的 125%/150% Windows 缩放。记录实际环境、截图或检查记录；不可测条件单列未验证。

第一部分做针对性检查，M2 完成后统一做一次最终全量回归、完整路径和构建验证；有新改动、失败或未解决疑点再重跑相关部分，不无目的反复打包。

已有用户授权且有可用运行时配置时，沿用授权执行相关真实请求，保存模型/供应商、实际参数、提示及契约版本、原始响应、用量、耗时和人工判定。缺少配置时完成离线开发验证并列出真实验证缺口，不搜索磁盘凭据，不把密钥写入代码或证据。

分别报告“功能实现”“离线程序验证”“真实模型/供应商验证”“人工与跨机体验”。未验证不写成通过；发现实际失败不靠修改 expected 或删除用例掩盖。单机烟测不等于跨机可用，程序接线通过不等于内容质量通过。

源码的 Chat Completions 路径在 `finish_reason == "length"` 时抛出这一错误。本次不是超过 120 秒的超时，也不是用户漏点某个按钮。

确认存在三项程序设计问题：

1. `src/promptsmith/api.py:20` 将结构化调用统一限制为 8192。请求没有显式配置思考模式或强度。2026-10-01 阅读的 DeepSeek 官方文档说明，当前模型默认开启思考，默认强度为 high；思考模式的默认生成额度为 64K，非思考模式为 8K。程序显式传入 8192，覆盖了服务商的默认额度。
2. 之前的截断修复主要针对 M1 第二轮增量分析。M2 仍加载 `M2_system_v0.1`，没有明确区分“制定讲义的工作方案”和“直接写完整讲义”，也没有控制步骤、每项描述及重复展开的篇幅。后者是风险因素，不能从本次空响应记录断言模型真的写了整篇讲义。
3. `workflow.py:321` 的 M2 调用捕获 `ApiError` 后重新构造空 `ApiResult`，丢弃了异常携带的部分文本、用量、响应 ID、模型和停止原因。M3/M4 的 `delivery_workflow.py` 和 M5 也有类似路径，因此日志不足以分析这次词元具体花在了哪里。

同一会话相邻三次成功 M1 调用的生成用量为 3216、5691、3923，其中思考用量分别为 2512、4918、3377。这证明本次配置下思考消耗不可忽略；**不证明失败的 M2 恰好用了多少思考词元，也不证明其可见方案超过了 8192。**

本窗口用一个携带部分 JSON、用量和停止原因的合成 `ApiError` 调用现有 M2 处理路径，确认这些信息全部丢失，pending request 被清理，错误仍为 truncated。此次复现没有真实模型调用。

官方来源，核对日期 2026-10-01：

- [Chat Completions 参数](https://api-docs.deepseek.com/api/create-chat-completion)
- [思考模式与强度](https://api-docs.deepseek.com/guides/thinking_mode)
- [当前模型与能力](https://api-docs.deepseek.com/quick_start/pricing)

结论：同一类“长度截断”现在发生在不同模块。需要补齐共享调用策略和 M2 输出控制，而不是再次只修改 M1 或延长等待时间。精确到本次响应的词元分配已被程序丢弃，不能补造。

### 2. 修复输出额度与思考模式的匹配

用一个小而明确的配置或参数生成方法替代所有结构化调用都写死 8192 的方式。优先适配当前接口，不为此重写客户端或搭建复杂框架。

对已核实的官方 DeepSeek 地址和当前支持的模型，首选验证以下组合：

```json
{
  "model": "deepseek-flash",
  "max_tokens": 32768,
  "reasoning_effort": "low",
  "response_format": {"type": "json_object"}
}
```

这是本轮建议的起点，**尚未实测**。32768 用于给思考和完整 JSON 留余量，不是要求模型写满；low 也不代表关闭思考。不得因降低强度而允许遗漏要求、编造事实或减少必要校验。真实验证后若质量或用量不合适，应据证据调整并说明。

实施细节：

1. 官方能力判断应核对规范化的服务地址和支持的模型；仅凭可任意填写的 provider 标签不够。自定义地址默认走兼容策略，除非已有明确能力配置。

4. M1-M5 的结构化调用都应使用同一套已解析的策略；允许按模块设置合理额度，但不要各自复制一份常量。已有 `complete_text` 的短文本限制不要无关扩大。

6. 连接测试只负责测试连接，不随正式方案策略扩成高成本生成。原有连接探测的专用行为要单独核对。

### 3. 让 M2 生成完整方案，而不是直接执行整项任务

新建并接入有版本说明的 M2 提示，旧版保留。优先沿用当前 `m2.v0.1` 契约；改提示不自动意味着必须改 Schema。

保留原有所有工作规则，再加入以下可直接使用的指导，按当前字段做适配：

```text

“完整”是目标、需求覆盖、工作步骤、交付物、完成标准、未确定信息、建议及关键工作齐备；不需要把最终讲义、报告、整套幻灯片或程序代码写入方案。

对一般任务，通常安排 3–6 个有依赖顺序的步骤，1–3 个交付物、3–5 条整体完成标准及 1–3 项关键工作。没有必要建议时 suggestions 可以为空。数量是组织建议，不是截断用户要求的硬上限。

每个步骤写清目的、所需输入、具体行动、输出及检查方法。每个行动用一两句话表达；输出写交付内容或结构，不写该交付物的完整正文。不要为了满足字段而反复复制同一句话。

一般任务的自然语言内容以约 1200–2500 个中文字为篇幅参考，不包含 JSON 字段名和 ID。这个参考不等于模型词元上限，不作为程序拒收标准。要求较多时可以超过参考篇幅，优先保证所有硬约束和全部需求 ID 被覆盖，全部未确定信息被保留。

已有资料中的“可能”“推测”及未核实内容不得升级为已证实事实。用户接受某个研究或学习方向，不等于证实某个术语定义、理论结论或资料的真实性。确有必要时把核对原始材料安排在相关步骤中，避免无根据地展开技术细节。

未知的学习基础、受众细分等信息，说明它影响哪部分、当前能先完成什么、何时需要核对；不能仅因存在允许延后的未知就返回“信息不足”。存在真正无法继续的输入问题时，按原契约返回结构化错误。

```

### 5. 失败时原地恢复，重试必须有实际变化

正常路径应是点击“生成方案”一次得到可查看的方案。修复重点是减少正常任务的截断，不只是增加一个重试按钮。

万一仍被截断：

1. 保留当前需求、回答、旧方案、编辑内容和确认状态；清理本次 pending/busy，恢复主操作按钮。
2. 在原主操作位置给“重新生成方案”，旁边自然说明：“这次没有收到完整方案，你的需求已保留。可以重新生成。”详细日志路径放在可展开的详情里，避免撑乱页面。别因恢复跳回首轮问答或要求用户重新确认全部需求。

4. 若提供针对截断的重试，保留完整输入、全部需求覆盖和未确定信息，通过简洁版方案指导减少重复展开；已核实服务可在明确的有限范围内调整额度，例如 32768 到 65536。不得超出模型能力，重试参数和尝试次数必须可追溯。

## 1. 初版模型配置

**建议：暂时继续使用 DeepSeek Chat Completions、`https://api.deepseek.com` 和配置模型 `deepseek-chat`。** M1 v0.3 的两个案例和一条两轮链路已经在这套配置下跑通；当前 v0.5／`m1.v0.2` 完成离线收尾，但新增字段仍需真实多轮测试。三周周期内更换接口会增加适配成本。

需要知道：真实响应的 `model` 字段曾返回 `deepseek-flash`。程序同时保存配置模型和响应模型，不推断供应商内部路由。比赛材料若需要写固定模型名称，应以演示当天的官方说明和响应记录为准。

## 2. 当前界面是否可作为迭代底稿

请从 `dist/PromptSmith.exe` 启动，重点检查：

1. 四步导航是否能让人理解当前只开放“输入与需求”。
2. API 配置、任务输入、候选需求、追问和正式需求的排列是否顺手。
3. “接受／忽略／编辑／撤销／回答／跳过／不确定／确认需求”的名称是否容易理解。
4. 窗口缩放后是否有文字遮挡、按钮不可见或列表难以操作。

**建议：先接受功能布局作为阶段二底稿，只记录最影响演示的 UI 问题；视觉优化与 M2 接入并行迭代。** 当前已有自动化 UI 合同和真实两轮控件链路，但这不等同于人工体验验收。

## 3. M1 与 M2 的先后顺序

**建议：阶段一、二程序收尾完成后进入 M2 内部开发，同时补 v0.5 小范围真实路径。** 顺序为：

1. 未知、部分、完整回答和明确重开路径，检查新增结构化字段。
2. 案例 02 的“仍有一次追问预算”变体，确认明确修改不会被重复询问。
3. M2 只读取当前已确认需求快照；真实测试发现严重问题时只回修 M1，不把未验证行为扩散到下游。

这两条是现有最关键的未实测状态边界，比立即扩展六类完整回归更适合当前时间。

## 4. API Key 轮换

本轮测试密钥没有写入代码、会话、运行日志或发行目录，扫描也没有发现符合完整密钥形态的内容。但密钥曾在聊天消息中明文出现，**建议测试结束后在 DeepSeek 控制台撤销并新建密钥**。新密钥只在应用运行时输入，不要提交到 Git 或写入配置文件。

**建议：在演示前安排一次。** 只把 `dist/PromptSmith.exe` 复制到另一台目标 Windows 电脑，检查程序能启动、能保存会话，并在输入临时密钥后完成一次连接测试。当前已经验证本机临时目录中只有这一份 exe 时可以启动，但不能据此声称跨机发行已经通过。

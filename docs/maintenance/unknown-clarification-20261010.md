# 未知事项先核对，再确认方案

日期：2026-10-10。源码修复已完成，离线与实际 Tk 验证见 [验收记录](../../verification/unknown_clarification_20261010/results.md)。

## 问题与原因

用户截图中，现有代码及运行材料未提供、交付形式尚未确定，界面却直接引导“确认方案并生成提示”。此前的容错把模型可以生成草稿，误当成用户允许暂缓所有未知。`confirm_requirements` 只检查方向阻断项，M2 新未知没有对应确认动作；主动作优先处理已确认需求/方案，问题和未知只作为文字说明。

## 当前行为

- 需求缺口的 `can_defer` 表示可以后置，仍需用户明确选择。尚未核对的事项逐题展示，用户可以回答、“我不确定”或“使用时再补充”。不使用中文关键词猜测重要性，不要求所有信息必须填齐。
- M2 可以接收并生成含未知的草稿。方案新增问题先进入同一组卡片，主动作和阶段提示优先引导核对；需求、方案、Skill 和生成入口共用 SessionState 检查。受阻时回到问题卡片，避免错误弹窗和无后续操作。
- 回答保存原文、来源与问题历史；第一条回答使旧需求确认和方案失效，剩余卡片仍保留。整组答完后一起发送 M1；最后一条选择暂缓也会提交先前的答案。重新核对需求、生成方案，用户再明确确认方案。
- 暂缓不自动确认、不修改需求或方案内容、不新增模型请求。全部暂缓后，可单独点击确认继续；未知仍随最终提示带出，供下游 AI 核对。已选 Skill 的格式和建议继续宽松接收。
- 显式草稿授权继续有效，程序加在来源未知上的草稿说明不会被误当成新问题。历史会话中已明确跳过/不确定的来源未知继续兼容；尚未核对的新事项仍提示核对。
- 普通引用编号的重写不会重复询问同一未变缺口；缺口描述/重要性变化、方案目标或相关确认需求变化会重新核对。方案新增未知的决策随问题历史保存，不用独立 UI 状态保存业务事实。

## 实现与约束

`clarification.py` 提供只读的问题投影、内容依据指纹和共享的 M2 来源描述。`SessionState.questions_for_review()` 合并已有问题与尚未核对的缺口；回答时才固化当前问题组，以便方案失效后仍继续收集。`record_question` 保存真实回答或暂缓记录。需求/方案预览包含问题及历史快照，旧卡片不能确认更新后的内容。

`conversation.py`、`guided_flow.py` 和 `ui.py` 共用这些方法；不会另建一份需求数据，不绕过工作流、请求/版本、会话切换和 Tk 主线程保护。`validate_delivery_entry` 防止直接调用交付绕过核对；已经明确暂缓的普通事项不会形成新的末端门槛。

Debug 记录任务、问题、阶段、answered/unsure/skipped 决策及转回澄清操作；方案落地记录未知/问题数量。只读预览检查用 DEBUG，用户实际决策用 INFO；不把回答正文或密钥写进新增日志。保存仍由用户点击控制台按钮触发。

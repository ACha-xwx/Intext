# 新建和打开对话：隔离旧后台请求

2026-10-09；代码已修改，运行回归按用户要求留到本批五个 BUG 修完后统一进行。

## 症状和原因

旧 M1 正在等待模型时新建对话，新空对话仍显示“正在整理”且无法发送；旧结果最终被业务层拒绝，但“已拒绝旧返回”又覆盖了新对话的状态。旧响应格式有问题时仍可能执行自动修正。

`new_session` 和 `open_session` 原先只复位 Skill/交付状态，没有清除通用 `busy` 和 M5 活动请求。`_submit` 未隔离会话回调；M1/M2 后台 lambda 还会在执行时读取已被替换的 `self.workflow`。

## 统一回归状态更新（2026-10-10）

用户已解除延期，TaskScope 6 项与 UI 会话取消 20 项通过，原阻塞、排队、成功/失败和同 task_id 重开边界均有离线证据；实际 Tk 新建/重开及后续交付可用。最后 M1/取消/超时关联 72 项复验通过。完整报告见 [本批验收](../../verification/bug_batch_20261009/results.md)。未调用真实模型、未重建 EXE；下方“待验证”是实施时记录，服务端已发出推理仍不承诺即时撤回。

## 本次实现

- 新建/打开成功时取消旧会话作用域，取消排队任务，清空 busy / busy_kind、M5 活动请求、搜索和交付状态，重新显示当前会话。取消新建、取消文件选择或打开失败不影响原任务。
- 通用后台任务捕获取消作用域；模型调用前后和 M1 自动修正边界检查取消。已进入完成队列的成功/失败，也在 Tk 主线程检查作用域后才操作界面。
- M1/M2 捕获原工作流及会话实例 token；重新打开相同 task_id 也能隔离旧回调。沿用业务版本、请求身份及配置检查。
- 清空旧对话未发送的输入并重绘时间线；卡片操作 token 包含会话实例，避免相同任务重开后旧卡片继续有效。
- 旧阻塞调用仍占用线程时退休原执行器，新对话使用新执行器。原线程在 HTTP 返回/超时后退出；关闭应用同时清理当前及退休的执行器。
- 索引预热使用应用作用域；普通会话切换保留预热。模型配置和已保存设置保留，旧探测结果不会改写新会话的忙状态。
- Skill 查询规划、适配筛选不把取消包装成可降级错误；取消后不再继续向模型请求正文核验。
- Debug 以 INFO 记录会话任务作废/后台取消，DEBUG 记录丢弃的回调，真实错误仍保留详细异常链。仅用户点击“保存日志”才写盘，保持分级颜色和密钥脱敏。

阻塞 urllib 请求已经发到服务端后，无法保证即时撤回服务端推理，也无法保证取消此次费用；本次保证新会话独立运行、旧响应不落入新会话、旧任务在取消边界停止后续请求。

## 待统一验证

新检查已写在 `tests/test_task_scope.py` 和 `tests/test_ui_session_cancellation.py`，尚未执行。

1. M1/M2/M5 分别处于等待期间，新建和打开；旧成功/失败不得修改新对话、弹旧错误或解除新请求的忙状态。
2. 旧回调已经排队后切换；新状态和输入保持有效。
3. 重新打开同一 task_id；旧工作流和旧 token 不得进入新会话。
4. 两个旧线程同时阻塞及第三个旧任务排队；新任务及时开始，旧排队任务不执行。
5. M1 首次/修正响应取消；不解析旧响应，也不继续第二/第三次请求。HTTP 返回后取消、Skill 查询/适配取消均正确退出。
6. 索引预热不因新建对话停止；同一会话的正常调用、配置失效、Skill/M3/M4 取消及退出清理保持有效。
7. 源码真实 Tk 中确认空对话可输入，正常后续结果可显示；Debug 有取消/丢弃记录且无自动日志文件。
8. 同批核对试运行删除、旧会话兼容、复制/导出、设置加密恢复；此前中断的两组 pytest 有部分失败，需排查后区分新问题和历史契约差异。

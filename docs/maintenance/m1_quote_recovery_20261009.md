## 此次日志的实际原因

用户首轮输入：“我想把一个基于python + tkinter的软件的UI页面重新设计修改，主要是布局和各个元素的样式”。

模型在一项候选的 `source_refs.quote` 中写了“把...的UI页面重新设计修改”。省略号使这句话不再是原始输入的连续片段，M1 原先逐字检查因此拒绝首轮响应；用户的输入本身没有问题。

只读检查本地同 request_id `req-0799225834ca4e5aaa7065108b88ac87` 的两份运行证据：第一份 API 14,230 ms，校验失败并标记 `retry_with_contextual_correction`；第二份 API 19,511 ms，`valid=true` / `attempt=2`。因此该 ERROR 表示中间一次内容校验失败，之后自动修正成功，用户才看到正常结果。它额外增加了一次调用和约 19.5 秒的模型等待。未调用真实 API，也未对原始数据运行回归。

## 修改

- M1 Schema 通过后，检查候选/缺口/问题的来源引用。来源存在且能够唯一按顺序匹配时，将省略号、空格、英文大小写差异还原成原始来源中的连续片段。候选文字、kind、依赖和用户确认状态保持原有业务含义。
- 不以原文替换任意语义改写；未知来源、虚构引文、反序和多处匹配仍走原校验/修正路径，不伪造用户事实。
- `normalization` 记录还原动作、字段路径及来源编号，Debug WARNING 说明本地兼容；原始模型响应保存不变，有效响应另存原有 `response.effective.json`。
- RunEvidenceWriter 对明确将继续自动修正的失败尝试使用 WARNING（黄色），最终失败和 API/网络错误仍 ERROR（红色）。所有严重级别仍保留完整异常堆栈和原始 check 文件，日志依旧由用户手动保存。
